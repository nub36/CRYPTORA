## 1. Резюме

CRYPTORA — крипто-терминал (React 19 + TypeScript + Vite, ~31 000 строк TS/TSX, 17 страниц + 404) с грамотной архитектурой провайдеров данных и **высокой культурой «честности данных»**: большинство старых заглушек уже устранено в v0.8.24–0.8.44, демо-режим выведен из production, статические наборы заменены на реальные API.

**Общий вердикт: проект в хорошем инженерном состоянии** (typecheck — 0 ошибок, 566/566 unit-тестов, 66/66 e2e, сборка — ок), **но найдено 7 немаркированных синтетических данных (заглушек), 5 функциональных багов (главный — страницы не обновляют данные после первой загрузки), 2 уязвимости в production-зависимостях и разрыв ~40 версий между кодом и прод-сервером.**

Ключевая проблема — не «мёртвые» разделы (их нет), а **точечные фабрикации в живом провайдере**, которые противоречат собственному инварианту проекта («никаких выдуманных чисел», `docs/DONT_DO.md` §Подходы-1/4) и не помечены в UI.

## 5. Найденные заглушки (синтетические данные)

### 5.1 КРИТИЧНО — показываются как реальные, без маркировки в UI

**З1. Таблица «Пары на ведущих биржах (Spot Market)» на странице монеты — полностью синтетическая.**
`src/services/data/LiveMarketDataProvider.ts:318–336`: объём Binance = `volume24h * 0.65`, KuCoin: цена `price * 0.9998`, объём `volume24h * 0.35`, спред `0.02`. Отображается в `CoinDetailPage.tsx:806–846` как фактические данные бирж. Реального запроса статистики KuCoin для этой таблицы не делается, хотя адаптер `KuCoinSpotAdapter.fetch24hrStats()` уже существует. (Частично признано в `docs/LIVE_DATA_AUDIT.md` §6, но в UI пометки нет.)

**З2. «Макс. 24ч / Мин. 24ч» = цена ×1.03 / ×0.97 при недоступных свечах.**
`LiveMarketDataProvider.ts:249–250` → UI `CoinDetailPage.tsx:446–447`. При этом в ответе Binance `GET /api/v3/ticker/24hr` есть **реальные** `highPrice`/`lowPrice` — они просто не мапятся в `normalizeBinanceTicker` (`adapters/normalization.ts:5–32`).

**З3. Индикаторы-заглушки при <26 свечах.**
`LiveMarketDataProvider.ts:253–262`: RSI = `50`, MACD = `{0,0,0}`, SMA20/50/200 = текущая цена, Bollinger = цена. Нарушает собственное правило проекта «0 ≠ null / нет данных» (P-фикс v0.8.44 применил эту семантику к OI и бете, но не к индикаторам).

**З4. Абсолютный OI = `quoteVolume × 0.15` при отсутствии исторического ряда.**
`src/services/derivatives/DerivativesEngine.ts:92–98`. В `getFuturesList()` эндпоинт `/fapi/v1/openInterest` (метод `fetchOpenInterest` в адаптере есть!) не вызывается вовсе — OI берётся либо из `openInterestHist` (факт), либо из эвристики. Бейдж ставится только на Δ OI (`OiDeltaBadge`), сам столбец OI (`FuturesPage.tsx:313`) выводит эвристику без пометки EST.

**З5. Фейковые high/low ±5% подаются в детектор аномалий (Радар).**
`LiveMarketDataProvider.ts:155–165`: REST-снапшот `getAssets()` скармливает AnomalyEngine `high24h = price*1.05, low24h = price*0.95` → range всегда ровно 10% цены → детектор VOLATILITY EXPANSION (`AnomalyEngine.ts:84–96`) получает искажённый вход, смешиваясь с реальными WS-тиками (`BinanceWebSocketClient.ts:289` передаёт настоящие `h`/`l`). Возможны ложные срабатывания и «замыленный» z-score.

**З6. Синтетический стакан «СИНТЕТИЧЕСКАЯ ГЛУБИНА».**
`src/components/market/OrderBookL2.tsx:15–40`: при отсутствии WS-снапшота рисуются выдуманные уровни вокруг цены (7 бидов/7 асков). Помечено бейджем, но по философии проекта (`DONT_DO` «Оценочные суммы вместо „нет данных“») правильнее скелетон «ожидание потока».

**З7. Спред по умолчанию 0.01%.**
`LiveMarketDataProvider.ts:286`: если `extractBinanceSpread()` не сработал (например, актив пришёл с KuCoin), Binance-строке таблицы пар присваивается выдуманный спред 0.01% (и 0.02% у KuCoin-строки, строка 330).

## 6. Найденные ошибки и баги

**Б1 (главный). Страницы не обновляют данные — один fetch на всё время жизни страницы.**
`MarketPage.tsx:24`, `OverviewPage.tsx:79`, `FuturesPage.tsx:24`, `HeatmapsPage.tsx:13`, `ScreenerPage.tsx:25` — `useEffect([provider])` без интервала. Кэш провайдера (TTL 10 c) никогда не переиспользуется повторно. Live-цены через WS тикают только для стартового watchlist (BTC/ETH/SOL) и открытой монеты (`CoinDetailPage.tsx:79` вызывает `subscribeSymbol`). Итог: на `/market` таблица 30 активов замирает на моменте монтирования, при этом горит бейдж «LIVE-ТИКЕР». Для «терминала реального времени» это критичный UX-дефект.

**Б2. Обогащение (change1h/change7d/sparkline) выполняется один раз за сессию.**
`LiveMarketDataProvider.ts:181–206`: флаг `enrichmentDone` блокирует повторный запуск навсегда. `CandleHistoryService` имеет TTL 60 c, но после первого успеха больше не опрашивается. В долгой сессии спарклайны и 7-дневные изменения застывают на значениях первой загрузки. Дополнительно: enrichment мутирует объекты `assetCache` in-place (строки 193–199) — побочная мутация кэша.

**Б3. WS-подписка watchlist не обновляется при изменении watchlist.**
`MarketDataContext.tsx:150–190`: эффект зависит только от `[dataMode]`, `watchlist` замкнут на момент монтирования. Добавленный в watchlist символ не подписывается на тики (цена не тикает, пока не зайдёшь на страницу монеты). Для алертов аналогичная подписка сделана правильно (отдельный эффект по `[alerts]`, строки ~245–252) — паттерн есть, к watchlist не применён.

**Б4. Двойная подача тиков в AnomalyEngine.**
REST-путь (`getAssets`, строка 155) и WS-путь (`handleTickerPayload`) пишут в одну и ту же историю символа, при этом REST-тики несут фейковые ±5% (З5). Данные смешиваются, статистика z-score загрязняется.

**Б5. Мёртвый код: `src/services/alerts/AlertService.ts` (186 строк).**
Не импортируется нигде в приложении (используется `alertEvaluator` + `AlertDispatcher`). Подтверждает «долг №4» из `docs/SITE_REPORT.md`. Также содержит `Math.random()` в id — против собственного правила `DONT_DO` §Подходы-2.

**Б6. Сборка — один чанк 1.45 МБ.** Нет `React.lazy` по 17 маршрутам; `lightweight-charts` и `lucide-react` едут в общем бандле. Известное предупреждение Vite.

**Б7. CSP ослаблена `unsafe-inline` в `script-src`.**
`server/productionServer.js:75–76`. Vite-сборка не содержит инлайн-скриптов — директиву можно убрать (style-src оставить, Tailwind инлайнит стили иногда — проверить).

**Б8. Прод отстаёт на ~40 версий** (v0.8.4 на VPS против v0.8.44 в коде) — см. §2.

## 8. Предлагаемые решения

### 8.1 Устранение заглушек (P0 — «честность данных»)

**З1 — реальные пары бирж.** В `getAssetDetail()` параллельно с тикером Binance запросить фактическую статистику KuCoin (адаптер уже есть):

```ts
// LiveMarketDataProvider.getAssetDetail()
const [binanceTicker, kucoinStats] = await Promise.allSettled([
  asset.binanceSymbol ? this.binance.fetch24hrTicker(asset.binanceSymbol) : Promise.reject(),
  asset.kucoinSymbol ? this.kucoin.fetch24hrStats(asset.kucoinSymbol) : Promise.reject(),
]);
const pairs = [
  binanceTicker.status === 'fulfilled' && {
    exchange: 'Binance', pair: `${asset.symbol}/USDT`,
    price: parseFloat(binanceTicker.value.lastPrice),
    volume24h: parseFloat(binanceTicker.value.quoteVolume),
    spreadPct: spreadPctFrom(extractBinanceSpread(binanceTicker.value)),
  },
  kucoinStats.status === 'fulfilled' && {
    exchange: 'KuCoin', pair: `${asset.symbol}/USDT`,
    price: parseFloat(kucoinStats.value.last),
    volume24h: parseFloat(kucoinStats.value.volValue),
    spreadPct: null, // KuCoin /market/stats не отдаёт bid/ask — показать «—»
  },
].filter(Boolean);
// отказ источника → строка не показывается, а не «65%/35%»
```

**З2 — реальные 24ч high/low.** Добавить маппинг в `normalizeBinanceTicker` (поля `highPrice`/`lowPrice` уже приходят в FULL-ответе; в `BinanceTicker24hr`-схеме они есть) и прокинуть `high24h/low24h` в `AssetSummary`; в fallback `getAssetDetail` использовать их вместо `×1.03/×0.97`. Типы уже содержат эти поля у `TickerTick`.

**З3 — nullable-индикаторы.** Сделать поля индикаторов `| null`; при `<26` свечах — `null` и «—» в UI (паттерн уже реализован для OI-дельты и беты портфеля после P-фикса v0.8.44 — просто применить его же).

**З4 — честный OI.** В `getFuturesList()` для символов без hist-ряда вызывать `fetchOpenInterest(symbol)` (1 запрос, кэшировать тем же `oiHistCache`-паттерном); если и он недоступен — `openInterest: null` + «—». Эвристику `×0.15` удалить. Для оставшихся модельных случаев — бейдж `EST.` прямо в столбце OI.

**З5/Б4 — убрать REST-подачу в AnomalyEngine.** Радар и так питается WS-тиками с реальными `high/low` (`BinanceWebSocketClient.ts:289`). Удалить блок `processTick` из `getAssets()` (строки 153–168) — исчезнет и двойная подача (Б4), и фейковые ±5% (З5).

**З6 — скелетон вместо синтетического стакана.** В `OrderBookL2` при `isSynthetic` рендерить заглушки-строки «ожидание потока…» без чисел (числа убрать полностью, бейдж оставить).

**З7 — спред null.** `spreadPct: number | null`; «—» при отсутствии bid/ask.

### 8.2 Свежесть данных (P1)

**Б1 — polling + WS-подписка видимых символов:**

```ts
// hooks/usePolling.ts
export function usePolling(fn: () => void, ms: number) {
  useEffect(() => {
    fn();
    const id = setInterval(() => {
      if (document.visibilityState === 'visible') fn();
    }, ms);
    const onVis = () => document.visibilityState === 'visible' && fn();
    document.addEventListener('visibilitychange', onVis);
    return () => { clearInterval(id); document.removeEventListener('visibilitychange', onVis); };
  }, [ms]);
}
// /market: usePolling(refetch, 15_000); /futures: 20_000; /overview: 30_000; /heatmaps: 30_000
```

**Б2 — периодическое обогащение.** Заменить `enrichmentDone` на метку времени: повторять при истечении TTL `CandleHistoryService` (60 c); мутацию кэша заменить на создание новых объектов (`this.assetCache.data = results.map(a => ({...a, ...derived}))`).

## 10. Вывод

Проект зрелый: архитектура провайдеров, политика LIVE-first, изоляция демо-режима, стражи заземления LLM и 632 автотеста — выше среднего для такого срока. Однако аудит показал, что **«честность данных» доведена не до конца**: 7 фабрикаций в живом провайдере всё ещё показываются пользователям как реальные числа, а главный функциональный дефект — отсутствие авто-обновления страниц — противоречит позиционированию «терминала реального времени». Все найденные проблемы локализованы, имеют конкретные решения (§8) и устранимы за ~3–4 дня работы; после этого деплой v0.8.4x на VPS и слияние в `main` закроют разрыв между кодом и продакшеном.
