# Strategy Operations — серверный движок стратегий

Как устроено управление стратегиями и генерация сигналов. Документ описывает
состояние на момент введения подсистемы; при изменении поведения обновляйте его
вместе с кодом.

---

## 1. Что это решает

До появления подсистемы сигналы генерировались **в браузере**
(`LiveSignalEngine` в `MarketDataContext`). Это означало:

* закрыл вкладку — анализ остановился;
* состояние переключателя и сами сигналы жили в `localStorage`;
* два независимых генератора (браузер и любой будущий сервер) дали бы два
  источника истины.

Теперь сигналы производит **серверный движок**, который работает на VPS
независимо от браузера и пишет результаты в PostgreSQL. Фронтенд их только
читает.

---

## 2. Три продуктовые стратегии

Множество стратегий зафиксировано **в двух местах**, и оба должны совпадать:

| Где | Что |
|---|---|
| `server/services/strategyCatalog.js` | id, версия, имя, таймфреймы, подпись статуса |
| `server/db/migrations/006_strategy_settings.sql` | `CHECK (strategy_id IN (...))` + seed |

Актуальные значения (сверены с `definition.ts` соответствующих версий):

| id | Версия | Имя в реализации | Таймфреймы | Подпись статуса |
|---|---|---|---|---|
| `V3_0_HTF_LIQUIDATION_TRAP` | 3.0 | HTF Liquidation Trap | 1h / 4h | Research validated |
| `V3_3_HTF_ZONE_MITIGATION` | 3.3 | HTF Zone Mitigation & LTF Squeeze | 1h / 4h | Train only |
| `V2_8_ZERO_FEE_SNIPER_TRAILING` | 2.8 | Zero-fee Sniper + Trailing (gross-only) | 15m | Gross-only validated |

**Четвёртой стратегии нет.** `strategy_id` — первичный ключ, и поверх него
стоит `CHECK`, поэтому создать новую стратегию нельзя ни через API (404), ни
прямым `INSERT` (ошибка `23514`). Одного первичного ключа для этого
недостаточно: он мешает только дубликатам.

Ни одна стратегия не является «рабочей», «прибыльной» или «проверенной в live».
Подписи выше описывают **статус исследования**, а не доходность.

---

## 3. Математика в БД не хранится

`strategy_settings` содержит только:

```
strategy_id · enabled · scan_interval_seconds · symbols ·
last_scan_at · last_signal_at · last_error · updated_at · updated_by
```

Пороги RVOL, wick/body, периоды ATR, коэффициенты коридора и буфера стопа,
формулы целей — **в коде**, в `src/services/strategyArchive/definitions/**`.
Через админ-панель их изменить нельзя: для них нет ни колонок, ни обработчика.
Тело `PATCH` читает ровно одно поле — `enabled`.

## 4. Таблицы

### `strategy_settings` (миграция 006)

* `enabled BOOLEAN NOT NULL DEFAULT FALSE` — мастер-переключатель;
* `scan_interval_seconds INTEGER NOT NULL DEFAULT 60` с `CHECK (>= 15)` —
  пол защищает публичные эндпоинты от слишком частых запросов;
* `symbols JSONB NULL` — `NULL` означает «использовать список из кода»;
* `updated_by UUID → users(id) ON DELETE SET NULL`;
* seed: три строки, **все `enabled = FALSE`**.

После `npm run migrate` не начинает работать ничего. Стратегии включает
администратор вручную.

`ON CONFLICT DO NOTHING` в seed принципиален: повторный прогон миграции не
сбрасывает стратегию, которую админ уже включил.

### `signals` (миграция 007)

* цены — `NUMERIC`, не `REAL`: цена не approximation, и NUMERIC не даёт
  артефактов двоичной арифметики при сравнениях;
* `NULL` в уровне означает «уровень не определён», а не «ноль»;
* `status` — `CHECK (ACTIVE | INVALIDATED | TARGET_REACHED | EXPIRED)`;
* `direction` — `CHECK (LONG | SHORT)`;
* **`UNIQUE (strategy_id, symbol, timeframe, signal_candle_ts)`** — дедупликация
  на уровне БД;
* триггер `trg_signals_touch_updated_at` поддерживает `updated_at`.

Миграции 001–005 не изменялись; это защищено тестом.

## 5. API

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `GET` | `/api/strategies` | публично | состояние трёх стратегий |
| `GET` | `/api/signals` | публично | сигналы; фильтры `strategy`, `status`, `symbol`, `limit` |
| `GET` | `/api/signals/statistics` | публично | агрегаты по PostgreSQL: `period`, `strategy`, `symbol` |
| `GET` | `/api/signals/monitor` | публично | телеметрия монитора открытых сигналов (только чтение) |
| `PATCH` | `/api/admin/strategies/:strategyId` | `requireAdmin` | `{"enabled": true\|false}` |
| `GET` | `/api/admin/strategies/status` | `requireAdmin` | сводка для админ-панели |

Ошибки: неизвестная стратегия → `404`, небулево `enabled` → `400`,
недопустимый `status` в фильтре → `400`, неадмин → `401/403`.

Роль, прочитанная на фронтенде, **защитой не является**: проверку делает
`requireAdmin` на сервере. Фронт использует её только чтобы решить, активна ли
кнопка.

Каждое переключение пишет в `audit_log` строку `STRATEGY_ENABLED` или
`STRATEGY_DISABLED` с `metadata.strategyId`, в одной транзакции с изменением
`strategy_settings` — они не могут разойтись.

`GET /api/signals/statistics` и `GET /api/signals/monitor` — **только чтение**.
Пользовательского эндпоинта, меняющего состояние стратегий или сигналов, нет и
не должно быть: `PATCH /api/admin/strategies/:id` остается единственной точкой
включения, за `requireAdmin` и с записью в `audit_log`.

## 6. Движок

```
server/services/strategyEngine/
├── entry.ts                  точка сборки ядра (TS-экспорты из src/)
├── strategyCoreBundle.js     esbuild → .generated/strategyCore.mjs → import
├── marketDataFetcher.js      публичные свечи: кэш, TTL, дедуп in-flight
├── strategyEngine.js         один проход оценки + запись сигналов
└── strategyScheduler.js      расписание, замки, телеметрия
```

### Почему сервер исполняет тот же код, что и браузер

Сервер написан на чистом JS, стратегии — на TypeScript в `src/`. Вместо ручного
пересказа формул `strategyCoreBundle.js` собирает `entry.ts` вместе с его
TS-зависимостями через esbuild (уже присутствует как зависимость Vite) и
импортирует результат в Node. Артефакт лежит в `.generated/` и в Git не
попадает.

Это принципиально: **именно копия-пересказ породила баг V3.3** (см. §9).
Артефакт проверяется тестом `tests/integration/strategyEngineCore.test.ts`,
который подтверждает, что собранный модуль несёт защиту от look-ahead и
инвариант геометрии.

### Рыночные данные

Только публичный `https://api.binance.com/api/v3/klines`. Торговых ключей,
приватных эндпоинтов и исполнения ордеров в подсистеме нет.

* кэш по `(symbol, timeframe)` с TTL 60 с;
* дедупликация in-flight: параллельные запросы одного набора сводятся к одному
  HTTP-запросу;
* счётчик `stats.httpRequests` — для контроля веера запросов;
* сбой пробрасывается наверх. **Тихой подмены реальных данных статикой нет.**

### Закрытые свечи

Формирующаяся свеча никогда не считается закрытой. Это обеспечивает
`ohlcvToArchive(candle, timeframe, nowMs)`: `isClosed = closeTime < nowMs`.
Движок обязан передавать `nowMs`. Регрессионные тесты:
`tests/unit/liveSignalLookAhead.test.ts` и
`tests/integration/strategyEngineCore.test.ts`.

### Планировщик

* стартует вместе с бэкендом (`server/index.js`), но **только если БД
  доступна**;
* перед **каждым** циклом перечитывает `strategy_settings`, поэтому
  переключение в админке действует **без перезапуска**;
* `enabled = false` ⇒ стратегия не доходит до оценки: ноль вычислений и ноль
  запросов за свечами;
* соблюдает `scan_interval_seconds` каждой стратегии;
* замок in-flight на стратегию, освобождение строго в `finally` — долгий скан
  не запускает второй параллельный, а исключение не блокирует стратегию навсегда;
* ошибки логируются и пишутся в `last_error`, процесс не падает;
* `stop()` отменяет таймеры и дожидается текущих сканов; вызывается по
  `SIGTERM`/`SIGINT`.

Если после миграции все стратегии выключены (состояние по умолчанию),
планировщик не делает ни одного скана.

## 7. Сигналы: дедупликация и целостность

### Дедупликация

Двухуровневая:

1. `INSERT … ON CONFLICT (strategy_id, symbol, timeframe, signal_candle_ts)
   DO NOTHING`;
2. `UNIQUE`-констрейнт в БД — защита на случай гонки.

Ключ — **закрытая свеча**, а не время создания сигнала. Поэтому повторное
сканирование того же бара не создаёт второй сигнал. Для этого в сетап добавлено
поле `sourceCandleTs` (open time закрытой свечи-триггера), соответствующее
`signals.signal_candle_ts`.

### Цепочка SHA-256

Это **append-only журнал целостности**, а не «блокчейн». Он доказывает одно:
строки не редактировали задним числом.

Формат совпадает с клиентским `SignalsAuditLedger`, чтобы семантика не
разъехалась:

```
hash          = 'sha256-' + sha256hex(JSON({...payload, prevHash}))
previous_hash = 'GENESIS' для первой записи
```

Хэш считается **одной и той же функцией `hashPayload`** и при вставке, и при
проверке — иначе цепочка не сходится. Допись сериализована
`pg_advisory_xact_lock(730117)`: без этого два параллельных скана прочитали бы
один и тот же хвост и цепочка раздвоилась бы. Advisory lock транзакционный и
освобождается на `COMMIT`/`ROLLBACK` автоматически.

Проверка: `verifyChain()` возвращает число разрывов (используется
админ-статусом, не публичным API).

## 8. Фронтенд

### `/strategies`

* переключатель ВКЛ/ВЫКЛ на каждой карточке: активен для администратора,
  неактивен для пользователя и гостя;
* статус `Работает` / `Выключена` / `Ошибка`, последний скан, последний сигнал,
  число активных сигналов;
* если скана не было — прочерк, **не 0 и не эпоха**;
* число активных сигналов — результат реального `SELECT COUNT(*)`;
* оптимистичный UI с откатом: при ошибке API значение возвращается к серверному;
* если состояние не удалось получить, панель не рендерится вовсе — выдуманного
  «Работает» не появляется;
* состояние переживает F5 и рестарт VPS: источник истины — PostgreSQL,
  `localStorage` не используется.

### `/signals`

* данные из `GET /api/signals`; лента опрашивается с интервалом 60 с, статус
  сканирования — 15 с, статистика — 60 с (`useAutoRefresh`, пауза при скрытой
  вкладке, отмена устаревших запросов);
* селектор монеты — полный активный Spot-universe `/api/market/universe/spot`
  (лениво, кэш), НЕ админ-вселенная скана; поиск локальный, по загруженному
  реестру, без обращений к сети за каждую букву;
* статус сканирования берется с сервера (`/api/strategies`): 0 включенных —
  «Сканирование сигналов выключено», N включенных — фактический интервал из
  `scan_interval_seconds`, ERROR — отдельной строкой, запрос упал — «статус
  недоступен». Подписи «LIVE-скан» больше нет ни в одном состоянии;
* пустое/ошибочное состояние одно: `signals-empty[data-state]` с причиной
  `scanner-off` / `empty` / `error` / `market-error`;
* `null` в уровне отображается прочерком; R показывается только у состояний со
  сделкой, формат единый (`+1.67 R`);
* доля успешных считается только по реально закрытым сделкам; пока сделок нет —
  прочерк, а не 0 %;
* время выводится в поясе браузера/ОС (`src/utils/timePresentation.ts`), в БД и
  API — UTC/ISO; захардкоженных UTC+3 / Europe/Moscow нет;
* hash показывается только внутри блока «Технические сведения».

### Чего на фронте больше нет

* автостарта `LiveSignalEngine` — браузер не генерирует сигналы;
* подписи «Сканирование 6 символов · 60с» — она описывала браузерный движок, а
  число символов и интервал задаются в БД;
* плитки «SHA-256 OK» — верификация цепочки теперь серверная, и клиент не имеет
  права заявлять её результат, не выполнив её.

## 9. Баг V3.3 с прода: что было найдено

Наблюдение: `ETH/USDT/USDT · V3.3 · SHORT · Entry 2612.7–2617.3 ·
Stop «< 2613.45» · Targets 2573.93 / 2611.9 · R:R 1:2`.

Три независимые причины:

**A. Удвоение символа — presentation.** `publish()` писал `${symbol}/USDT`,
а `SignalsPage` добавлял суффикс повторно. Исправлено идемпотентным
`pairLabel()`.

**B. Знак у Stop Loss — presentation.** «<» был захардкожен для всех
направлений; для SHORT стоп выше входа. Исправлено `stopComparator(direction)`.

**C. Геометрия — расхождение адаптера с определением.** Живой `runV33` считал
уровни иначе, чем замороженное определение, и **не проверял инвариант порядка**,
который само определение проверяет при исполнении (`v33Runner.ts`):

```
LONG : stop < entry && tp1 > entry && tp2 > tp1
SHORT: stop > entry && tp1 < entry && tp2 < tp1
```

Из-за этого публиковался SHORT со стопом внутри зоны входа и с TP2 ближе TP1.
Инвариант вынесен в `setupGeometry.ts` и подключён к `publish()`:
противоречивый сетап не публикуется, а фиксируется в `lastRejected`.

**Математика стратегий не изменялась** — добавлен только контроль публикуемой
геометрии по правилу, уже существующему в замороженном определении.

Расхождение формул живого адаптера с определением (якорь стопа, вывод TP1/TP2)
задокументировано, но **не переписано**: это изменило бы генерируемые значения,
а любое такое изменение требует отдельного отчёта и регрессионных тестов.

## 10. Развёртывание

```bash
npm ci                 # ПОЛНАЯ установка: esbuild (транзитивно через vite) нужен
                       # серверу для сборки ядра стратегий из src/
npm run migrate        # применяет 001–009
npm run build          # фронтенд в dist/ — его раздаёт nginx, не Node
npm run server         # server/index.js: Express + PostgreSQL + движок стратегий
```

### 10.1. Чего запускать НЕЛЬЗНО (подтверждённая ошибка эксплуатации)

| Команда | Что на самом деле запускается | Последствие |
|---|---|---|
| `npm start` | `server/productionServer.js` — legacy static-сервер для `dist/` | Нет PostgreSQL, нет auth/сессий, нет `/api/signals`, `/api/strategies`, `/api/admin/*`, **нет движка стратегий**. Внешне «сайт работает», поэтому подмену легко не заметить |
| `npm run server` | `server/index.js` — настоящий бэкенд | Единственный корректный способ запустить бэкенд вручную |
| `systemctl restart cryptora` | юнит из `systemd/cryptora.service` | Шаблон в репозитории теперь указывает на `server/index.js`; до этого он запускал `productionServer.js` и расходился с фактической схемой VPS |

Требования к окружению бэкенда (`server/config.js` читает `process.env`, `.env`
не подхватывается автоматически — экспортируйте переменные или используйте
`EnvironmentFile=` в юните):

* `DATABASE_URL` — production PostgreSQL. Без него `/api/health` отвечает
  `degraded`, а планировщик стратегий **не стартует** (сканов и сигналов не будет);
* `SESSION_SECRET`, `SESSION_STORE=postgres` (`memory` отклоняется при
  `NODE_ENV=production`);
* `APP_ORIGIN` — канонический публичный origin (CSRF-проверки и ссылки в письмах);
* `HOST=127.0.0.1`, `PORT=3000` — nginx проксирует `/api` на этот адрес;
* право на запись в `server/services/strategyEngine/.generated` — туда esbuild
  кладёт бандл ядра (см. `ReadWritePaths` в шаблоне юнита).

После миграции все три стратегии выключены. Включение — только администратором
через `PATCH /api/admin/strategies/:id`. Первого администратора создаёт
`npm run create-admin`; `ADMIN_PASSWORD` в `.env` не используется.

Порядок остановки (`SIGTERM`/`SIGINT`) в `server/index.js` существенен:
планировщик стратегий → HTTP-сервер → пул PostgreSQL. Пул закрывается
последним, иначе запрос, долетевший во время остановки, открывает соединение к
закрывающейся БД и получает `FATAL 57P01` на простаивающем клиенте (раздел 10.3).

### 10.2. Проверка, что конвейер сигналов живой

Стратегии по умолчанию выключены, поэтому «пустой `/api/signals`» — нормальное
состояние, а не признак поломки. Проверка выполняется по включённой стратегии:

```bash
curl -s http://127.0.0.1:3000/api/strategies | jq '.strategies[] | {strategyId, enabled, status, execTimeframe, lastScanAt, lastError, activeSignalCount}'
curl -s 'http://127.0.0.1:3000/api/signals?limit=5' | jq '{count, total, ordering, statuses}'
journalctl -u cryptora -n 200 --no-pager | grep -iE 'strateg|schedul|pg-pool|error'
```

Ожидаемая картина работающего конвейера: `lastScanAt` продвигается с периодом
`scanIntervalSeconds`, `lastError` = `null`, `status` = `ON`; у появившегося
сигнала `targets` содержит всю лестницу целей (TP1..TPn), `status` = `ACTIVE`,
а после исполнения — `FILLED` и `fillPrice`.

Та же цепочка автоматизирована: `tests/integration/schedulerPersistence.test.ts`
поднимает настоящий PostgreSQL, настоящие миграции и настоящее Express-приложение,
включает стратегию через админ-API и выполняет `StrategyScheduler.tick()` с
настоящим скомпилированным ядром (подменяется только сетевой слой рыночных
данных — klines и exchangeInfo). Проверяются: `last_scan_at` продвигается,
`last_error` = null, статус `ON`, повторный цикл уважает `scan_interval_seconds`
и не создаёт дублей, отказ рынка попадает в `last_error`/статус `ERROR`, а запись,
построенная `buildSignalRecord()`, доходит до `GET /api/signals` со всеми целями.

Вручную остаётся одно: прогон с **живыми** данными Binance, на котором ядро
дейительно публикует сетап (синтетические свечи условиям замороженных стратегий
не удовлетворяют). Порядок: включить одну стратегию на стейджинге, дождаться
`lastScanAt`, проверить появившийся сигнал в БД и в API, затем выключить.

### 10.3. Проверка миграций и надёжности на реальном PostgreSQL

## 12. Остаток работы серверного конвейера сигналов

То, что уже работает: `StrategyScheduler` → `runStrategyScan()` → ядро
(`scanNow()`) → `signalRepository` → PostgreSQL (миграции 007 + 009) →
`GET /api/signals`. Схема и API совместимы с будущим Signals UI: лестница целей
хранится целиком, домен состояний совпадает с `SetupStatus` ядра, исполнение и
исход — отдельные группы колонок.

Что добавлено в ветке `arena/01a0d27d-cryptora` (миграция 010):

* **Серверный монитор открытых сигналов** (`server/services/signalMonitor/`):
  тик каждые 30 с независимо от браузера, бюджет `<= 500` сигналов и `<= 64`
  групп за цикл, lookback свечей `<= 1000` баров **на группу, размер считается
  по таймфрейму группы** (`timeframeMs()` → `ARCHIVE_TF_MS` ядра; таймфрейм
  берётся из `signals.timeframe`, а не предполагается равным 1h). Исполнение и
  исход считает ЗАМОРОЖЕННЫЙ `trackPublishedSetup()` через адаптер
  (`signalTradeManager`), паритет зафиксирован тестом. Отказ рыночных данных не
  роняет тик и не закрывает сигнал; состояние цикла переживает рестарт
  (`signal_monitor_state` + колонки `signals.monitor_*`), а монитор stateless по
  стратегии — исход восстанавливается из бара сетапа, поэтому рестарт не может
  его изменить (рестарт-паритет проверен на настоящем PostgreSQL для V3.0, V3.3
  и V2.8). Монитор стартует и при выключенных стратегиях: он сопровождает уже
  сохранённые открытые сигналы и не создаёт новых.
* **Серверная статистика** (`server/services/signalStatistics.js` →
  `GET /api/signals/statistics`): агрегаты по persisted lifecycle, включая
  раздельные счетчики «опубликовано / ожидают входа / дождались входа /
  завершились сделкой», gross/net R, суммы R и разрезы по стратегии и
  инструменту. Браузерный `SignalsAuditLedger` больше не является источником
  для этих чисел.

Чего здесь сознательно НЕТ (и что потребуется отдельной задачей):

1. **Мониторинг внутри бара (tick-realtime).** Автоматическое серверное
   сопровождение работает по факту закрытия свечи: пока бар исхода не
   закрылся, строка остается в `ACTIVE`/`FILLED` — «неизвестно» не
   превращается в «закрыто». Нет стриминга цены, нет частичных исполнений,
   нет учёта реальной ликвидности. В пользовательском тексте это называется
   **«автоматическое серверное сопровождение по закрытым свечам»**, а не «в
   реальном времени».
2. **Горизонт синхронизации исходов.** За один скан сопоставляется не более
   `MAX_LIFECYCLE_SYNC_PER_SCAN = 500` открытых строк; реплей возвращает сетапы
   текущего окна (1000 баров, размер по таймфрейму группы), поэтому исход
   сетапа старше окна уже не пересчитывается. Для полной истории нужен
   отдельный архивный проход. Окно заведомо больше максимального жизненного
   цикла любой из трёх стратегий (максимум ≈ 113 баров у V2.8 против 1000
   доступных): см. `docs/SIGNALS.md` §9.2.
3. **Синхронизация журнала браузера с БД.** `SignalsAuditLedger` (localStorage)
   и таблица `signals` — два независимых журнала одного и того же ядра:
   браузерный ограничен 500 записями и продвигается только пока вкладка видима,
   серверный живёт независимо от браузера. Страница `/signals` показывает
   серверную ленту как основной источник, а браузерный журнал — отдельным
   сворачиваемым блоком «Статистика и аудит»; они не смешиваются.
4. **`pnl_result_pct` из серверного пути.** Колонка есть (009), но live-реплей
   ядра её не заполняет: значение появляется в журнале браузера
   (`SetupOutcome.pnlResultPct`). Сервер не досчитывает его сам — это была бы
   вторая копия формулы.
5. **Включение стратегий в production.** После миграций все три стратегии
   выключены; включение — отдельное осознанное действие администратора.

### 13.2. Порядок включения на production (выполняет владелец)

```bash
cd /root/CRYPTORA
set -a; . ./.env; set +a
echo "$DATABASE_URL"                                  # убедиться, что это production
pg_dump "$DATABASE_URL" -Fc -f /root/cryptora-$(date +%F-%H%M).dump
npm run migrate:status                                # pending не должно остаться
npm run migrate                                       # применяет 010_signal_monitor_bookkeeping
npm run migrate:status                                # 001..010 applied
psql "$DATABASE_URL" -c "SELECT strategy_id, enabled FROM strategy_settings"   # 3 строки, все false
```

1. **Canary-вселенная (runbook-only).** Для пробного скана указать в
   `strategy_settings.symbols` ровно `["BTC", "SOL"]`. Это НЕ меняет боевую
   вселенную скана по умолчанию и не включает стратегию — только сужает набор
   инструментов для одной стратегии. Откат — вернуть прежнее значение
   (`symbols = NULL` = вселенная скана).
2. **Включить ОДНУ стратегию** (рекомендуется V3.0 — единственная валидированная):
   ```bash
   curl -s -X PATCH http://127.0.0.1:3000/api/admin/strategies/<id> \
     -H 'content-type: application/json' -b '<admin-cookie>' \
     -d '{"enabled": true}'
   ```
3. **Наблюдать 24 часа:**
   ```bash
   curl -s http://127.0.0.1:3000/api/strategies | head -c 600      # status ON, last_error null
   curl -s http://127.0.0.1:3000/api/signals/monitor | head -c 600 # running, stale=false
   curl -s "http://127.0.0.1:3000/api/signals/statistics?period=24h" | head -c 600
   journalctl -u cryptora -n 200 --no-pager | grep -iE 'monitor|strateg|error'
   psql "$DATABASE_URL" -c "SELECT status, count(*) FROM signals GROUP BY status"
   ```
4. **Критерии продолжения:** `last_error = null`, `stale = false`, монитор
   переводит сетапы в терминальные состояния (в `signals` появляются
   `FILLED` и исходы), в `/api/signals/statistics` «дождались входа» и
   «завершились сделкой» растут согласованно.
5. **Откат:** `PATCH … {"enabled": false}`. Уже сохраненные сигналы остаются в
   БД и продолжают отслеживаться монитором (он не зависит от `enabled`).
6. **Только после 24 часов на одной стратегии** — по одной добавлять V3.3
   (TRAIN-ONLY) и V2.8 (GROSS-ONLY, net отрицателен при комиссиях 2/5 bps).

### 13.3. Чего канарейный прогон НЕ делает

* не включает стратегии автоматически и не по расписанию;
* не меняет математику, пороги, комиссии и правила выхода;
* не расширяет боевую вселенную скана: сужение до BTC/SOL — параметр одной
  стратегии, откатываемый значением `symbols = NULL`.
