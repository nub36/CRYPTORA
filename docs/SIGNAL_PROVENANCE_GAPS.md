### Детали найденных проблем

**P-1 (исправлено).** `insertSignal` принимал `signal_candle_ts` из будущего.
Хэш-цепочка и дедупликация такую строку приняли бы: UNIQUE-ключ валиден,
CHECK на время нет. Сигнал по незакрытой/ненаступившей свече — классический
look-ahead: он выглядит обычным и отравляет статистику стратегии.
*Исправление:* жёсткий инвариант `FUTURE_CANDLE` на границе персистентности,
допуск 60 с на расхождение часов сервера и биржи.

**P-2 (исправлено).** `writeLifecycle` писал `closed_at` раньше `filled_at`
или раньше `signal_candle_ts`, если такие значения приходили от вызывающего.
Строка с перевёрнутым порядком событий невосстановима: её `bars_held` и `R`
не имеют смысла, а `outcome_hash` фиксирует бессмыслицу навсегда.
*Исправление:* `INVALID_LIFECYCLE_TIMESTAMPS` — транзакция откатывается,
исходная строка остаётся целой, факт отказа виден в логе и в аудите.

**P-3 (исправлено).** `strategy_version` был nullable без обязательности на
пути публикации: сигнал мог быть сохранён без указания версии кода,
посчитавшего его. Через несколько релизов такую строку нельзя соотнести с
математикой, которая её породила.
*Исправление:* `MISSING_PROVENANCE` на границе скана.

**P-4 (исправлено).** Просроченный бар. Сетап, найденный по свече, закрывшейся
десятки баров назад (рестарт бэкенда, долгая недоступность биржи, догоняющий
скан), публиковался как новый сигнал по текущему рынку.
*Исправление:* `STALE_CANDLE`, порог `MAX_SETUP_AGE_BARS = 12` бара.

**P-5 (НЕ исправлено, см. §4).** Источник (биржа) не хранится в строке.

## 3. Статистика (§6 задачи): аудит без изменений кода

Проверены инварианты `server/services/signalStatistics.js`:

- `wins + losses + breakEven + unrated = completed` — выполняется по
  построению: четыре взаимоисключающих `FILTER` по `result_r` (`> 0`, `< 0`,
  `= 0`, `IS NULL`) над одним и тем же набором терминальных статусов;
- `waitingEntry + filled + completed + cancelled + expired + unresolved =
  published` — статусы образуют разбиение домена `CHECK`;
- один сигнал не может быть учтён дважды: все счётчики — `COUNT(*) FILTER`
  над одной строкой таблицы, без `JOIN` и без `UNION`;
- `ratedCompleted ≤ completed`, `wins ≤ ratedCompleted` — следствие
  вложенности предикатов;
- фильтр тестового периода строгий по `test_run_id` (членство назначается на
  INSERT), а не по `created_at`: сигнал, созданный в Run 1 и закрытый во
  время Run 2, остаётся в Run 1. Исторические строки доступны через
  `testRunId='none'` и с периодами не смешиваются;
- в показатели входит только `provenance_status = 'VERIFIED'`; строки в
  карантине не удалены и видны в блоке `provenance`.

**Дефектов не найдено, код не менялся.** Инварианты закреплены тестами в
`tests/integration/healthEndpointPostgres.test.ts` — чтобы будущая правка не
сломала их молча.

## 4. Пробелы, сознательно НЕ закрытые миграцией в этом PR

### G-1 — нет колонки источника (биржа/провайдер)

**Что отсутствует.** `signals` не хранит, с какой биржи взяты свечи.
Сегодня это выводится косвенно: серверный движок ходит только на Binance
Spot (`marketDataFetcher.BINANCE_BASE`), поэтому источник у всех строк
один. Косвенный вывод перестанет работать в момент добавления второго
провайдера — и перестанет незаметно.

**Почему не делается сейчас.** Добавление `source_exchange` — это:
(1) миграция, (2) бэкофилл существующих строк значением, которое мы можем
только предположить (а предположение в колонке доказательства — хуже NULL),
(3) решение, входит ли поле в `hashPayloadV2` (если да — перерасчёт
хэш-цепочки, то есть потеря свойства append-only).

**Рекомендация.** Отдельный PR: `ALTER TABLE signals ADD COLUMN
source_exchange TEXT NULL` + заполнение ТОЛЬКО для новых строк + явное
решение «вне payload хэша» (как у `provenance_status` и `test_run_id`).
Приоритет — перед подключением второй биржи к движку, не раньше.

### G-2 — нет отдельной отметки времени расчёта

**Что отсутствует.** Три разных момента сейчас представлены двумя
колонками: закрытие бара (`signal_candle_ts`), момент вычисления сетапа и
момент записи в БД (`created_at`). Второй и третий различаются на время
скана и записи — обычно миллисекунды, но при долгом скане или ретрае запись
может отстать на секунды.

**Почему не делается сейчас.** Величина расхождения не влияет ни на один
расчёт: R, уровни и исход считаются от свечей, а не от времени записи. Поле
было бы полезно для профилирования задержки публикации — это наблюдаемость,
а не корректность, и не повод для миграции в hardening-PR.

**Обходной путь без миграции.** `metadata.publishedAt` уже содержит
`setup.createdAt` ядра — момент расчёта доступен, просто не в
типизированной колонке.

### G-3 — монотонность lifecycle не выражена в схеме

**Что отсутствует.** Монотонность обеспечена кодом (guard + CAS в `UPDATE`),
но не констрейнтом БД. Прямой `UPDATE` из psql может откатить статус назад.

**Почему не делается сейчас.** Корректное выражение требует либо триггера
`BEFORE UPDATE` с таблицей рангов, либо `CHECK` поверх дополнительной
колонки ранга. И то и другое — изменение поведения записи на production-БД,
то есть именно тот класс миграций, который запрещён в этом PR. Риск
закрывается на уровне доступа: прямой `UPDATE` в production выполняет только
оператор.

**Рекомендация.** Отдельный PR с триггером и прогоном на staging-копии.

## 5. Как проверить это на production (read-only)

```bash
npm run audit:production-health
```

Разделы `signal provenance completeness`, `lifecycle timestamps`,
`duplicate signals` и `signal statistics consistency` выводят ровно те
инварианты, которые описаны выше. Скрипт не выполняет ни одного изменяющего
запроса (`BEGIN READ ONLY … ROLLBACK`, белый список SQL-префиксов).
