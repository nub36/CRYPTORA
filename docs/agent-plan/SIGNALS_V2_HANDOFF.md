# SIGNALS V2 — Handoff-документ дизайна (без реализации UI)

> **Статус:** DESIGN ONLY. Ни один компонент UI в этой задаче не создан и не изменён.
> Документ описывает, что именно строить следующему агенту на готовом серверном фундаменте
> (PR #16, ветка `fix/signal-pipeline-foundation`, задача 9.2 в `docs/PRODUCTION_ROADMAP.md`).
>
> **Приоритет экрана:** mobile-first. Порядок блоков ниже — обязательный порядок сверху вниз
> на узком экране; на широком допускается двухколонничная раскладка с тем же порядком чтения.
>
> **Главное правило:** UI показывает ТОЛЬКО то, что посчитало замороженное ядро и сохранил сервер.
> Ни один уровень, статус, R или время не досчитывается и не «улучшается» на клиенте.

## 1. Что уже готово и является источником истины

| Слой | Где | Что даёт UI |
|---|---|---|
| API ленты | `GET /api/signals` (`server/routes/signals.js`) | `signals[]`, `count`, `total`, `limit`, `offset`, `maxLimit`, `ordering`, `appliedFilters`, `statuses`, `openStatuses`, `source: "server"` |
| Клиент | `src/services/strategyOps.ts` | `SignalDto`, `SignalsPageDto`, `SignalStatus`, `OPEN_SIGNAL_STATUSES`, `fetchSignalsPage(filters)` |
| Хранилище | PostgreSQL, миграции `007_signals` + `009_signal_levels_and_lifecycle` | идентичность, вся лестница целей, исполнение, исход, целостность |
| Репозиторий | `server/services/signalRepository.js` | домен статусов, `resolveLevels()` (tp1/tp2 = targets[1]/targets[2]), hash-цепочка v2, `verifyChain()` |
| Ядро | `src/services/signals/**`, `src/services/strategyArchive/**` (frozen) | уровни, статусы, R — сервер исполняет то же ядро через esbuild-бандл |
| Текст для человека | `src/utils/signalText.ts`, `src/utils/labels.ts` | `exitReasonLabelRu`, `describeSetupOutcome`, `formatSignedR`, `countTradeOutcomes`, `strategyShortLabel`, `sideLabel`, `pairLabel` |

Контракт запроса (всё серверное, всё ограниченное):

```
GET /api/signals?symbol=BTC/USDT&open=true&limit=50&offset=0
GET /api/signals?symbol=BTC/USDT&limit=20            # последние сигналы инструмента (маркеры)
GET /api/signals?strategy=V3_0_HTF_LIQUIDATION_TRAP&status=TARGET_REACHED&limit=50
```

* `symbol` принимает `BTC/USDT`, `BTCUSDT`, `BTC` → нормализуется к `BTC/USDT` (видно в `appliedFilters`);
* `open=true` → `ACTIVE` + `FILLED`; `open=false` → терминальные состояния;
* `limit` 1..200 (дефолт 50), `offset` 0..5000; выход за границы → `400` с кодом
  (`INVALID_LIMIT`, `INVALID_OFFSET`, `INVALID_STATUS`, `INVALID_STRATEGY`, `INVALID_DIRECTION`,
  `INVALID_OPEN`, `INVALID_SYMBOL`);
* порядок всегда `created_at DESC, id DESC` (новые сверху).

## 2. Чего делать НЕЛЬЗЯ (инварианты задачи)

1. **Не изобретать уровни на клиенте.** Entry/Stop/TP — только из `entryMin`, `entryMax`, `stopLoss`,
   `targets[]` (и после исполнения — `fillPrice`, `fillStop`, `fillTargets[]`). Никаких «примерных»
   целей, округлений «для красоты», средних по зоне, пересчёта RR в цену.
2. **Не тянуть свечи для всех монет.** Свечи — только для ВЫБРАННОГО символа и ВЫБРАННОГО таймфрейма.
   Запрещены N×candles, предзагрузка вселенной, «прогреть кэш по всем сигналам».
3. **Не менять формулу R** и не считать свою: `resultR` / `netResultR` приходят готовыми. R — вторичная,
   «advanced»-информация (см. §6).
4. **Не подменять источник:** серверный журнал (`/api/signals`) и браузерный (`SignalsAuditLedger`,
   localStorage) — два разных журнала. В Signals V2 источник — серверный. Смешивать их на одном экране
   без явной пометки нельзя (§8).
5. **Не показывать demo/оценочные данные как live** (RULES §1, §3): нет данных → «—» с пояснением,
   а не 0 и не заглушка.
6. **SHA-256 не должен доминировать на мобильном экране.** Хэши — компактный индикатор целостности и
   раскрытие в деталях (§7), не полотно текста в первом экране.
7. **Не включать стратегии и не менять их параметры из UI сигналов.** ВКЛ/ВЫКЛ — только админка
   (`/api/admin/strategies/:id`), параметры стратегий не редактируются нигде.
8. **Не возвращать регрессию PR #13** (зависание Chrome в `IndicatorEngine.calculateVolumeProfile`):
   любые новые индикаторные панели на графике сигналов — только через существующий `CandleChart`
   с его ограничителями; тест `tests/unit/volumeProfileTermination.test.ts` обязан оставаться зелёным.

## 3. Порядок блоков на мобильном экране

### Блок 1 — Селектор монеты + поиск (первым)

* Компонент: существующий `src/components/common/SymbolPickerModal.tsx`.
* **Вселенная — ПОЛНАЯ Active Supported Universe**, которую пикер грузит сам лениво
  (`GET /api/market/universe/spot`, `src/services/data/registry/exchangeUniverse.ts`).
  **НЕ Admin Scan Universe** (`/api/admin/scan-universe`, `scan_universe` из миграции 008): скан-вселенная
  — это список инструментов для серверного движка (24 символа), а пользователь выбирает из всех активных
  инструментов. Подменять одно другим нельзя: пользователь не нашёл бы свою монету.
* Поведение: поиск по тикеру и названию, текущий выбор подсвечен, выбор меняет ТОЛЬКО выбранный символ
  (свечи и лента перезапрашиваются для него).
* Дополнительный affordance: «монеты с сигналами» — список символов, полученных из уже загруженной ленты
  (`distinct` по `signals[].symbol`), а не отдельным запросом по всей вселенной.

### Блок 2 — Сводка последнего сигнала (кратко, человеческим языком)

Один экран-строка, без таблиц:

```
BTC/USDT · V3.0 · 1h · LONG
Вход 115 200,50 – 115 480,25   Стоп 114 310,75
Цель 1 116 900,50 · Цель 2 118 400,25 · Цель 3 121 050,00
Ожидает входа · бар 19 сен, 04:00 (локальное время)
```

* Источник — первый элемент `signals` при `limit=1` (или первый в ленте выбранного символа).
* Если сигналов нет — честное пустое состояние: «Сигналов по этому инструменту нет. Стратегии
  публикуют сетап редко (V2.8 — порядка одного в несколько месяцев на инструмент)» + ссылка на статус
  стратегий (`GET /api/strategies`: `enabled`, `status`, `lastScanAt`, `lastError`). Пустой журнал —
  норма, а не сбой (см. `docs/SIGNALS.md` §1.2).
* Направление и статус — словами (§5), не кодами.

### Блок 3 — Свечной график выбранного инструмента

* Свечи — только выбранный символ и выбранный таймфрейм (по умолчанию `1h` = `execTimeframe` из
  `GET /api/strategies`; переключатель ТФ разрешён и меняет только этот запрос).
* Маркеры — из СОХРАНЁННЫХ сигналов (`GET /api/signals?symbol=…&limit=50`): тип маркера по `status`
  (открыт / цель достигнута / стоп / без сделки), сторона по `direction`, время — `signalCandleTs`
  (openTime закрытого бара сетапа).
* Линии уровней рисуются ТОЛЬКО для выбранного сигнала (Блок 4 → выделение), а не для всех сигналов
  ленты: двадцать наборов линий на мобильном экране нечитаемы и провоцируют «угадай уровень».
* Прецедент реализации — `src/components/market/LiquidationPriceChart.tsx` (свечи + `setMarkers`
  событий поверх). Базовый `src/components/common/CandleChart.tsx` маркеров и произвольных
  горизонтальных линий НЕ имеет (props: `data`, `symbol`, `height`, `indicators`, `realtimeKline`,
  `showRSI`, `showMACD`, `timeframe`, `chartType`, `showMA`), поэтому нужен либо аддитивный props
  (`markers?`, `levelLines?`), либо отдельная обёртка `SignalChart` по образцу LiquidationPriceChart.
  Аддитивность обязательна: `/coin` и другие потребители `CandleChart` не должны измениться.
* Высота на мобильном — компактная (порядка 260–320 px), с возможностью раскрыть; `showMA` по умолчанию
  выключен, чтобы линии уровней не тонули в оверлеях.

### Блок 4 — Уровни Entry / Stop / TP (списком и на графике)

* Строки: `Вход (зона)`, `Стоп`, `Цель 1..N` — по массиву `targets`, **включая третью и последующие**
  (миграция 009 хранит всю лестницу; до этого TP3 терялся).
* Для `FILLED` и закрытых: отдельно «Факт входа» (`fillPrice`, `filledAt`) и, если ядро сдвинуло уровни
  (V2.8 входит по OPEN следующего бара), «Эффективный стоп» (`fillStop`) и «Эффективные цели»
  (`fillTargets`). Публикационные уровни при этом остаются видимы как «исходные» — оба набора честны,
  подменять один другим нельзя.
* Выбранный сигнал управляет видимыми линиями на графике (тап по карточке в ленте → линии этого сигнала).
* Дополнительно из DTO (не уровни, но контекст): `entryType` (`LIMIT_CORRIDOR` → «лимитный коридор»,
  `MARKET_NEXT_OPEN` → «вход по открытию следующего бара»), `validForBars` («действителен N баров»),
  `exitRule` (правило выхода словами — строка из ядра, не пересказ).

### Блок 5 — Детали сигнала

Раскрытие (`src/components/common/Collapsible.tsx`):

* идентичность: `strategyId` + `strategyVersion` + `engineSetupId`, `timeframe`, `signalCandleTs`,
  `createdAt`, `updatedAt`;
* исход: `status` (человеческим языком), `closeReason` → `exitReasonLabelRu()`, `closePrice`, `closedAt`,
  `barsHeld` («в позиции N баров»), текстовое описание — `describeSetupOutcome()`;
* аналитика сетапа: `metadata.riskRewardRatio`, `metadata.confirmingFactors`,
  `metadata.invalidationFactors`, `metadata.latencyBars`, `metadata.engineVersion`;
* результат (advanced, см. §6): `resultR`, `netResultR`, `pnlResultPct`;
* целостность (см. §7): `chainVersion`, `hash`, `previousHash`, `outcomeHash`.

### Блок 6 — История (лента) выбранного инструмента

* Источник — тот же `GET /api/signals?symbol=…`, постранично (`limit`/`offset`, `total` из ответа;
  компонент `src/components/common/Pagination.tsx`). Никакой «бесконечной истории одним запросом».
* Фильтры — только серверные: `open=true|false`, `status`, `strategy`, `direction`. Клиентская
  фильтрация загруженной страницы допустима как convenience, но счётчики обязаны браться из `total`.
* Строка ленты: время (локальное), пара, стратегия (коротко — `strategyShortLabel()`), сторона,
  статус словами, вход/стоп/первая цель, при наличии исхода — причина выхода.
* Порядок — как отдаёт сервер (новые сверху); не пересортировывать на клиенте.

### Блок 7 — Компактная статистика

* Только то, что можно честно посчитать из ЗАГРУЖЕННОЙ страницы/ленты, с явной подписью области:
  «по N сигналам на этом инструменте» (использовать `countTradeOutcomes()` из `signalText.ts`).
* Открытые / закрытые, доля сделок с R > 0, Σ net R — только по состояниям со сделкой
  (`TRADE_CLOSED_SIGNAL_STATUSES`); отмены и истечения идут отдельной строкой «без сделки».
* Если данных мало (N < 5) — показывать счётчики, но НЕ показывать доли/проценты: выборка слишком мала,
  а «красивый процент» на трёх сделках — это выдуманная статистика.
* Глобальная статистика по стратегии (не по инструменту) — отдельный запрос с `strategy=…` и своей
  подписью области; смешивать области в одном числе нельзя.

## 4. Бюджет запросов на экран (анти-N×candles)

| Действие | Запросы |
|---|---|
| Открыть экран | 1× лента (`/api/signals?limit=…`), 1× статус стратегий (`/api/strategies`), свечи НЕ грузятся до выбора символа |

`document.hidden`), с `AbortController` на размонтировании (регрессия `/coin` из v0.9.3 не должна вернуться).

## 6. R — вторичная, «advanced» информация

* Показывать R только там, где есть сделка: `resultR` (gross) и `netResultR` (net, модель комиссий
  2 bps maker вход / 5 bps taker выход). Формула и владение — `src/services/signals/live/lifecycle.ts`
  (подробнее: `docs/SIGNALS.md` §8.4). **Не пересчитывать на клиенте.**
* В мобильном первом экране R НЕ показывается. Место R — детали сигнала и компактная статистика
  (с подписью «gross» / «net» и областью выборки).
* Обязательные оговорки рядом с числами R:
  * V2.8 исследована при нулевых комиссиях → её net R отрицателен по построению (бейдж GROSS-ONLY уже
    есть в `STRATEGY_VERDICT`);
  * `INVALIDATED` ≈ −1 R — это нормальный исход, а не ошибка;
  * у `EXPIRED` / `CANCELLED` / `UNRESOLVED` R = `null` → текст «сделки не было», никогда не 0.
* Цветовая подсветка знака R допустима, но не должна быть единственным носителем смысла (доступность):
  рядом всегда знак и подпись.

## 7. Целостность (SHA-256) — компактно

* На мобильном экране — одна строка-индикатор: «Цепочка цела · v2» (или «Проверка недоступна»), плюс
  иконка. Полные хэши — в деталях, моноширинным шрифтом, с обрезкой и копированием по тапу.
* Проверка на сервере — `verifyChain()` из `signalRepository` (возвращает `{ rows, breaks }`);
  публичный эндпоинт для неё в этой задаче НЕ добавлялся. Если UI должен показывать результат проверки,
  нужен отдельный админ-эндпоинт (не публичный): решение владельца.
* Смысл для пользователя: публикация сигнала неизменяема (`hash`, `previousHash`), а исполнение/исход
  хэшируются отдельно (`outcomeHash`, `chainVersion = 2`). Строки до миграции 009 имеют
  `chainVersion = 1` и проверяются своей формой — UI обязан показывать версию, а не «ошибку цепочки».

## 8. Переход с браузерного журнала на серверный

Текущая страница `/signals` читает БРАУЗЕРНЫЙ `SignalsAuditLedger` + `LiveSignalEngine`
(`src/pages/SignalsPage.tsx`). Серверный конвейер независим и живёт даже при закрытом браузере.

План перехода (отдельная задача, не часть фундамента):

1. Signals V2 строится сразу на `fetchSignalsPage()` (`/api/signals`) — серверный источник основной.
2. Браузерный журнал остаётся для «Ретроспективы окна» и диагностики покрытия (он показывает окно
   реплея, которого нет в БД), но с явной пометкой источника и без смешивания чисел с серверными.
3. Расхождения ожидаемы и объяснимы (разный охват окна, момент публикации, `pnl_result_pct` только в
   браузерном пути). Показывать оба числа без подписи источника — нарушение RULES §1.
4. Обратная совместимость: `/api/signals` сохраняет поле `count` (длина страницы) рядом с `total`,
   поэтому существующие потребители не ломаются.

## 9. Остаток работы на бэкенде (блокирует не всё, но влияет на UI)

| Что | Влияние на UI | Где описано |
|---|---|---|
| Realtime-мониторинг позиции (сейчас исход определяется реплеем по закрытым свечам окна) | Статус может отставать на бар; UI обязан показывать «по данным последнего закрытого бара», а не «сейчас» | `docs/STRATEGY_OPERATIONS.md` §12 |
| Синхронизация исходов старше окна реплея (≤1000 баров 1h ≈ 41 день) | Старые сигналы могут остаться в `ACTIVE`/`FILLED`; в истории нужна честная пометка | там же |
| `pnl_result_pct` не заполняется серверным путём | В деталях показывать «—», не досчитывать | `docs/SIGNALS.md` §8.2 |
| Включение стратегий в production (после миграций все выключены) | Пустая лента — нормальное состояние; UI показывает статус стратегий | `docs/STRATEGY_OPERATIONS.md` §10.1 |
| Миграции 006–009 на production VPS (задача 7.1 roadmap) | Без них `/api/signals` отвечает ошибкой БД | `docs/PRODUCTION_ROADMAP.md` §7.1 |

## 10. Acceptance criteria для UI-задачи

1. Порядок блоков на мобильном экране совпадает с §3; на 360 px ширины нет горизонтального скролла
   и нет «полотна» хэшей.
2. Все уровни и статусы приходят из API; в коде нет арифметики над ценами (кроме форматирования).
3. Свечи запрашиваются только для выбранного символа/ТФ; число запросов соответствует §4
   (проверяется тестом на счётчике fetch, а не «на глаз»).
4. Пустые/ошибочные состояния честные: нет данных → «—» с пояснением; `400` от API → сообщение с кодом;
   недоступность БД → статус деградации, а не пустая лента «как будто сигналов нет».
5. Селектор монет использует Active Supported Universe (`/api/market/universe/spot`), а не
   Admin Scan Universe — проверяется тестом.
6. Существующие тесты зелёные: `tests/unit/strategyOpsUi.test.tsx`, `tests/unit/volumeProfileTermination.test.ts`,
   интеграционные наборы; Browser e2e в CI (локально Playwright в песочнице недоступен).
7. Математика стратегий не тронута: diff по `src/services/strategyArchive/**` и `src/services/signals/**`
   пуст (перенос `statusLabel()` в `signalText.ts` — единственное допустимое перемещение кода внутри
   `src/utils`/`src/pages`, формул оно не касается).
