## 1. Ответы на вопросы 1–12 по фактическому коду

**1. Когда создаётся Entry Zone.**
Внутри реплея, на баре сетапа, до создания pending:
`v33LiveReplay.ts:272-288` — `baseLow = c.close − 0.10·ATR`, `baseHigh = c.close + 0.10·ATR`
(`V33_CONSTANTS.CORRIDOR_ATR_FRAC = 0.10`, ATR(14) по 1H), затем `corridorHook(...)`.
Для V3.4 hook возвращает `[baseLow − 0.25·ATR, baseHigh + 0.25·ATR]`, т.е. `close ± 0.35·ATR`.
Зона строится **вокруг close закрытого бара-триггера**, не вокруг рыночной цены.

**2. Какая рыночная цена существует в момент публикации.**
Никакой. Движок видит только закрытые свечи: формирующийся бар отбрасывается
(`ohlcvAdapter.ts:27`, `isClosed = closeTime < nowMs`). Самая свежая цена, доступная
системе в момент публикации, — это `close` бара N, то есть **центр зоны**.
Фактическая рыночная цена в этот момент коду недоступна и нигде не запрашивается.

**3. Находится ли цена публикации внутри зоны.**
По построению — да, если под «ценой публикации» понимать ту цену, которую видит система
(`close` бара N = центр зоны). Фактическая рыночная цена измерена по минутным данным —
раздел 2: при лаге 60 с она внутри базовой зоны в 65.5 % случаев и внутри расширенной
в 98.9 %.

**4. Сигнал публикуется до / при / уже внутри зоны.**
Уже внутри — и центр зоны совпадает с последней известной ценой. Публикация происходит
после закрытия бара N (`rec.setupOpenTime === lastClosed.openTime`,
`LiveSignalEngine.scanSymbol`), то есть зона выставляется вокруг цены, которая только что
была. Это не «ожидание отката к уровню», это «коридор вокруг текущей цены».

**5. Начальный статус.**
`ACTIVE`. В журнале ядра — `SetupInput.status = 'ACTIVE'` (`LiveSignalEngine.publish`),
в БД — `record.status = 'ACTIVE'` (`buildSignalRecord`).

**6. Есть ли WAITING_FOR_ENTRY / PENDING_ENTRY.**
Нет. `SIGNAL_STATUSES` = `ACTIVE, FILLED, TARGET_REACHED, INVALIDATED, CLOSED, EXPIRED,
CANCELLED, UNRESOLVED` (`server/services/signalRepository.js:68`).
Роль «ждём входа» играет `ACTIVE`; `OPEN_SIGNAL_STATUSES = ['ACTIVE','FILLED']`.
Отдельного состояния ожидания входа не существует ни в БД, ни в ядре.

**7. Что монитор считает активацией входа.**
`corridorStep` (`v30Core.ts:212-231`), по одному ЗАКРЫТОМУ бару:

```
touches = LONG ? c.low <= zoneHigh : c.high >= zoneLow
hitStop = LONG ? c.low <= stop     : c.high >= stop
touches && hitStop → CANCELLED
touches           → FILLED (после проверки геометрии)
hitStop           → CANCELLED
waited >= 3       → EXPIRED
```

**8. Может ли монитор активировать сигнал на первой же проверке.**
На первой проверке — нет; на первой проверке **после закрытия бара N+1** — да, и почти
всегда. `trackPublishedSetup` возвращает `UNCHANGED`, пока бар сетапа является последним
в окне (`lifecycle.ts:78`). Как только бар N+1 закрывается, активация происходит, потому
что `open` бара N+1 равен `close` бара N, то есть центру зоны, и условие `touches`
выполняется автоматически. Практически: фил наступает через ~1 час после публикации,
и он предопределён уже в момент публикации.

**9. Источник цены у монитора.**
Только закрытые klines таймфрейма исполнения (1h): `low`, `high` для касания/стопа и
`open` для цены исполнения. Тикер, mark price, текущая цена, `close` как триггер — не
используются нигде. Окно — `MAX_LOOKBACK_BARS = 1000` баров ядра, `isClosed` — та же
граница look-ahead.

**10. Какая цена становится fill.**
`fill = LONG ? min(c.open, zoneHigh) : max(c.open, zoneLow)` — открытие бара, ограниченное
худшей гранью коридора. Поскольку `c.open = close_N` = центр зоны, ограничение почти
никогда не срабатывает: **fill = open бара N+1** (измерено: 99.76 % случаев, см. отчёт
по чувствительности).

**11. Использует ли LIVE расширенную зону V3.4.**
Да. Hook отрабатывает до создания pending, `record.entryZone` = расширенные границы,
`buildSignalRecord` кладёт их в `entry_min`/`entry_max`, монитор читает их же
(`toPublishedSetup`). Отдельной «базовой» зоны в живом контуре не существует —
публикуется и ведётся только расширенная.

**12. Есть ли ситуация, где база не коснулась бы, а расширение коснулось.**
В том виде, как система работает сейчас, — **нет ни одной**: `touches` проверяется по
целому закрытому бару N+1, чей `open` уже лежит в центре базовой зоны. Исторический
прогон: 0 таких случаев из 26 767 сетапов при любом значении расширения 0.00…0.30 ATR.
Сигнал рождается внутри обеих зон.
В гипотетической внутрибарной модели (ордер живёт с момента публикации) такие случаи
есть, но их мало — 30 из 4722 (0.64 %), раздел 3.

## 3. Гипотетическая внутрибарная модель (продуктовый код так НЕ работает)

Модель: лимитный ордер выставлен через 60 с после закрытия бара N, живёт
`CORRIDOR_EXPIRY_BARS = 3` часовых бара, касание проверяется по минутным барам
(стоп и касание на одной минуте → отмена, как в `corridorStep`).

| | базовая зона ±0.10 ATR | расширенная ±0.35 ATR |
|---|---|---|
| сетапов в модели | 4722 | 4722 |
| исполнено | 4688 — **99.28 %** | 4718 — **99.92 %** |
| отменено стопом | 2 | 2 |
| так и не коснулась | 32 | 2 |
| исполнено на первой же минуте | 4459 (95.1 % от исполненных) | 4712 (99.9 %) |
| **только за счёт расширения** | — | **30 (0.64 %)** |

Все 30 «expansion-only» случаев — это ситуации, где цена ушла из базовой зоны за первую
минуту и за три часа туда не вернулась; расширенная зона ловила их на первой же минуте
(29 из 30 — через 0 минут, один — через 1 минуту). Примеры:
`BTCUSDT 2022-04-08 13:00 LONG`, `BTCUSDT 2022-12-14 18:00 SHORT`,
`ETHUSDT 2024-10-28 14:00 SHORT`, `SOLUSDT 2025-08-13 13:00 SHORT`,
`XRPUSDT 2023-06-21 05:00 SHORT` (через 1 мин) — полный список в
`docs/v34-live-entry-audit.c3c1dce.json`.

Даже в этой, максимально благоприятной для расширения модели, прирост исполнений —
**+0.64 п.п. (99.28 % → 99.92 %)**, тогда как цена, уплаченная за него по историческому
аудиту, — падение числа публикуемых сетапов с 6300 до 4722 (−25 %), потому что тот же
отступ ужесточает фильтр качества.

## 4. ОТЧЁТ ПО ФОРМЕ ЗАПРОСА

```
LIVE SIGNAL CREATION:
  Сетап создаётся реплеем на ЗАКРЫТОМ 1H-баре N. Публикуется только если
  rec.setupOpenTime === последний закрытый бар и rec.publishable === true.
  LiveSignalEngine.publish → ledger → buildSignalRecord → insertSignal (PostgreSQL).
  Задержка: планировщик, тик 15 с, scan_interval_seconds по умолчанию 60.

INITIAL STATUS:
  ACTIVE (и в ledger ядра, и в колонке signals.status). Других начальных статусов нет.

WAITING FOR ENTRY EXISTS:
  НЕТ отдельного состояния. Роль «ждём входа» играет ACTIVE;
  OPEN_SIGNAL_STATUSES = ['ACTIVE','FILLED']. PENDING_ENTRY / WAITING_FOR_ENTRY
  в SIGNAL_STATUSES отсутствуют.

PRICE SOURCE:
  Только ЗАКРЫТЫЕ klines таймфрейма исполнения (1h) из MarketDataFetcher
  (Binance основной, KuCoin резерв). Незакрытый бар отбрасывается
  (isClosed = closeTime < nowMs). Тикер / current price / mark price
  НЕ используются нигде в сигнальном пути (проверено grep).

PRICE AT PUBLICATION:
  Для системы — close бара N, то есть точный центр Entry Zone.
  Фактическая рыночная цена коду недоступна. По минутным данным при лаге 60 с
  медианный дрейф от центра = 0.0722 ATR, p99 = ~0.25 ATR.

BASE ZONE AT PUBLICATION:
  close ± 0.10·ATR(14,1H). Цена внутри: 100 % по данным системы;
  65.50 % по факту рынка через 60 с, 49.85 % через 120 с, 33.74 % через 300 с.

EXPANDED ZONE AT PUBLICATION:
  close ± 0.35·ATR(14,1H) (базовые 0.10 + V34_ENTRY_ZONE_ATR_PAD 0.25).
  Цена внутри: 100 % по данным системы;
  98.94 % по факту рынка через 60 с, 96.23 % через 120 с, 87.57 % через 300 с.

ENTRY ACTIVATION CONDITION:
  corridorStep по закрытому бару: LONG touches = c.low <= zoneHigh,
  SHORT touches = c.high >= zoneLow. touches && hitStop → CANCELLED;
  touches → FILLED (после проверки геометрии risk>0, stop по нужную сторону,
  tp1 за входом, tp2 за tp1); hitStop → CANCELLED; waited >= 3 → EXPIRED.

FIRST MONITOR CHECK:
  Пока бар сетапа — последний в окне, результат UNCHANGED (входа нет).
  Первая проверка ПОСЛЕ закрытия бара N+1 активирует сигнал практически всегда:
  open бара N+1 = close бара N = центр зоны ⇒ touches выполняется автоматически.
  Измерено исторически: 11 342 из 11 342 исполнений (100 %) приходятся на бар N+1.

FILL PRICE SEMANTICS:
  LONG: min(open бара N+1, zoneHigh); SHORT: max(open бара N+1, zoneLow).
  Фактически = open бара N+1 в 99.76 % случаев; ограничение гранью срабатывает
  в 0.24 %. Никакой цены исполнения «по касанию внутри бара» не существует.

V3.3 LIVE ENTRY SEMANTICS:
  Рыночный вход по открытию следующего часа с верхним ограничением по худшей
  грани коридора шириной 0.2 ATR. Ожидания входа фактически нет,
  EXPIRED без фила — 0 из 26 767 за 4 года.

V3.4 LIVE ENTRY SEMANTICS:
  Идентична V3.3 по механике входа. Коридор шире (0.7 ATR против 0.2 ATR),
  но `touches` и цена исполнения от этого не меняются, потому что решение
  принимается по целому закрытому бару N+1. Единственное действующее отличие
  V3.4 — фильтр качества целей, считаемый ОТ РАСШИРЕННОЙ худшей грани,
  поэтому расширение работает как ужесточение допуска, а не как вход.

CAN EXPANSION CREATE ADDITIONAL LIVE FILLS:
  NO — в текущей архитектуре. Вход определяется закрытым баром N+1, чей open
  равен центру базовой зоны; базовая зона касается всегда. Исторически:
  0 дополнительных исполнений из 26 767 при любом расширении 0.00…0.30 ATR.
  CONDITIONAL — если бы вход исполнялся внутрибарным лимитным ордером,
  выставленным в момент публикации: +30 исполнений из 4722 (+0.64 п.п.,
  99.28 % → 99.92 %). Такой семантики в коде нет.

HISTORICAL/LIVE SEMANTICS DIFFERENCE:
  РАЗЛИЧИЙ НЕТ — и это главный вывод. Живой контур не имеет собственной
  реализации входа: сканер и монитор позиций вызывают ту же frozen-функцию
  corridorStep по закрытым 1H-свечам, что и исторический реплей
  (это зафиксировано намеренно, см. комментарии в signalTradeManager.js).
  Поэтому выводы исторического аудита переносятся на LIVE без оговорок.
  Расхождение существует не между историей и live, а между обеими и
  РЕАЛЬНОЙ торговлей человеком, который видит сигнал через минуту после
  публикации: там цена уже вне базовой зоны в 34.5 % случаев.

IS 0.25 ATR ACTUALLY SERVING AS WIDER ENTRY OPPORTUNITY:
  NO для системы. В том, что система считает и записывает как исполнение,
  расширение не участвует: исполнений оно не добавляет (0 из 26 767),
  цену входа меняет в 7 случаях из 3780 и всегда в худшую сторону.
  Фактически 0.25 ATR работает как ужесточение фильтра качества:
  publishable 6300 → 4722 (−25 %), R1 median 1.099 → 0.980.
  YES для человека, торгующего по сигналу вручную: отступ 0.25 ATR покрывает
  p99 дрейфа цены за первую минуту после публикации, то есть опубликованная
  зона остаётся актуальной в 98.9 % случаев против 65.5 % у базовой.
  Но это свойство ПУБЛИКУЕМОГО ДИАПАЗОНА, а не механизма исполнения,
  и в статистике стратегии оно никак не отражается.

RECOMMENDATION:
  (только на основании найденного кода; изменений не внесено)

  1. Считать вопрос закрытым фактически: расширение 0.25 ATR НЕ является
     механизмом увеличения fill probability в текущей архитектуре. Любое
     обоснование параметра через «больше шансов на вход» неверно и должно
     быть убрано из описаний стратегии.

  2. Если 0.25 ATR оставляют — оставлять его осознанно как
     (а) более честный публикуемый диапазон для ручной торговли и
     (б) более строгий фильтр качества. Обе роли измеримы, обе в отчётах есть.
     Решение о значении остаётся за человеком; автоматически ничего не меняется.

  3. Развилка, которую стоит поставить явно, но НЕ реализовывать сейчас:
     текущая семантика входа = «рынок по открытию следующего часа», а не
     «лимит в зоне». Если продукт обещает лимитный вход в диапазоне, расходятся
     обещание и исполнение, и чинить надо семантику входа, а не ширину зоны.
     Это отдельная задача с отдельным решением, вне объёма PR #39.

  4. Не смешивать это с V3.4-гейтом качества: гейт работает корректно и
     от семантики входа не зависит.

PRODUCTION MODIFIED: NO
DATABASE MODIFIED: NO
DEPLOYED: NO
```

## 6. Ограничения

- Минутное разрешение: лаги меньше 60 с неразличимы, поэтому строки 0/15/30 с
  показывают одну и ту же цену. Реальная задержка публикации может быть меньше минуты,
  и тогда доля «внутри базовой зоны» выше 65.5 %.
- Фактическая задержка публикации на проде не измерялась (нет доступа к БД и логам):
  она оценена по конфигурации планировщика (`TICK_MS = 15_000`,
  `scan_interval_seconds DEFAULT 60`).
- Внутрибарная модель раздела 3 — гипотеза для оценки порядка величины, а не
  предложение к реализации. Проскальзывание, глубина стакана и частичные исполнения
  в ней не моделируются.
