# ALERTS — Система оповещений и триггеров

> **Назначение:** Мониторинг рыночных условий и доставка уведомлений пользователям.  
> ⚠️ **ПРИНЦИП:** Алерты служат исключительно для информирования человека. Система алертов не инициирует автоматических сделок и не связана с исполнением ордеров.

---

## 1. Типы триггеров алертов

1. **Ценовые пороги (Price Level):** Достижение или пересечение заданной цены.
2. **Динамика цены (Price Change %):** Импульс $\pm X\%$ за окно в 15м / 1ч / 24ч.
3. **Всплеск объема (Volume Spike):** Превышение среднего объема в $N$ раз.
4. **Аномалии открытого интереса (OI Spike):** Изменение OI более чем на $Y\%$ за 1ч.
5. **Экстремум фандинга (Funding Rate Alert):** Ставка превышает или опускается ниже заданного порога.
6. **Крупные ликвидации (Whale Liquidation):** Ликвидация свыше $Z$ USD.
7. **Технические индикаторы:** Пересечение скользящих средних (Golden Cross), выход RSI из зоны перепроданности/перекупленности.

---

## 2. Каналы доставки

- **Web (In-app notification / Sound trigger):** Доступно в браузере.
- **Telegram Bot:** Персональные мгновенные уведомления.
- **Email:** Дайджесты и важные макро-события.
- **Webhooks:** Для интеграции в личные аналитические сервисы.

> **Реализовано:** пользовательские правила `ABOVE`, `BELOW`, `FUNDING_EXTREME`, `OI_SPIKE`; каналы In-app,
> браузерные уведомления, Telegram Bot и Webhook (`cryptora.alert.v1`). Настройки каналов сохраняются для аккаунта.
> Bot token шифруется AES-256-GCM отдельным deployment-ключом, не возвращается API и используется только backend.
> Telegram получает как срабатывания пользовательских правил (триггер пока оценивается открытым браузером), так и серверные
> события сигналов ПОЛНОГО жизненного цикла — `NEW_SIGNAL`, `FILL`, `TP1`..`TPn`, `BREAKEVEN`, `STOP_LOSS`, `CANCELLED`
> (до входа), `CLOSED`, — которые доставляются scheduler/monitor независимо от браузера. С 2026-10-05 события `TP1` и
> `BREAKEVEN` приходят ОПЕРАТИВНО — пока позиция ещё открыта: frozen-ядро экспортирует прогресс (`tp1Booked`/`beArmed`
> из инспекторов того же степпера, что считает исход), монитор отправляет их на каждом тике, повторы гасит персистентный
> дедуп `signal_lifecycle_events` (миграция 018), переживающий рестарты и гонки писателей. У V3.x TP1 бронируется по
> правилу R2, BE взводится на баре строго после TP1 (R3); у V2.8 TP1-события нет (трейлинг без лестницы), BE — реальный
> armed frozen-трейлинга при MFE ≥ 1R; терминальная классификация остаётся fallback и восстанавливает пропущенные
> события. Факты берутся только из frozen-ядра и строки `signals` (см. docs/SIGNALS.md §9.6).
> Email, объём, крупные ликвидации и индикаторные правила в этом UI не реализованы.
