# Сигналы · Промежуточные события TP1/BREAKEVEN открытой позиции — исследование и решение

> **Дата:** 2026-10-05 · **Ветка:** `arena/01a10ae1-cryptora` (PR #56, follow-up к «Telegram-события полного жизненного цикла»)
> **Вопрос владельца:** может ли Telegram уведомлять о TP1 и переводе SL в безубыток ОПЕРАТИВНО — в момент,
> когда серверная модель уже считает TP1 достигнутым / SL переведённым на entry, — а не постфактум при
> терминальном исходе (`TP1_THEN_BE` и др.)?
> **Жёсткие рамки:** не менять frozen strategy/lifecycle trading logic; не менять математику; не выводить
> событие из live ticker (lifecycle — по закрытым свечам); не создавать Telegram-факт раньше server source
> of truth; не нарушить детерминированный replay; сохранить persistent dedup; не деплоить.

---

## 1. Вывод (кратко)

**Реализация промежуточных TP1/BREAKEVEN НЕ выполнена** — по ветке «если безопасно определить нельзя,
не реализуй предположение». Причина: детерминированно и без дублирования торговых правил это определить
**невозможно**. Данные (уровни, fill, закрытые свечи) вне frozen-ядра есть; **правил интерпретации в
наблюдаемой форме нет** — состояние «TP1 забронирован / BE взведён» живёт только в локальных переменных
цикла `manageTrade`/`simulateTrailing` и наружу не возвращается, пока позиция открыта.

Вместо реализации:
- задокументирована точная API-граница (§3–4) и минимальное изменение API, которое позволило бы отдавать
  progress events без изменения торговой математики (§6, НЕ применено — frozen-файлы не тронуты);
- добавлены тесты-документы: граница наблюдаемости (касание TP1 при открытой позиции ⇒ событий нет,
  §7.1) и forward-compatibility текущего дизайна с будущими progress events (§7.2) — персистентный
  дедуп уже гасит повторы, терминальная классификация учитывает записанные события.

Семантика **TP1 ≠ BREAKEVEN** подтверждена и в текущей реализации раздельна: BE никогда не выводится из
TP1 — только из фактического выхода по безубытку (`TP1_THEN_BE` V3.x / `BE` V2.8, см. §5).

## 2. Что доступно ВНЕ frozen-ядра (и чего не хватает)

| Компонент | Есть | Чего нет |
|---|---|---|
| Строка `signals` (PostgreSQL) | `fill_price`, `filled_at`, `fill_stop`, `fill_targets`, опубликованные уровни, статус `FILLED` | Любого поля «TP1 достигнут», «SL переведён в BE» — прогресс не персистится (docs/SIGNALS.md §9.4) |
| Свечи (MarketDataFetcher) | Закрытые бары окна — тот же вход, которым пользуется lifecycle | Правил, по которым бар «подтверждает» TP1/BE с учётом R1–R5 (они внутри frozen-цикла) |
| `trackPublishedSetup` (единственный оракул ведения) | fill и терминальный исход | Прогресс открытой позиции (см. §3) |

Ключевое различие: **данные ≠ правила**. Касание свечой уровня TP1 — ещё не «TP1 забронирован»:
на том же баре первым мог сработать стоп (R1 «stop first, always»), и frozen-ядро вернуло бы `SL`.
Правильно интерпретировать последовательность баров может только сам frozen-цикл.

## 3. Какой именно frozen API/return type не даёт промежуточный факт

**`LifecycleResult`** (`src/services/signals/live/lifecycle.ts:30–37`) — union из четырёх видов:

```ts
export type LifecycleResult =
  | { kind: 'UNCHANGED' }
  | { kind: 'SKIP'; reason: string }
  | { kind: 'FILLED'; fill: SetupFill }        // ← позиция открыта: ТОЛЬКО уровни исполнения
  | { kind: 'RESOLVED'; fill: SetupFill | null; outcome: SetupOutcome };
```

`SetupFill` = `{ price, at, barOpenTime, stop, targets }` — прогресса нет. Точка, где прогресс
отбрасывается, — `lifecycle.ts:114` (`trackCorridor`) и `lifecycle.ts:152` (`trackNextOpen`):

```ts
const r = manage(dir, fill, stop, tp1, tp2, bars);
if (!r) return { kind: 'FILLED', fill };       // r === null ⇒ позиция открыта; hitTp1/beArmed УТЕРЯНЫ
```

**`manageTrade` V3.0/V3.3** (`v30Core.ts:119–188`, `v33Core.ts:241–295`) — возвращает
`V30TradeResult | null`: `null`, пока позиция открыта (граница датасета), а `hitTp1: boolean` /
`hitTp2: boolean` — поля **терминального** результата (`v30Core.ts:107–113`, `v33Core.ts:237`).
Через серверный бандл функция и вовсе не экспортируется (`server/services/strategyEngine/entry.ts`
реэкспортирует только `trackPublishedSetup`).

**V2.5 trailing** (`v25Trailing.ts:38–105`): `simulateTrailing` возвращает `V25Outcome | null`;
`reachedBreakeven: boolean` и `finalStop` — только в терминальном исходе; пока позиция открыта — `null`.

**V2.8-обёртка** (`v28Live.ts:346–354`): `v28TrailOutcome` → `{ reason, exitPrice, barsHeld, grossR, netR } | null`.

**Retrospective движка** (`ReplayRecord`, `replays/types.ts:49+`): `fill`/`outcome` — только терминальные
факты; `getRetrospective()` и `getStatus()` прогресса открытых позиций не содержат.

## 4. Где внутри ядра TP1/BE становится известен (точные места)

| Стратегия | TP1 забронирован | BE взведён (SL → entry) |
|---|---|---|
| **V3.0** | `v30Core.ts:156` условие касания, `:166`/`:177` `hitTp1 = true; tp1Bar = i` (R2: TP1 бронируется раньше TP2 на том же баре) | `v30Core.ts:152` `const beArmed = hitTp1 && tp1Bar >= 0 && i > tp1Bar;` (R3: строго ПОСЛЕ бара TP1), `:153` `stopNow = beArmed ? entry : stop` (R4) |
| **V3.3 / V3.4** | `v33Core.ts:270` условие, `:278`/`:287` `hitTp1 = true` | `v33Core.ts:267–268` — те же R3/R4 |
| **V2.8** | не существует: трейлинг не отслеживает лестницу целей (docs/SIGNALS.md §3.1) — TP1-событие для V2.8 в принципе не выводится | `v25Trailing.ts:76–78` `if (!armed && peakMfe >= BREAKEVEN_R) { armed = true; stop = entryPrice; }` — BE НЕ связан с TP1 (порог MFE ≥ 1R) |

Оба файла стратегий помечены `DO NOT EDIT — historical semantics` (v33Core.ts:5, v25Trailing.ts:6).

## 5. Семантика TP1 ≠ BREAKEVEN (проверено)

Текущая реализация (`signalLifecycleEvents.classifyLifecycleTransition`) выводит BE **только** из
фактического выхода по безубытку и никогда — из TP1:

- `TP1_THEN_BE` (V3.x) → события `[TP1, BREAKEVEN]`: BE реально применён (стоп стоял на entry, и по нему
  закрылись). Это доказывается исходом, а не выводится из TP1.
- `TP1_THEN_SL` → `[TP1, STOP_LOSS]`, **BE нет**: стоп и TP1 задеты одним баром (R1 stop-first),
  BE никогда не взводывался (`beArmed = false` в `v30Core.ts:162`).
- `BE` (V2.8) → `[BREAKEVEN]` без TP-событий: у трейлинга нет TP1.
- `TP2` → `[TP1, TP2]`, **BE не эмитируется**: хотя между TP1 и TP2 стоп, вероятно, стоял в BE,
  это недоказуемо из терминального результата — TP2 мог исполниться на баре TP1 (R2), тогда
  BE не успел взвестись. Предположение не делается.

Для промежуточных событий (будущая реализация, §6) разделение сохраняется: у V3.x TP1 и BE — независимые
факты с РАЗНЫМ моментом наступления (BE — бар строго после TP1, R3); у V2.8 BE вообще без TP1.

## 6. Минимальное изменение API для progress events (ПРЕДЛОЖЕНИЕ, не применено)

Цель: отдать наружу промежуточное состояние БЕЗ изменения торговой математики и БЕЗ второй копии правил.
Принцип: **одна реализация цикла** — инспектор пользуется тем же кодом, что и `manageTrade`/`simulateTrailing`.

1. **Замороженные модули (v30Core/v33Core):** чистая функция-инспектор рядом с `manageTrade` —
   `inspectTrade(dir, entry, stop0, tp1, tp2, bars) → { open, hitTp1, beArmed, tp1Bar, barsProcessed }`.
   Реализация — извлечение тела цикла в общий внутренний степпер, который вызывают ОБЕ функции:
   `manageTrade` байт-в-байт сохраняет поведение (доказывается существующими parity-тестами
   `tests/unit/signalMonitorParity.test.ts` и интеграционными — их показания не должны измениться).
2. **V2.5 trailing (v25Trailing):** аналогично `inspectTrailing(...) → { open, armed, stop, peakMfeR }`
   тем же общим степпером.
3. **`lifecycle.ts`:** аддитивное необязательное поле в существующем виде результата —
   `{ kind: 'FILLED'; fill: SetupFill; progress?: { tp1Booked: boolean; beArmed: boolean } }`
   (расширение union назад совместимо: текущие потребители поле игнорируют).
4. **`entry.ts` (серверный адаптер, не frozen):** реэкспорт инспекторов при необходимости.
5. **Монитор:** на каждом тике для `FILLED`-строк прогресс приходит ИЗ ТОГО ЖЕ вызова
   `trackPublishedSetup` по ТЕМ ЖЕ закрытым свечам: `tp1Booked` ⇒ запись+эмиссия `TP1` (ровно один
   раз — PK `signal_lifecycle_events`), `beArmed` ⇒ `BREAKEVEN` (ровно один раз). Терминальная
   классификация остаётся как сейчас; PK-дедуп гасит повторы — forward-compatibility уже доказана
   тестом (§7.2). BE по-прежнему не выводится из TP1 (§5).

Инварианты предложения: детерминированный replay сохраняется (инспектор — чистая функция тех же
входов, тот же результат на тех же свечах); событие не опережает server truth (прогресс вычислен
теми же правилами из тех же закрытых свечей — никакого live ticker); рестарт/параллельные тики/
монитор×скан — персистентный PK-дедуп; Frozen-математика не меняется (цикл один, меняется только
возврат промежуточного состояния наружу).

## 7. Что сделано в этом проходе (без изменения frozen-файлов)

### 7.1. Тесты-документы границы наблюдаемости

`tests/integration/signalLifecycleEventsPostgres.test.ts`:
- V3.0: касание TP1 закрытой свечой при ОТКРЫТОЙ позиции ⇒ событий `TP1`/`BREAKEVEN` НЕТ
  (только ранее отправленный `FILL`) — пока позиция не закрыта, факт TP1 наружу не наблюдаем;
- V2.8: MFE ≥ 1R при открытой позиции (BE внутри трейлера уже взведён) ⇒ события `BREAKEVEN` НЕТ —
  запрет выводить BE из свечной математики вне frozen-правил зафиксирован тестом.

### 7.2. Forward-compatibility: терминальная классификация учитывает записанные события

Там же: предзаписанный в журнал `TP1` (модель будущего progress-события) не отправляется повторно при
терминальном `TP1_THEN_BE` (уходит только `BREAKEVEN`) и при `TP2` (уходит только `TP2`). Это доказывает,
 что текущая архитектура дедупликации готова к подключению progress events из §6 без изменений
классификатора.
