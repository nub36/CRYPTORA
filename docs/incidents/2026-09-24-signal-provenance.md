# Инцидент 2026-09-24: три strategy_id получили один payload (provenance)

**Статус:** причина найдена и исправлена в коде; данные НЕ удалялись и НЕ переписывались.
Production-процедура классификации написана, проверяема и НЕ выполнена.

---

## 1. Что произошло

Три разные стратегии (`V3_0_HTF_LIQUIDATION_TRAP`, `V3_3_HTF_ZONE_MITIGATION`,
`V2_8_ZERO_FEE_SNIPER_TRAILING`) записали на одном символе и одном
`signal_candle_ts` полностью одинаковый payload: `direction`, `entry_min`,
`entry_max`, `stop_loss`, `targets`.

Пример от владельца — BTC/USDT, `signal_candle_ts = 2026-09-24 14:00 UTC`:

| Поле | Значение |
|---|---|
| direction | `LONG` |
| entry_min | `83612.89569417082` |
| entry_max | `83734.64430582919` |
| stop_loss | `83297.56854125623` |
| targets | `{85389.275, 87278.54}` |

Та же картина наблюдалась на SEI, RENDER, NEAR, INJ.

Три стратегии заморожены и имеют РАЗНУЮ логику входа и выхода. Совпадение
уровней до 14 знаков невозможно как результат независимого расчёта — это
признак того, что уровни посчитала ОДНА стратегия, а записаны они были под
тремя разными `strategy_id`.

---

## 2. Что показала арифметика уровней

Разбор production-строк (вычисления в `docs/SIGNALS.md` §12.4):

* середина коридора входа = `83673.77`, полуширина = `60.874305829185`
  = `0.10 × ATR` ⇒ `ATR(14) ≈ 608.743`;
* TP1 = `85389.275` — это середина между 4H-экстремумами
  (`(87278.54 + 83500.01) / 2 = 85389.275`); TP2 = `87278.54` — 4H-максимум;
* стоп `83297.56854125623` и уровень прокола `83388.88 = stop + 0.15 × ATR`
  одинаково объясняются и V3.0 (`sweepExtreme`) и V3.3 (`min(climax, zoneEdge)`);
* **V2.8 исключён однозначно**: его вход — точка (`entry_min == entry_max`),
  а в строке коридор шириной `121.7486`. V2.8 не мог породить эту строку.

**Важный отрицательный результат:** геометрия уровней НЕ различает V3.0 и V3.3 —
обе стратегии дают на этих данных один и тот же коридор и те же цели.
Авторство доказывается не арифметикой, а структурным provenance:
префиксом `engine_setup_id`, полями `strategy_version`, `exit_rule`,
`metadata.confirmingFactors`.

---

## 3. Root cause

Инфраструктурный, не математический:

1. `SignalsAuditLedger` — статический синглтон ядра
   (`src/services/signals/SignalsAuditLedger.ts`),
   `LiveSignalEngine` — тоже статический синглтон, который в конструкторе берёт
   `this.ledger = SignalsAuditLedger.getInstance()`
   (`src/services/signals/live/LiveSignalEngine.ts:250`).
2. `StrategyScheduler` запускает стратегии **конкурентно**: `tick()` не
   дожидается окончания скана.
3. Серверный скан читал `SignalsAuditLedger.getInstance()` **ПОСЛЕ** `await`
   предзагрузки свечей. К моменту возобновления статический синглтон уже
   принадлежал движку стратегии, запущенной последней.
4. `buildSignalRecord` ставил в строку `strategyId` ВЫЗЫВАЮЩЕГО, не сверяя его
   с тем, какая стратегия реально создала сетап.

Итог: три скана читали ОДИН чужой журнал, и один payload ушёл в БД под всеми
тремя `strategy_id`. Сетапы двух других стратегий при этом молча терялись.

Отдельно: `loadStrategyCore()` присваивал `cached` только после `await import()`,
поэтому два одновременных вызова на холодном старте могли получить РАЗНЫЕ объекты
модуля (URL бандла содержит `?v=${Date.now()}`), а значит — разные наборы
статических синглтонов. Вопрос «делят ли эти сканы состояние» переставал быть
свойством кода.

## 5. Что исправлено в коде

Четыре рубежа, каждый следующий страхует предыдущий:

1. **Свой движок на скан.** `runStrategyScan` делает
   `new core.LiveSignalEngine({...})` вместо `resetInstance() + getInstance()`.
   Глобальный синглтон серверным сканом не трогается вообще: чужой скан не
   может ни обнулить, ни остановить наш движок (`resetInstance()` в ядре делает
   `instance.stop()` для запущенного движка).
2. **Ссылка на журнал захвачена синхронно с созданием движка.** Точки внедрения
   журнала нет (`LiveSignalConfig` не содержит `ledger`), поэтому журнал
   получается через статический синглтон, но сброс и чтение идут в ОДНОМ
   синхронном блоке: между `resetInstance()` и `getInstance()` нет ни одного
   `await`. Дальше скан работает с захваченной ссылкой, а не с синглтоном.
3. **Мьютекс критической секции** (`server/services/strategyEngine/scanMutex.js`):
   внутри замороженного ядра в каждый момент ровно один скан. Стоимость —
   wall-clock, а не нагрузка на биржу: предзагрузка свечей вынесена из
   блокировки, а `MarketDataFetcher` дедуплицирует in-flight серии.
4. **Provenance-инвариант до записи.** `buildSignalRecord` отвергает сетап,
   чей `setup.strategyId` не совпадает с `strategyId` скана: строка не пишется
   вовсе, факт подмены идёт в `console.error` и в счётчик `provenanceMismatch`
   сводки скана. Новый сигнал получает `provenance_status = 'VERIFIED'` только
   при совпадении; если `setup.strategyId` нет — `'UNKNOWN'` (fail-closed).

Дополнительно: `loadStrategyCore()` сделан single-flight целиком — все сканы
гарантированно получают один объект модуля.

Математика стратегий (V3.0 / V3.3 / V2.8) **не изменена**: ни условия, ни вход,
ни стоп, ни цели, ни индикаторы, ни пороги, ни торговое сопровождение.

## 6. Карантин (миграция 011)

Аддитивно, без удаления и без переписывания данных:

```
signals.provenance_status TEXT NOT NULL DEFAULT 'UNKNOWN'
  CHECK (provenance_status IN ('VERIFIED','MISMATCH','UNKNOWN'))
```

Классификация по префиксу `engine_setup_id` (формат ядра
`${strategyId}-${SYMBOL}-${setupOpenTime}`):

| Префикс | Статус | Смысл |
|---|---|---|
| совпадает с `strategy_id` | `VERIFIED` | запись согласна с генератором |
| есть, но другой | `MISMATCH` | строка перемаркирована, доказательство прямое |
| отсутствует / не читается | `UNKNOWN` | доказательства нет; **никогда** не повышается до `VERIFIED` автоматически |

Правила использования:

* **Монитор** ведёт только открытые `VERIFIED`. Открытый `MISMATCH` — никогда:
  доводить чужой сетап до исхода значит записать чужой `result_r` в репутацию
  стратегии. `UNKNOWN` — fail-closed, не мониторится до явной проверки.
* **Статистика** считает только `VERIFIED` (win rate, R, сравнение стратегий).
  Числа карантина доступны отдельными audit-счётчиками
  (`provenance: { verified, mismatch, unknown, total }`), чтобы «показатели
  обнулились» не выглядело как пропажа данных.

`provenance_status` **не входит** в публикуемый payload (`hashPayloadV2`),
поэтому перенос строки в карантин не меняет `hash` и `outcome_hash`:
хэш-цепочка остаётся валидной до и после карантина (проверено тестом).
