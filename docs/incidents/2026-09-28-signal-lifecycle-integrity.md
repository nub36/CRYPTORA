# Инцидент 2026-09-27: исполненный сигнал PEPE «отменён» скан-синхронизацией (561186ba)

**Статус:** оба дефекта найдены и исправлены в коде (кэш финальности свечи + монотонность
lifecycle). Производственные данные НЕ изменялись: строка 561186ba, статистика, настройки —
нетронуты. Решение об исторической записи — отдельное решение владельца.

---

## 1. Что произошло (read-only аудит 2026-09-28)

V3.3 HTF Zone Mitigation опубликовал SHORT-сетап `PEPE/USDT`, бар сетапа
2026-09-27 15:00 UTC (сокращённый id `561186ba`). Хронология по production-API (только GET):

| Момент (UTC) | Событие |
|---|---|
| 16:00:20.408 | Публикующий скан получил из кэша ответ Binance, снятый ДО закрытия бара 15:00 |
| — | `isClosed` вычислен ПО МОМЕНТУ ЧТЕНИЯ (`closeTime < nowMs`) → незавершённый снапшот принят как закрытый бар |
| — | Опубликован коридор с центром 0.00000446 (= close формирующегося бара), а не 0.00000445 (осевший close) |
| 17:00:19.029 | Монитор по опубликованным уровням записал `FILLED` (fill_price 0.00000446) |
| 17:00:22.962 | Скан на осевших данных пересчитал ДРУГУЮ геометрию → `REJECTED_GEOMETRY` → `syncSignalLifecycle` закрыл строку как `CANCELLED` |

Итоговое состояние строки: статус `CANCELLED` («сделки не было») при сохранённых
`fill_price`/`filled_at` («сделка была»), `result_r = NULL`. Вошедная сделка исчезла из
статистики; истинный исход по опубликованным уровням — SL, gross −1, net ≈ −1.0346,
barsHeld 3, закрытие 19:00 UTC (воспроизведено реплеем замороженного ядра на
production-свечах в аудите 2026-09-28).

## 2. Root cause A — кэш «дозакрывает» формирующуюся свечу

`server/services/strategyEngine/marketDataFetcher.js`: TTL-кэш (60 c) хранил сырой ответ
целиком, включая формирующуюся свечу. `src/services/signals/live/ohlcvAdapter.ts`
вычисляет `isClosed = closeTime < nowMs` на стороне ПОТРЕБИТЕЛЯ. Сочетание:

```
T0 — ответ получен, бар X ещё формируется (close = цена в T0)
T1 — ответ закэширован (TTL 60 c)
T2 — часы пересекли X.closeTime
T3 — кэш отдан без обновления (TTL жив)
T4 — потребитель: isClosed = now > closeTime → true
T5 — снапшот T0 используется как ФИНАЛЬНЫЙ бар X
```

Ключевая улика: центр коридора публикации = close ± 0.10·ATR совпал с ценой формирующегося
бара (0.00000446), а не с осевшим close (0.00000445); один тик close меняет идентичность
сетапа (воспроизведение на замороженном ядре давало ДРУГОЙ SHORT-сетап с `publishable: false`).

## 3. Root cause B — lifecycle допускал регрессию исполненной строки

`server/services/signalRepository.js`, `syncSignalLifecycle` → `closeSignal` →
`writeLifecycle`: единственный guard — «строка уже терминальная» (`ALREADY_CLOSED`).
Переход `FILLED → CANCELLED/EXPIRED/UNRESOLVED` (безсделковая семантика при состоявшемся
входе) не блокировался ничем: ни на границе синхронизации, ни в персистентности.
Гонка не была даже нужна — достаточно, чтобы скан и монитор разошлись в данных
(что и устроил root cause A). Скан читает состояние ДО записи монитора, решение принимает
по устаревшему `ACTIVE`, а персистентность не перепроверяет семантику перехода.

## 4. Что исправлено

Математика стратегий (условия, индикаторы, Entry/Stop/Targets, R, net-R, комиссии,
таймауты, классификация) НЕ изменена. Оба фикса — инфраструктурные.

### Fix A — граница финальности в `MarketDataFetcher`

- `dropFormingCandles(candles, acquiredAtMs)`: свечи, незавершённые на момент ПОЛУЧЕНИЯ
  ответа (`closeTime >= acquiredAtMs`, либо closeTime не читается — fail-closed),
  отбрасываются ДО кэша и до выдачи потребителю. Нечитаемый `closeTime` не выдаётся
  за закрытую свечу.
- Кэш-запись хранит `nextBoundaryMs` (closeTime + 1 первой отброшенной свечи) и НЕ
  выдаётся, если эта граница уже пройдена — потребитель, ждущий последний закрытый бар,
  получает свежие данные, а не ожидание конца TTL.
- Инвариант: снапшот, полученный пока интервал был открыт, НИКОГДА не становится финальной
  закрытой свечой из-за времени, проведённого в кэше. Состав закрытых баров, которые видят
  стратегии, не меняется (они и раньше фильтровали `isClosed`) — меняется то, что
  незавершённый снапшот больше не может «дозреть».

### Fix B — монотонность входа в персистентности

- `writeLifecycle` (единая точка записи, транзакция + `SELECT … FOR UPDATE`): если строка
  исполнена (`FILLED` либо есть `fill_price`/`filled_at`), а пишется безсделковый статус
  (`EXPIRED`/`CANCELLED`/`UNRESOLVED`) — отказ (`ENTERED_SIGNAL_NO_TRADE`). Инвариант
  повторён в `WHERE` самого UPDATE (CAS): безсделковый статус пишется только в строку
  `ACTIVE` без входа.
- `syncSignalLifecycle`: ранний отказ с той же причиной + одна диагностическая строка в
  лог (событие целостности, не шум).
- Что НЕ заблокировано (проверено тестами): `FILLED → TARGET_REACHED | INVALIDATED | CLOSED`
  (легитимные исходы исполненной сделки), `ACTIVE → EXPIRED | CANCELLED | UNRESOLVED`
  (безсделковые терминалы неисполненной строки), идемпотентные перезаписи fill.
- Следствие для edge-case: `UNRESOLVED` (OUT_OF_DATA_WINDOW) для ИСПОЛНЕННОЙ строки теперь
  отклоняется — строка остаётся `FILLED` и продолжает вестись. «Исход не отслежен» не
  означает «сделки не было»: записать отказ входа в историю — та же ложь об истории,
  что и в инциденте.
