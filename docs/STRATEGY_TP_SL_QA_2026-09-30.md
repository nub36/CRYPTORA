### 1. Как рассчитывается Entry Zone?

**Одинаково у V3.0 и V3.3: коридор вокруг закрытия триггерного бара шириной ±10 % ATR.**

```
entryLow  = c.close − 0.10 · ATR
entryHigh = c.close + 0.10 · ATR
```

| | файл : строки |
|---|---|
| V3.0 | `src/services/strategyArchive/definitions/v3_0-htf-liquidation-trap/v30Core.ts:239,247` — `const half = V30_CONSTANTS.CORRIDOR_ATR_FRAC * atr;` … `zoneLow: c.close - half, zoneHigh: c.close + half` |
| V3.3 | `src/services/signals/live/replays/v33LiveReplay.ts:207,218` — `const half = CORRIDOR_ATR_FRAC * atr;` … `zoneLow: c.close - half, zoneHigh: c.close + half` |
| константа | `CORRIDOR_ATR_FRAC = 0.10` — `v30Core.ts:24`, `v33Core.ts:31` |

**Человеческим языком.** Стратегия не входит по рынку. Она ставит лимитный коридор шириной
в пятую часть ATR (0.2·ATR от края до края) по центру на цене закрытия сигнальной свечи и
ждёт, пока цена вернётся в него.

**Время жизни: 3 бара** (`CORRIDOR_EXPIRY_BARS = 3`, `v30Core.ts:25`, `v33Core.ts:32`),
отсчёт с N+1. Не дождались — `EXPIRED`, сделки не было.

**Исполнение — по ХУДШЕЙ границе, а не по середине:**

```
LONG :  fill = min(bar.open, entryHigh)
SHORT:  fill = max(bar.open, entryLow)
```

`v30Core.ts:220` (`corridorStep`) и `v33LiveReplay.ts:154`.

> **Важно.** `risk` и весь R стратегии считаются от `fill`, а не от середины зоны:
> `const risk = Math.abs(fill - p.stop)` (`v30Core.ts:221`, `v33LiveReplay.ts:155`).
> UI же показывает R от середины (`replays/shared.ts:79` `rrFrom`, вызов
> `v30LiveReplay.ts:121` `const mid = (pending.zoneLow + pending.zoneHigh) / 2`).
> **Отображаемый R всегда чуть лучше расчётного.**

### 2. Как рассчитывается Stop?

**Разный у версий. Общее — «за структурой плюс буфер 15 % ATR».**

**V3.0** — за экстремумом свипа (`v30Core.ts:241-243`, функция `buildPending`):

```
LONG :  stop = минимум сигнальной свечи (sweepExtreme) − 0.15 · ATR
SHORT:  stop = максимум сигнальной свечи (sweepExtreme) + 0.15 · ATR
```

`sweepExtreme` ставит `detectTrap` (`v30Core.ts:88,92`): это `c.high` для SHORT и `c.low`
для LONG — то есть тот самый хвост, которым свеча проколола 4H-уровень.

**V3.3** — за худшей из двух точек: климаксом свечи или дальней гранью зоны
(`v33LiveReplay.ts:208-212`):

```
zoneEdge = zone.zoneLow (LONG) | zone.zoneHigh (SHORT)
climax   = c.low       (LONG) | c.high        (SHORT)

LONG :  stop = min(climax, zoneEdge) − 0.15 · ATR
SHORT:  stop = max(climax, zoneEdge) + 0.15 · ATR
```

Это вариант `protective` (в архиве есть и `climax`, где грань зоны игнорируется —
`v33Runner.ts:189-191`; **live использует `protective`**, `v33LiveReplay.ts:44`
`V33_LIVE_VARIANT_ID = 'while-protective-displacement'`).

Константа `STOP_BUFFER_ATR = 0.15`: `v30Core.ts:26`, `v33Core.ts:33`.

**Человеческим языком.** Стоп ставится не на фиксированный процент и не на фиксированный R,
а сразу за ту точку, пробой которой означает «идея не сработала», плюс небольшой запас
в 15 % ATR, чтобы не выбивало шумом.

### 3. Как рассчитывается TP1?

**У обеих версий TP1 — СТРУКТУРНЫЙ уровень. Ни процента, ни кратности риска.**

**V3.0: равновесие 4H-диапазона** (`v30Core.ts:240`):

```
TP1 = (SH + SL4) / 2          // середина между 4H swing high и swing low
```

**V3.3: середина displacement-ноги** (`v33LiveReplay.ts:216`):

```
TP1 = (zone.legLow + zone.legHigh) / 2
```

Что такое «нога» (`v33Core.ts:121-126` для order block, `:138-142` для FVG):
это минимум и максимум 4H-свечей от свечи-основания зоны до свечи импульса включительно,
где импульсом считается свеча с телом ≥ 0.6·ATR (`detectDisplacement`,
`shared/primitives.ts:270-279`, порог `FROZEN_ENGINE.displacementMinBodyAtr`).

**Человеческим языком.** TP1 — это «половина пути обратно»: у V3.0 — центр
четырёхчасового диапазона, у V3.3 — центр того импульса, который создал зону.
Стратегия заранее не знает и не проверяет, далеко ли это от входа.

### 4. Как рассчитывается TP2?

**У обеих версий одинаково: противоположный ПОДТВЕРЖДЁННЫЙ 4H-свинг.**

**V3.0** (`v30Core.ts:244`): `tp2 = long ? levels.swingHigh : levels.swingLow`
Уровни даёт `confirmedLevels` (`v30Core.ts:55-72`) с двумя фильтрами каузальности:
берутся только 4H-бары, закрывшиеся к моменту закрытия 1h-бара, и пивот считается
существующим только начиная с `confirmedIndex` (правые бары уже напечатаны).

**V3.3** (`v33LiveReplay.ts:214`): `const opposing = long ? levels.high[closed4h] : levels.low[closed4h]`
Таблицу строит `confirmedSwingLevels` (`v33Core.ts:298`), индекс `closed4h` — число
закрытых 4H-баров на данный 1h-бар (`v33LiveReplay.ts:104-112`).
Если противоположного свинга ещё нет — **сетап не создаётся вовсе** (`v33LiveReplay.ts:215` `continue`).

**Человеческим языком.** TP2 — это ближайшая «настоящая» цель по структуре: вершина или
дно, подтверждённые на четырёхчасовом графике. Тоже без привязки к риску.

### 5. Почему у BTC SHORT TP1 почти рядом с Entry, а TP2 намного дальше?

Три причины, все структурные, ни одна не является багом:

**(1) TP1 и вход измеряются от РАЗНЫХ вещей.** Вход — от цены закрытия сигнальной свечи.
TP1 — от середины 4H-ноги. Когда триггер случается близко к этой середине, расстояние
между ними стремится к нулю. Формула вообще не содержит члена, который бы этому мешал.

**(2) Минимального TP1 в коде НЕТ.** Единственный фильтр — `corridorGeometryOk`
(`replays/shared.ts:95-103`) и его близнец `geomOk` на баре исполнения
(`v30Core.ts:222-224`, `v33LiveReplay.ts:156-158`):

```ts
(long ? tp1 > fill && tp2 > tp1 : tp1 < fill && tp2 < tp1)
```

Требуется только «строго впереди». `tp1` впереди на 0.01 % — проходит.
Поиск по `v30Core.ts`, `v33Core.ts`, обоим live-реплеям: **ни одного сравнения цели
с кратностью риска (`min_rr`, `R`, `risk *`) нет**.

**(3) TP1 и TP2 асимметричны по построению.** TP1 — середина (половина хода),
TP2 — противоположный край структуры (полный ход). У V3.0 это видно прямо в формуле:
вход возникает у одного края 4H-диапазона, `TP1 = (SH+SL4)/2` — центр, `TP2` —
противоположный край, поэтому **R2 ≈ 2·R1 по геометрии**. У V3.3 «нога» короче
диапазона, и разрыв ещё больше.

**Масштаб явления — не единичный случай (архив V3.3 TRAIN, n = 6 957 сделок,
`src/services/strategyArchive/results/v33/v33-train-metrics-while-protective-displacement.json`):**

| | p25 | median | p75 |
|---|---|---|---|
| R до TP1 | **0.2425** | **0.5824** | 1.1911 |
| R до TP2 | 1.8127 | **2.9164** | 4.5831 |

и `triggersWithTp1BehindClose = 7 762` из `15 957` = **48.6 % триггеров имеют TP1 уже
позади закрытия сигнальной свечи**; `rejected = 8 140` (51 %) отсеиваются проверкой
геометрии на баре исполнения. **Близкий TP1 у V3.3 — системное свойство дизайна.**

### 6. Что происходит после достижения TP1?

Функция `manageTrade` — `v33Core.ts:241-295` и `v30Core.ts:136-196` (семантика идентична,
различается только `TIMEOUT_BARS`: **50** у V3.0, **48** у V3.3).

На баре, где задет TP1 (`v33Core.ts:277-284`):

```ts
if (hitT1) {
  hitTp1 = true; tp1Bar = i;
  realised += 0.5 * rOf(tp1);                          // ← фиксируется 50 % позиции
  legs.push({ price: tp1, weight: 0.5, taker: true }); // ← нога с комиссией taker
  if (hitT2) return finish('TP2', tp2, 0.5, i);        // TP2 на том же баре — закрыть остаток
  ...
}
```

Со **следующего** бара включается безубыток (`v33Core.ts:267-268`):

```ts
const beArmed = hitTp1 && tp1Bar >= 0 && i > tp1Bar;   // строго ПОСЛЕ бара TP1
const stopNow = beArmed ? entry : stop0;               // стоп переезжает в цену входа
```

Итого по шагам:
1. **50 % позиции закрывается** по цене TP1;
2. **стоп для оставшихся 50 % переносится в безубыток** — не на баре TP1, а со следующего;
3. **TP2 продолжает мониториться** оставшимися 50 % (`v33Core.ts:285`);
4. таймаут 48/50 баров: остаток закрывается по `close` последнего бара → `TP1_THEN_TIMEOUT`.

Наблюдение за живым сигналом делает серверный монитор каждые 30 с
(`server/services/signalMonitor/signalMonitor.js:43` `MONITOR_TICK_MS = 30_000`),
вызывая **ту же** frozen-функцию через `lifecycle.trackPublishedSetup`
(`src/services/signals/live/lifecycle.ts:52`). Своей копии правил выхода на сервере нет —
это явно зафиксировано в `signalTradeManager.js:14-18`.

### 7. Может ли сигнал после TP1 получить SL?

**Нет. Исходный стоп после TP1 недостижим.**

Порядок проверок в цикле жёсткий (`v33Core.ts:265-276`): сначала считается `beArmed`,
затем `stopNow`, и только потом проверяется касание. На любом баре ПОСЛЕ бара TP1
`beArmed === true`, значит `stopNow === entry`. На самом баре TP1 `beArmed === false`,
но стоп там проверяется **до** TP1 (строка 273 раньше строки 277) — то есть если стоп
задет на этом баре, TP1 ещё не зафиксирован, и исход будет обычный `SL`.

Следствие: ветка `finish('TP1_THEN_SL', ...)` (`v33Core.ts:275`) **структурно
недостижима**. Подтверждение в данных: ни в одном архивном прогоне V3.0/V3.3 ключа
`TP1_THEN_SL` в распределении `exits` нет:

```
V3.3 TRAIN  : TP1_THEN_BE 3295 · SL 2298 · TP2 865 · TP1_THEN_TIMEOUT 379 · TIMEOUT 120
V3.0 TRAIN  : SL 772 · TP1_THEN_BE 410 · TP2 275 · TP1_THEN_TIMEOUT 80 · TIMEOUT 48
V3.0 VALID  : SL 274 · TP1_THEN_BE 157 · TP2 76 · TP1_THEN_TIMEOUT 21 · TIMEOUT 8
```

Худшее, что бывает после TP1, — `TP1_THEN_BE`: **+0.5·R(TP1) и ноль по второй половине**.

### 8. Как тогда считается результат сигнала?

**Формула результата** (`v33Core.ts:258`, `v30Core.ts:150`):

```
grossR = 0.5 · R(TP1) + 0.5 · R(цена выхода остатка)
где R(p) = (LONG: p − fill | SHORT: fill − p) / |fill − stop0|
netR   = grossR − комиссии (2 bps maker на вход, 5 bps taker на каждый выход)
```

Комиссия считается поногово, на собственный номинал ноги: `legFeeR`
(`v33Core.ts:222-225`, `v30Core.ts:104-107`).

**Статус сигнала** (`replays/shared.ts:34-38` `managedStatus`):

| выход | статус в БД |
|---|---|
| `TP2` | `TARGET_REACHED` |
| `SL` | `INVALIDATED` |
| `TP1_THEN_BE`, `TP1_THEN_TIMEOUT`, `TIMEOUT` | `CLOSED` |
| без входа | `EXPIRED` / `CANCELLED` / `UNRESOLVED` |

> **TP1 сам по себе НЕ делает сигнал «выигрышным».** После `TP1_THEN_BE` статус
> `CLOSED`, а не `TARGET_REACHED`.

**Классификация в статистике** (`server/services/signalStatistics.js:175-177`):

```sql
COUNT(*) FILTER (WHERE status = ANY($T) AND result_r > 0) AS wins,
COUNT(*) FILTER (WHERE status = ANY($T) AND result_r < 0) AS losses,
COUNT(*) FILTER (WHERE status = ANY($T) AND result_r = 0) AS break_even,
```

То есть **только по записанному `result_r`**, никогда по названию исхода
(`signalStatistics.js:20-23` — это оговорено отдельным инвариантом).
Знаменатель win rate — завершённые сделки с известным R, без `EXPIRED`/`CANCELLED`
(`signalStatistics.js:108-135`). R на клиенте не пересчитывается.

### 9. Есть ли partial close или TP1/TP2 — только информационные уровни?

**Partial close есть — в модели расчёта. Реальных ордеров нет ни одного.**

Два разных утверждения, и оба верны:

* **В математике** позиция делится **ровно пополам, 50 % / 50 %**, и это не настройка,
  а литерал в коде: `realised += 0.5 * rOf(tp1)` (`v33Core.ts:279`, `v30Core.ts:154`),
  `finish(exit, exitPrice, 0.5, i)` (`v33Core.ts:281,285,290,292`).
  Веса нигде не конфигурируются: в `strategy_settings` (миграция 006) вообще нет
  числовых параметров стратегии, только `enabled` / `scan_interval_seconds` / `symbols`
  (комментарий таблицы: *«Contains NO strategy math»*, `006_strategy_settings.sql:70`).
* **В исполнении** CRYPTORA сделок не совершает: торговых ключей, ордеров и приватных
  эндпоинтов в проекте нет (`server/services/strategyEngine/strategyEngine.js:9-10`).
  Для пользователя TP1/TP2 — уровни на графике; для движка — точки, в которых
  считается результат.

Так что «информационные» — только в смысле «мы не исполняем». В расчёте R и win rate
TP1 — полноценное частичное закрытие половины позиции.

### 10. Чем TP/SL V3.0 отличается от V3.3?

| | **V3.0 HTF Liquidation Trap** | **V3.3 HTF Zone Mitigation** |
|---|---|---|
| триггер | прокол подтверждённого 4H-свинга с закрытием обратно; тело ≥ 0.35, RVOL **> 1.25** (`v30Core.ts:84-97`) | касание/митигация 4H-зоны (OB или FVG) + абсорбция; RVOL **≥ 1.25** (`v33LiveReplay.ts:189-199`) |
| Entry Zone | `close ± 0.10·ATR` | `close ± 0.10·ATR` — **идентично** |
| **Stop** | экстремум свипа ∓ 0.15·ATR (`v30Core.ts:241-243`) | `min/max(климакс, грань зоны)` ∓ 0.15·ATR (`v33LiveReplay.ts:210-212`) — **может быть дальше**, если зона шире свечи |
| **TP1** | равновесие 4H-диапазона `(SH+SL4)/2` (`v30Core.ts:240`) | середина displacement-ноги `(legLow+legHigh)/2` (`v33LiveReplay.ts:216`) — **систематически ближе** |
| **TP2** | противоположный 4H-свинг | противоположный 4H-свинг — **идентично** |
| после TP1 | 50 % + BE со следующего бара | **идентично** |
| таймаут | **50** баров (`v30Core.ts:29`) | **48** баров (`v33Core.ts:34`) |
| типичная стоп-дистанция | median **1.25 %** (TRAIN) / **1.28 %** (VALIDATION) | median **1.70 %** (TRAIN) |
| TP1 hit rate | 48.26 % TRAIN / 47.39 % VALID | **65.24 %** TRAIN |
| TP2 hit rate | 17.35 % TRAIN / 14.18 % VALID | **12.43 %** TRAIN |
| уровень доказанности | **RESEARCH** — прошла отложенную VALIDATION (gross 0.1274 R, net 0.0600 R) | **TRAIN_ONLY** — валидации НЕ было; без топ-1 % сделок gross 0.0264 R < комиссий 0.0511 R |

**Одной фразой:** геометрия входа и семантика TP2/после-TP1 у версий совпадают;
отличаются якорь стопа, якорь TP1 и уровень доказанности. TP1 у V3.3 ближе — поэтому он
чаще достигается (65 % против 48 %), но приносит меньше (медиана 0.58 R против неизвестной
у V3.0), и вторая половина позиции в 47 % случаев уходит в безубыток.
