## 1. Что именно работает в LIVE (v0.8.48)

Три стратегии исследовательского архива запускаются на **фактических закрытых свечах** биржи (Binance / KuCoin через
`LiveMarketDataProvider`) без изменения правил. LIVE-движок — это **детерминированный реплей архивного раннера** на
окне последних закрытых баров, а не отдельная «упрощённая» реализация.

| Стратегия | Что вызывается (frozen, без изменений) | Вход | Вердикт исследования |
|---|---|---|---|
| **V3.0 HTF Liquidation Trap** | `detectTrap` → `buildPending` → `corridorStep` → `manageTrade` (v30Core) | лимитный коридор close ± 0.10 ATR, 3 бара, худшая граница | VALIDATED (3 из 6 символов) |
| **V3.3 HTF Zone Mitigation** | `buildZones` → `trackZone` → `absorption` → коридор → `manageTrade` (v33Core), вариант `while-protective-displacement` | лимитный коридор, 3 бара | TRAIN-ONLY, не валидировано |
| **V2.8 Zero-fee Sniper + Trailing** | `evaluateV2` @4839074 + `extremePoolKind`/`baseSniper` + `resolveEntry`/`executableLadder` + `trackOutcome` (слот) + `simulateTrailing` — через архивную обёртку `v28Live.ts` | OPEN бара N+1 | GROSS-ONLY (fees = 0), при 2/5 bps net-отрицательна |

Файлы: `src/services/signals/live/LiveSignalEngine.ts`, `live/replays/{v30,v33,v28}LiveReplay.ts`, `live/lifecycle.ts`,
`src/services/strategyArchive/definitions/v2_8-zero-fee-sniper-trailing/v28Live.ts`.

### 1.1. Цикл скана
1. Каждые 60 с (первый — через 5 с после старта LIVE-режима) для BTC, ETH, BNB, SOL, XRP, DOGE запрашиваются
   1000 свечей 1h и 4h (+ 400 свечей 1d для V2.8). **Forming-свеча отбрасывается** (`ohlcvToArchive(c, tf, nowMs)`).
2. Сначала ведутся уже опубликованные сетапы (см. §3) — это дёшево и не зависит от появления нового бара.
3. Если закрылся новый 1h-бар — запускаются реплеи трёх стратегий по всему окну; **в журнал публикуются только сетапы
   последнего закрытого бара** (latency 0 баров). Идентификатор `${strategyId}-${SYMBOL}-${setupOpenTime}`
   детерминирован — повторные сканы не создают дублей.
4. Pending, которые раннер отклонил бы на баре исполнения по геометрии (TP1 позади коридора — в исследовании V3.3 таких
   ≈ 51 %), не публикуются, но видны в «Ретроспективе окна» — счётчики сходятся с воронкой исследования.
5. Ошибки провайдера записываются **по инструменту** в `getStatus()` и показываются на странице; сбой одного символа не
   останавливает остальные. Демо-данные в LIVE-путь не подставляются никогда.

### 1.2. Почему сигналов мало
V3.0 в исследовании давала порядка одного сетапа на инструмент в несколько дней; V3.3 после геометрического фильтра —
реже; V2.8 (sniper) — ещё реже на 1h. Пустой журнал сразу после запуска — норма, а не сбой. Диагностика того, что стратегии
действительно считаются на данных, — блок «Покрытие по инструментам» и «Ретроспектива окна» на `/signals`.

## 2. Модель данных журнала (`SignalsAuditLedger`, ключ `cryptora_signals_ledger_v2`)

```typescript
interface AnalyticalSetup {
  id: string;                 // `${strategyId}-${SYMBOL}-${setupOpenTime}`
  strategyId: string;         // V3_0_HTF_LIQUIDATION_TRAP | V3_3_HTF_ZONE_MITIGATION | V2_8_ZERO_FEE_SNIPER_TRAILING
  strategyVersion: string;
  symbol: string;             // BTC/USDT
  direction: 'LONG' | 'SHORT';
  timeframe: '1h';
  setupOpenTime: number;      // openTime закрытого бара сетапа (ms UTC)
  entryType: 'LIMIT_CORRIDOR' | 'MARKET_NEXT_OPEN';
  entryZone: [number, number];
  invalidationLevel: number;  // стоп
  targets: number[];          // TP1, TP2 (V2.8 — лестница frozen-движка, ориентир)
  riskRewardRatio: number;
  confirmingFactors: string[];
  invalidationFactors: string[];
  exitRule: string;
  validForBars: number | null;
  createdAt: string;          // ISO UTC публикации
  latencyBars: number;        // 0
  status: 'ACTIVE' | 'FILLED' | 'TARGET_REACHED' | 'INVALIDATED' | 'CLOSED' | 'EXPIRED' | 'CANCELLED' | 'UNRESOLVED';
  fill?: { price; at; barOpenTime; stop?; targets? };   // исполнение (уровни после сдвига на дельту исполнения)
  closedAt?; exitReason?; exitPrice?; resultR?; netResultR?; pnlResultPct?; barsHeld?;
  prevHash: string;           // 'GENESIS' или auditHash предыдущей записи
  auditHash: string;          // sha256(issuance + prevHash) — фиксируется при публикации
  outcomeHash?: string;       // sha256(outcome) — фиксируется один раз при исходе
}
```

## 3. Жизненный цикл опубликованного сетапа (`live/lifecycle.ts`)

Исход считается по **опубликованным (уже захэшированным) уровням**, а не повторным прогоном стратегии, теми же
frozen-функциями архива:

- **V3.0 / V3.3 (LIMIT_CORRIDOR):** `corridorStep` на барах N+1…N+3 (исполнение по худшей границе, отмена при касании
  стопа, `REJECTED_GEOMETRY`, истечение) → `manageTrade` соответствующей версии (TP1 → 50 % и BE со
  следующего бара, TP2, таймаут 50 / 48 баров).
- **V2.8 (MARKET_NEXT_OPEN):** `v28EntryAtNextOpen` (OPEN N+1, сдвиг стопа/целей на дельту исполнения, `executableLadder`,
  rr1 ≥ min_rr) → `v28TrailOutcome` (Trail V2.5: BE при MFE ≥ 1R, трейлинг 1R шагом 0.25R, таймаут 10 баров).

Статусы: `ACTIVE → FILLED → TARGET_REACHED | INVALIDATED | CLOSED` (сделка была) или `ACTIVE → EXPIRED | CANCELLED`
(сделки не было). `UNRESOLVED` — бар сетапа вышел за окно данных до исхода (честно помечается, не считается сделкой).

### 3.1. Один бар, где коснулись и стопа, и цели — правило РАЗНОЕ у разных стратегий

Никакого общего «всегда стоп»: у каждой стратегии своя реализация, и у одной из них пары TP/SL не существует вовсе.
Источник — frozen-код, а не удобство формулировки.

| Стратегия | Frozen-источник | Функция (строки) | Точное правило на спорном баре | Является ли stop-first правилом ЭТОЙ стратегии |
|---|---|---|---|---|
| **V3.0** | `definitions/v3_0-htf-liquidation-trap/v30Core.ts` | `manageTrade` (124–188) | Внутри цикла по барам `hitStop` вычисляется на строке 158 **до** `hitT1`/`hitT2`, и на строке 160 стоит комментарий `// R1: stop first, always.` → `if (hitStop)` возвращает `SL` (TP1 ещё не было) либо `TP1_THEN_BE`/`TP1_THEN_SL` (TP1 был). BE взводится только со **следующего** бара: `beArmed = hitTp1 && tp1Bar >= 0 && i > tp1Bar` (строка 154) | **ДА.** Явное, задокументированное в самом коде правило R1 именно V3.0 |
| **V3.3** | `definitions/v3_3-htf-zone-mitigation/v33Core.ts` | `manageTrade` (241–295) | Та же структура: `hitStop` на строке 269, `if (hitStop)` на строке 270 — **до** `hitT1` (строка 274). Комментария `R1` здесь **нет**. Набор причин выхода (`V33ExitReason`, строка 46) **совпадает** с V3.0 (`V30ExitReason`, строка 38): `SL \| TP2 \| TP1_THEN_BE \| TP1_THEN_SL \| TP1_THEN_TIMEOUT \| TIMEOUT` | **ДА по поведению, НЕТ по документированию.** Стоп проверяется первым в этой реализации, но это свойство двух независимо написанных функций, а не общего правила; таймаут другой (48 против 50) |
| **V2.8** | `shared/legacyResearch/v25Trailing.ts` | `simulateTrailing` (38–105) | **Пары TP/SL нет.** Внутри одного бара `hitStop` действительно вычисляется первым (строка 66), но её исходы — только `SL \| BE \| TRAIL \| TIMEOUT` (`V25ExitReason`, строка 15). Развилки «TP1 против SL на одном баре» не существует: после входа позиция ведёт единственный трейлинг-стоп | **НЕТ.** Правило стоп-первым здесь — артефакт внутреннего устройства трейлера, а не выбор между целью и стопом |

Порог зафиксирован и в замороженных настройках: `outcome.sl_priority_on_ambiguous_bar = true`
(`strategyArchive/results/v2-real-20260915-080338/settings.json`, строка 69; читается в
`legacy/v2/tracker.ts` и пробрасывается как `FROZEN_ENGINE.slPriorityOnAmbiguousBar` в
`shared/frozenSettings.ts:55`). Он относится к V2.x-линии, где стоп и цель вообще могут коснуться одного бара;
к V3.x применим только через их собственный `manageTrade`.

**Что это доказывает тестом:**

| Стратегия | Фикстура |
|---|---|
| V3.0 / V3.3 | `tests/unit/signalMonitorParity.test.ts` — сценарии «LONG: стоп раньше цели» и «коридор и стоп на одном баре ⇒ отмена, а не сделка» |
| V3.0 / V3.3 | `tests/integration/signalMonitorPostgres.test.ts` — блок «Рестарт-паритет…» (V3.0, V3.3) и «TP1 → BE» |
| V2.8 | `tests/integration/signalMonitorPostgres.test.ts` — «V2.8: вход по следующему open ⇒ FILLED, затем trail-исход идентичен контролю» (исход `TRAIL`, не `SL`/`TP2`) |

**Ведение сделки отслеживает TP1 и TP2.** `trackCorridor` читает `entry.targets[0]` / `[1] ?? [0]` и передаёт
именно эти две цели в `manageTrade`. Цели лестницы за пределами TP2 в frozen-ведение не входят — это замороженное
поведение, а не упущение монитора.

## 4. Принцип неизменяемости (Immutable History)

1. **Никакого переписывания задним числом:** публикация хэшируется цепочкой в момент закрытия бара; `verifyIntegrity()`
   ломается при любом изменении уровней или исхода. Метод `expireStale()` прежних версий удалён — он переписывал записи.
2. **Неудачные сигналы сохраняются навсегда:** удаление или редактирование записей API не предусмотрено.
3. **Честная статистика:** «Доля сделок с R > 0» считается только по сделкам с исходом; отмены/истечения — отдельно;
   net R учитывает комиссии 2/5 bps (maker вход / taker выход).

## 5. Отсутствие автоматического исполнения (No Auto-Execution)

- Сетапы — структурированные наблюдения для человека. Платформа **не отправляет ордера** и не хранит торговые ключи.
- Любое торговое решение принимается пользователем самостоятельно на внешних площадках.

## 6. Ограничения и честные оговорки

- Журнал страницы `/signals` хранится в **localStorage браузера** — другой браузер = другой журнал, а закрытая вкладка
  останавливает ведение сетапов (журнал ограничен 500 записями и продвигается только пока вкладка видима). Отдельно
  существует **серверный** журнал — таблица `signals` в PostgreSQL, которую ведёт серверный движок независимо от
  браузера (см. §8). Это два журнала ОДНОГО ядра: они расходятся по охвату окна и по моменту публикации, поэтому
  числа на странице и в `GET /api/signals` могут отличаться.
- LIVE-эмиссия в песочнице сборки не воспроизводима (нет доступа к биржам); проверено паритетом реплеев с архивными
  раннерами и сквозным тестом на mock-«бирже» (`tests/unit/signals/*`).
- V2.8 в LIVE — только 1h-подмножество исследования (15m/30m/4h не сканируются); все цифры V2.8 — GROSS.
- Окно данных конечно (≤ 1000 баров 1h): зоны V3.3, известные до начала окна, отбрасываются правилом прогрева (как
  `zonesSkippedByWarmup` в источнике), поэтому первые сканы после старта могут пропустить сетапы по очень старым зонам.
- **Зона V3.3, образованная последним закрытым 4h-баром, появляется только после закрытия следующего 4h-бара.**
  `buildZones` (`v33Core.ts`) требует бар `i+1` для проверки FVG, поэтому на момент скана самая свежая зона видна
  с задержкой до 4 часов. То же поведение у архивного раннера (`v33Runner.ts`), то есть это свойство замороженной
  стратегии, а не расхождение LIVE: за счёт новой зоны candidate-selection (Amendment-1, «сначала новая зона») при
  скане может выбрать более старую зону → stop/TP1 отличаются от ретроспективного прогона по всей истории.
  Практический вывод: уровни в журнале — уровни **на момент скана**, задним числом они не «переписываются».
- Резервный источник KuCoin (при недоступном Binance) теперь запрашивается явным окном `startAt`/`endAt`
  (`FetchCandles` + `TIMEFRAME_MS`, v0.8.46): без окна биржа отдаёт свою страницу по умолчанию. Если глубина всё же
  меньше запрошенной, провайдер пишет `console.warn`, а движок отчитывается о нехватке истории вместо тишины.
- Источник свечей виден в статусе: `SymbolScanStatus.source` = провенанс последней свечи окна (`binance` /
  `kucoin (резерв)`, v0.8.47). В журнал по-прежнему попадают только сетапы стратегий — провенанс не влияет на уровни.
- **Журнал аудита принимает только фактические сетапы** (v0.8.48): если провайдер отдаёт QA-фикстуру
  (`provider.isDemo`), движок считает стратегии для диагностики, но ничего не публикует, а `/signals` предупреждает об
  этом. QA-данные не могут попасть в журнал рядом с реальными сделками.

## 7. Валидация на реальных данных (офлайн-протокол)

Песочница сборки не имеет доступа к биржам, поэтому LIVE-путь проверялся на **закреплённом историческом датасете**
Binance spot (`c3c1dce`, месячные ZIP, 2022-01 → 2025-12-31, 6 пар: BTC/ETH/BNB/SOL/XRP/DOGE) через **те же**
LIVE-реплеи (`runV30LiveReplay`, `runV33LiveReplay`, `runV28LiveReplay`), которые вызывает `LiveSignalEngine`.
Датасет лежит вне репозитория (≈17 МБ), поэтому постоянных тестов на нём нет — протокол воспроизводится вручную.

### 7.1. Что подтверждено

| Проверка | Результат |
| --- | --- |
| Прогон полной истории (V3.0 / V3.3, 6 пар) | Сетапы есть: V3.0 ≈540–600 записей на пару за 4 года, V3.3 ≈4.2–4.9 тыс. записей |
| Q4-2025, публикуемые V3.0 | BTC 23, ETH 30, BNB 40, SOL 32, XRP 36, DOGE 33 |
| Q4-2025, публикуемые V3.3 | BTC 110, ETH 124, BNB 99, SOL 115, XRP 127, DOGE 93 |
| Прогон **через сам движок** (241 скан, 10 суток скользящего окна ≤1000 баров) | 121 опубликованный сетап; ledger: 96 закрытых сделок, accuracy 86.5 %, avg RR 3.38, Σ net R +50.30 |
| Сверка журнала движка с полным реплеем | 50/50 сетапов совпали по времени/направлению/входу; V3.0 `runV30Series` vs журнал — 0 расхождений в обе стороны |
| V2.8, полная 1h-история (4 года, 6 пар) | 65 сетапов всего (≈1 на пару в 3–5 месяцев), все исполнимы |
| V2.8, скользящее окно 1000 баров | ни один сетап полной истории не потерян (0 missing); 31 из 65 отличаются на один тик по входу/стопу (квантование коридора, ATR считается от начала ряда) |

### 7.2. Почему V2.8 молчит в коротком окне

Sniper-фильтр V2.8 очень строгий: из ≈1150–1250 actionable-сетапов движка V2 на пару за 4 года публикуются лишь
10–14. В окне 10 суток (240 баров) математическое ожидание числа сетапов ≈0.05 на пару — тишина ожидаема.
Утверждение «V2.8 ничего не публикует» корректно формулировать так: **стратегия редкая**, а не «сломана»;
подтверждение работоспособности — те 65 реальных сетапов плюс паритетный тест `v28Live.test.ts`.

### 7.3. Что из этого следует для продукта

- Три стратегии действительно считаются на фактических свечах и публикуют сетапы; заглушек в LIVE-пути нет.
- Уровни V3.3 в журнале — «как на момент скана» (см. §6), включая задержку зоны до одного 4h-бара.
- Числа §7.1 — исторический факт на закреплённом датасете, **не прогноз**; CRYPTORA не исполняет сделки.

## 8. Серверный конвейер сигналов (PostgreSQL + `GET /api/signals`)

Серверный путь существует с интеграции серверного слоя стратегий (миграции 006/007) и приведён в рабочее состояние
в задаче «signal pipeline foundation» (миграция 009). Он НЕ заменяет LIVE-движок браузера и не содержит собственной
математики: сервер исполняет то же замороженное ядро, собранное esbuild из `src/`.

### 8.1. Путь данных

```
Binance REST (публичные klines)
   └─ MarketDataFetcher (кэш TTL, дедуп in-flight, нормализация символа/таймфрейма, лимит ядра)
        └─ LiveSignalEngine.scanNow()          ← ТОТ ЖЕ код, что и в браузере
             ├─ SignalsAuditLedger (сетапы последнего закрытого бара)
             └─ getRetrospective() (fill/outcome по закрытым свечам окна)
                  └─ signalRepository (hash-цепочка v2, дедуп по UNIQUE из 007)
                       └─ PostgreSQL: signals (007 + 009)
                            └─ GET /api/signals (публичное чтение, newest-first, ограничено)
```

Расписанием владеет `StrategyScheduler` (`server/services/strategyEngine/strategyScheduler.js`): он читает
`strategy_settings` перед каждым циклом и вызывает `scanStrategySafely()` только для включённых стратегий. Ядро
сканируется одним проходом (`scanNow()`), без внутренних интервалов.

### 8.2. Что хранится (миграции 007 + 009)

| Группа | Колонки | Источник значения |
|---|---|---|
| Идентичность | `strategy_id`, `strategy_version`, `engine_setup_id`, `symbol` (пара `BTC/USDT`), `timeframe`, `signal_candle_ts` | `SetupIssuance` ядра; `signal_candle_ts` = `setupOpenTime` закрытого бара |
| Уровни публикации | `entry_min`, `entry_max`, `stop_loss`, `targets` (NUMERIC[] — вся лестница TP1..TPn), `tp1`, `tp2` (первые два элемента, для совместимости с 007) | `entryZone`, `invalidationLevel`, `targets` |
| Контекст | `entry_type` (`LIMIT_CORRIDOR` \| `MARKET_NEXT_OPEN`), `valid_for_bars`, `exit_rule`, `metadata` (RR, факторы, latency, engineVersion) | `SetupIssuance` |
| Исполнение | `fill_price`, `filled_at`, `fill_stop`, `fill_targets` | `ReplayRecord.fill` (V2.8 сдвигает стоп/цели на дельту исполнения) |
| Исход | `status`, `closed_at`, `close_price`, `close_reason`, `result_r`, `net_result_r`, `pnl_result_pct`, `bars_held` | `ReplayRecord.outcome` |
| Целостность | `hash`, `previous_hash`, `outcome_hash`, `chain_version` | см. §4 и §8.3 |

**Миграция 010 (`010_signal_monitor_bookkeeping`, аддитивная):** колонки учёта монитора открытых сигналов
(`monitor_check_count`, `monitor_last_check_at`, `monitor_last_result`, `monitor_last_error`) и таблица
`signal_monitor_state` (одна строка на открытую группу `symbol+timeframe`, обслуживающая индекс
`idx_signals_open_group`). Миграция 009 **не переписана**: 010 добавлена отдельным файлом, только `ADD COLUMN` /
`CREATE TABLE` / `CREATE INDEX` без потери данных, применяется обычным раннером (без
`CREATE INDEX CONCURRENTLY`, который невозможен внутри одной транзакции `scripts/migrate.mjs`).

Ключ дедупликации — `UNIQUE (strategy_id, symbol, timeframe, signal_candle_ts)` из 007. Поскольку
`signal_candle_ts` = `setupOpenTime`, повторный скан того же закрытого бара и рестарт процесса не создают дублей, а
новый закрытый бар с новым сетапом — создаёт новую строку.

`tp1`/`tp2` — производные от `targets` (`resolveLevels()` в `signalRepository`), а не второй источник истины: движок
их не заполняет, их выводит репозиторий. Строки, записанные до 009 (только `tp1`/`tp2`), при чтении получают
лестницу из этих двух уровней.

### 8.3. Жизненный цикл: состояние сетапа и исход сделки

Домен `status` (009) = `SetupStatus` ядра, разделённый на две группы:

```
A) состояние сетапа:   ACTIVE  ──(коридор исполнен)──▶  FILLED
B) исход:              TARGET_REACHED | INVALIDATED | CLOSED      ← сделка была, есть R
                       EXPIRED | CANCELLED | UNRESOLVED           ← сделки не было, R = null
```

Правила переноса (и что здесь НЕ делается):

* значения берутся из `ReplayRecord.fill` / `ReplayRecord.outcome` **как есть** — сервер не пересчитывает ни уровни,
  ни R, ни причину выхода;
* если ядро исход не определило (`outcome = null`), статус не меняется: «ещё не известно» не превращается в «закрыто»;
* переход монотонен: закрытая строка больше не изменяется (`ALREADY_CLOSED`);
* строка, которой нет в БД (стратегия была выключена, когда сетап сформировался), не выдумывается — в сводке скана
  это `lifecycle.notFound`;
* `closed_at` — время ЗАКРЫТИЯ бара исхода (`barOpenTime` ядра + длительность бара). Если ядро время не отдало,
  сохраняется `null`, а не «сейчас»: выдуманное время попало бы в `outcome_hash`.

Целостность: `chain_version = 2` (строки после 009) означает, что `hash`/`previous_hash` считаются только по
неизменяемой части публикации, а изменяемый исход хэшируется отдельно в `outcome_hash`. Строки формы 007
(`chain_version = 1`) продолжают проверяться своей формой payload'а. `verifyChain()` возвращает ровно
`{ rows, breaks }` для обеих форм. Это сознательное расхождение с браузерным журналом, где `auditHash` считается по
issuance, а `outcomeHash` — по исходу: сервер дополнительно хэширует исход при КАЖДОМ переходе, включая `FILLED`.

### 8.4. R в CRYPTORA: что это, кто считает, что нужно для пересчёта

**R — результат сделки в единицах первоначального риска**, а не процент и не «профит-фактор».

| Величина | Формула (frozen-ядро) | Где живёт |
|---|---|---|
| `grossR` (`result_r`) | signed: `(exit − entry) / (entry − stop)` для LONG и зеркально для SHORT; для TARGET_REACHED — по фактической цене выхода | `src/services/signals/live/lifecycle.ts` (`manageTrade` → `r.grossR`), агрегация окна — `ReplaySummary` |
| `netResultR` | `grossR − feeR(makerBps, takerBps)`, где комиссия выражена в R: 2 bps на вход (maker) и 5 bps на выход (taker); константы — `V30_CONSTANTS` / `V33_CONSTANTS` | там же (`lifecycle.ts:110-119`) |
| `pnlResultPct` | `pnlPct(direction, entry, exit)` — процент от цены входа (gross) | там же |
| ΣR / «доля R > 0» | сумма и доля по сделкам с исходом: `TRADE_CLOSED_STATUSES` = TARGET_REACHED + INVALIDATED + CLOSED; отмены/истечения в знаменатель не входят | `ReplaySummary.{grossRSum, netRSum, positiveR, negativeR}`, `strategyArchive/engine/rMetrics.ts` |

Входы для пересчёта: закрытые свечи окна (1h исполнение + 4h/1d контекст), уровни публикации, факт и цена
исполнения, правило выхода стратегии. Ничего из этого сервер не хранит «про запас» и не восстанавливает по-своему:
R приходит готовым из реплея и записывается в `result_r` / `net_result_r`.

Оговорки, которые обязаны быть видны пользователю:

* **V2.8 исследована при нулевых комиссиях** (`fees = 0`), поэтому её net R при модели 2/5 bps отрицателен. Это
  свойство стратегии (GROSS-ONLY), а не ошибка хранения или транспортировки;
* **R существует только у сделок**: у `EXPIRED` / `CANCELLED` / `UNRESOLVED` он `null`, и «0» здесь недопустимо
  (0 ≠ «нет данных»);
* **отрицательный net R ≠ ошибка**: `INVALIDATED` даёт ≈ −1 R по построению;
* **UI показывает серверные `result_r` / `net_result_r`** (`GET /api/signals` → карточка сигнала и панель
  статистики). Браузерный журнал (`SignalsAuditLedger`) остаётся отдельным источником только в сворачиваемом
  блоке «Статистика и аудит» и **не смешивается** с серверными агрегатами. Формат R единый
  (`formatSignedR`, «+1.67 R»), на клиенте R не пересчитывается.

### 8.5. Контракт `GET /api/signals`

```
GET /api/signals?symbol=&strategy=&status=&open=&direction=&limit=&offset=
```

* **Фильтры:** `symbol` (принимаются `BTC/USDT`, `BTCUSDT`, `BTC` → нормализуется к `BTC/USDT`), `strategy`
  (только известные id, иначе `400 INVALID_STRATEGY` — молча пустой список не отдаётся), `status` (одно из восьми
  состояний), `open=true|false` (открытые = ACTIVE+FILLED / терминальные), `direction=LONG|SHORT`;
* **Пагинация:** `limit` 1..200 (по умолчанию 50), `offset` 0..5000; выход за границы — `400`, а не тихая обрезка;
* **Порядок:** детерминированный, новые сверху — `created_at DESC, id DESC` (`ordering` в ответе);
* **Ответ:** `signals`, `count` (страница), `total` (всего под фильтром), `limit`, `offset`, `maxLimit`,
  `appliedFilters` (что реально применено), `statuses` и `openStatuses` (домен состояний — UI не должен хардкодить),
  `source: "server"`;
* **Уровни:** только посчитанные стратегией — `entryMin`/`entryMax`, `stopLoss`, `targets` (вся лестница),
  после исполнения — `fillPrice`/`fillStop`/`fillTargets`. Досчитывать цели на клиенте запрещено.

Индекс `idx_signals_symbol_status_created` (009) обслуживает горячий путь будущего UI: выбранный инструмент +
ограниченная лента последних сигналов с фильтром по состоянию.

### 8.5.1. Контракты `GET /api/signals/statistics` и `GET /api/signals/monitor`

```
GET /api/signals/statistics?period=all|24h|7d|30d|90d&strategy=&symbol=
GET /api/signals/monitor
```

* **`/statistics`** — агрегаты по PostgreSQL (`server/services/signalStatistics.js`), НЕ по браузерному журналу:
  `published`, `waitingEntry`, `filled`, `completed`, `cancelled`, `expired`, `unresolved`, `targetReached`,
  `invalidated`, `closed`, `wins`, `losses`, `winRatePct`, `avgGrossR`, `avgNetR`, `grossRSum`, `netRSum`,
  `fillRatePct`, `completionRatePct` + разрезы `byStrategy` / `bySymbol` + `definitions` (человеческие пояснения
  метрик). Доля успешных считается только по сделкам (`TRADE_CLOSED_STATUSES`): сигнал, не дождавшийся входа, в
  знаменатель не попадает. `null` означает «нет данных» и обязан отображаться как «—», а не «0 %».
* **`/monitor`** — телеметрия серверного монитора открытых сигналов: `running`, `cycles`, `inFlight`,
  `lastTickStartedAt`/`lastTickFinishedAt`/`lastTickDurationMs`, `lastError`, `consecutiveFailures`, `stale`,
  `lastSummary`. Эндпоинт **только читает**: ни один пользовательский маршрут не меняет состояние стратегий.

### 8.6. Что серверный путь НЕ делает

* не исполняет ордера, не хранит торговые ключи (§5);
* мониторит открытые сигналы **не в реальном времени внутри бара**, а по факту закрытия свечи: см. §9;
* не синхронизируется с журналом браузера и не «чинит» его;
* не включает стратегии: после миграций все три выключены, включение — действие администратора
  (`PATCH /api/admin/strategies/:id`).

### 8.8. Пользовательский интерфейс (Signals V2)

Страница `/signals` переведена с браузерного журнала на серверную ленту `GET /api/signals`
(задача 9.3, дизайн — `docs/agent-plan/SIGNALS_V2_HANDOFF.md`). Главный принцип сохраняется:
**показывается только то, что посчитало ядро и сохранил сервер** — ни один уровень, статус, R или время
не досчитывается на клиенте.

**Компоненты и порядок на мобильном** (`src/pages/SignalsPage.tsx`):

| Блок | Компонент | Источник |
|---|---|---|
| Селектор монеты (+ чипы монет с сигналами) | `SignalsCoinSelector` | полный активный Spot-universe (`SymbolPickerModal`, лениво, кэш) — **не** админ-вселенная скана; чипы — `distinct` по загруженной ленте |
| Сводка последнего/выбранного сигнала | `SignalSummaryCard` | `signals[0]` / выбранный сигнал |
| Свечной график выбранного инструмента | `SignalChartCard` → общий `CandleChart` | свечи — только выбранный символ и таймфрейм (`useSignalChartCandles`), маркеры — сохранённые сигналы, линии — уровни выбранного сигнала |
| Уровни выбранного сигнала + детали | `SignalDetailsPanel` | `entryMin/entryMax/stopLoss/targets[]` (+ `fill*` после исполнения), исход, R, аналитика, целостность |
| История сигналов монеты | `SignalHistoryList` | та же лента `GET /api/signals?symbol=…`, постранично (`limit`/`offset`) |
| Статистика и аудит | `SignalsLedgerAuditSection` | серверная лента и браузерный журнал — **отдельно**, не смешиваются |

**График.** `CandleChart` расширен аддитивными пропсами `markers` / `levelLines` / `onMarkerClick`
(`src/types/chart.ts` — библиотечно-независимые типы). Существующие потребители (/coin, /overview) их не
передают и ведут себя как раньше. Линии уровней заменяются по `id`: выбор другого сигнала переключает линии,
смешать уровни двух сигналов нельзя. Маркер встаёт только на бар, реально присутствующий в загруженных свечах;
сторона читается без цвета (форма `arrowUp`/`arrowDown`, позиция и текст «LONG · V3.0»).

**Отображение.** `src/services/signals/ui/signalUiModel.ts` — единственная точка `SignalDto` → модель UI
(произвольная длина `targets[]`, отсутствующие поля, неизвестный статус); `signalChartProjection.ts` — маркеры
и линии; `src/utils/serverSignalText.ts` — человеческий словарь (статусы, направление, «Цель N», пояснение R).
Таймфрейм сигнала (исполнения, у всех трёх стратегий `1h`; V2.8 — не «15m») отделён от таймфрейма графика,
рассогласование помечается.

**Гонки и бюджет запросов.** Смена монеты/таймфрейма отменяет устаревшие запросы (`AbortController` +
монотонный номер запроса в `useServerSignals` / `useSignalChartCandles`). Свечи запрашиваются только для
выбранного символа и таймфрейма — веера `universe.map(fetchCandles)` нет: открытие экрана не грузит свечи,
выбор монеты — один запрос свечей, переключение таймфрейма — один запрос того же символа.

**Статусы.** Отображается только достоверный серверный статус; фронтенд не определяет «цель достигнута /
стоп сработал / позиция закрыта» по текущей цене. Рядом со статусом — подсказка «Статус отражает последнее
состояние, зафиксированное сервером по закрытым свечам». Неизвестный серверу статус показывается как есть,
не подменяется нейтральным словом.

**Часовой пояс.** `src/utils/timePresentation.ts` — ЕДИНСТВЕННЫЙ форматтер времени в продукте: оси графиков,
перекрестие, бейджи свежести, время сигнала и время исхода зовут его. Источник зоны —
`Intl.DateTimeFormat().resolvedOptions().timeZone` (пояс ОС/браузера), поэтому Asia/Tokyo, Europe/Berlin с
переходом на летнее время и любой другой пояс отображаются корректно без правок кода. В базе и API время
остается UTC/ISO. Режим `mode: 'UTC'` сохранен только для отладки и печати. Захардкоженных UTC+3 / Europe/Moscow
в презентационной логике нет — это проверяется тестом, сканирующим исходники.

**Статус сканирования (BUG C).** Прежняя плашка читала состояние браузерного движка
(`LiveSignalEngine.getStatus()`) и показывала «LIVE-скан · каждые 60с» при выключенных стратегиях. Теперь
источник один — серверный `/api/strategies` (`useServerScanner`, опрос 15 с, пауза при скрытой вкладке):

| Состояние сервера | Что показывает плашка |
|---|---|
| 0 включенных стратегий | «Сканирование сигналов выключено» (+ пояснение, что сохраненные сигналы продолжают отслеживаться) |
| N включенных | «Сканирование включено: N стратегий · каждые Xс» — X из `scanIntervalSeconds`, а не константа UI |
| стратегия в ERROR | отдельная строка с текстом ошибки сканирования, не подмененная словом «выключено» |
| запрос состояния упал | «Статус сканирования недоступен»: отсутствие ответа сервера не есть доказательство выключенного сканера |

Плашка ничего не переключает: пользовательского эндпоинта, меняющего состояние стратегий, нет.

**Пустые и ошибочные состояния (BUG B).** Раньше на экране было ДВА разных блока про «нет сигналов»
(страничный и внутри `SignalSummaryCard`). Теперь блок один — `signals-empty[data-state]` с явной причиной:
`scanner-off` (сервер не публикует), `empty` (лента загрузилась и пуста), `error` (`/api/signals` упал),
`market-error` (свечи недоступны). Ни одна причина не маскируется под другую.

**Авто-обновление.** Лента сигналов опрашивается с интервалом 60 с, статус сканера — 15 с, статистика — 60 с
(`useAutoRefresh`: ограниченный polling, пауза при скрытой вкладке, отмена устаревших запросов). Серверный
монитор (§9) пишет исход в PostgreSQL независимо от открытой вкладки, поэтому статус сигнала меняется на
экране сам — без перезагрузки страницы. Это проверено в `e2e/signalsV2.spec.ts` сценарием P.

**Серверная статистика.** `SignalStatisticsPanel` показывает агрегаты `GET /api/signals/statistics` (PostgreSQL),
а не браузерный `SignalsAuditLedger`. Первый экран — человеческие счетчики (опубликовано, ожидают входа,
дождались входа, завершились сделкой, прибыльных/убыточных, доля успешных); производные метрики (gross R,
net R, суммы R, разрезы по стратегии и инструменту) — под «Подробнее». Браузерный журнал остался отдельным
сворачиваемым блоком «Статистика и аудит» и с серверными агрегатами не смешивается.

**Ограничения (остаток).** Статус может отставать на бар: исход определяется по закрытым свечам окна
(<= 1000 баров 1h), это «последнее зафиксированное сервером состояние», а не «прямо сейчас». Сигналы старше
окна реплея могут оставаться `ACTIVE`/`FILLED` до тех пор, пока не попадут в окно (§9). Серверный перенос
браузерного журнала — отдельная задача.

## 9. Автоматическое серверное сопровождение открытых сигналов

> Терминология. Монитор — это **«автоматическое серверное сопровождение по закрытым свечам»**.
> Он работает по **закрытым** свечам и потому отстаёт от цены не более чем на один бар;
> это не tick-realtime исполнение и не стриминг. В интерфейсе и документации нельзя
> обещать «в реальном времени» для TP/SL-сопровождения: внутри незакрытого бара
> «неизвестно» честнее любого предположения.

До монитора исход сигнала определялся только реплеем окна скана: страница показывала статус «по данным
последнего закрытого бара», а сигнал, не дождавшийся входа, мог годами висеть `ACTIVE`, если стратегия была
выключена или окно реплея не покрывало момент.

**Архитектура.** `server/services/signalMonitor/signalMonitor.js` + `signalTradeManager.js`:

```
StrategyScheduler (независимо) ──▶ getSignalMonitor().tick()   MONITOR_TICK_MS = 30 с
                                     ├─ SELECT открытые сигналы (ACTIVE|FILLED), бюджет <= 500 / цикл
                                     ├─ группировка по symbol+timeframe (<= 64 групп, конкуррентность <= 4)
                                     ├─ MarketDataFetcher: lookback = минимум(окно ядра, окно сигнала),
                                     │                      размер считается по ТАЙМФРЕЙМУ ГРУППЫ
                                     └─ trackPublishedSetup()  ← ЗАМОРОЖЕННЫЙ trade-management, без изменений
                                          └─ closeSignal(...) → PostgreSQL (монотонный переход, outcome_hash)
```

**Свойства, которые обязаны сохраняться:**

* **Независимость от браузера.** Монитор живет в процессе сервера; закрытая вкладка не влияет на учет.
* **Переживание рестарта.** Состояние цикла — в `signal_monitor_state` (010), счетчики проверок — в колонках
  `signals.monitor_*`. После перезапуска процесс продолжает с того же места, строки не дублируются.
  Монитор **stateless по стратегии**: он не хранит промежуточное состояние сделки, а каждый тик
  восстанавливает его из бара сетапа и закрытых свечей теми же frozen-функциями. Поэтому рестарт не может
  изменить исход — это проверено `tests/integration/signalMonitorPostgres.test.ts`
  (блок «Рестарт-паритет и частичный жизненный цикл») для V3.0, V3.3 и V2.8 на настоящем PostgreSQL.
* **Переживание отказа рынка.** Ошибка рыночных данных не роняет тик и не переводит сигнал в терминальное
  состояние: группа помечается `ERROR`, сигнал остается открытым, следующий тик повторяет попытку. После
  `MONITOR_STALE_AFTER_FAILURES` подряд статус монитора помечается `stale` — UI обязан показать это честно.
* **Паритет с ядром.** `signalTradeManager` — адаптер вокруг замороженного `trackPublishedSetup()`
  (`src/services/signals/live/lifecycle.ts`): семантика закрытого бара, `CORRIDOR_EXPIRY_BARS = 3`,
  `TIMEOUT_BARS = 50` (V3.0) / `48` (V3.3), комиссии из `V30_CONSTANTS`/`V33_CONSTANTS`,
  LONG fill = `min(open, zoneHigh)`, SHORT fill = `max(open, zoneLow)` — все как в ядре. Любое расхождение
  ловит `tests/unit/signalMonitorParity.test.ts`.
* **Бюджет запросов.** Нет fan-out'а: на группу (символ+таймфрейм) — один запрос свечей за тик, число групп и
  число сигналов ограничены константами. Вселенная из сотен инструментов не превращается в сотни запросов,
  потому что в группу идут только ОТКРЫТЫЕ сигналы.

### 9.1. Таймфрейм исполнения — из строки сигнала, не из удобства провайдера

Монитор читает `signals.timeframe` и запрашивает свечи **именно этого** таймфрейма; длительность бара
(`tfMs`) для расчёта размера окна берётся из той же таблицы ядра `ARCHIVE_TF_MS`
(`src/services/strategyArchive/types.ts`), по которой переводит свечи `ohlcvArrayToArchive`.
Никакой стратегии таймфрейм не подменяется.

Доказательства по коду:

| Стратегия | Таймфрейм исполнения | Где зафиксировано |
|---|---|---|
| V3.0 | `1h` | `V30_CONSTANTS.EXEC_TF = '1h'` (`v30Core.ts:32`); движок публикует `timeframe: EXEC_TIMEFRAME`, `EXEC_TIMEFRAME = '1h'` (`LiveSignalEngine.ts:56`, применение на `:522`) |
| V3.3 | `1h` | `V33_CONSTANTS.EXEC_TF = '1h'` (`v33Core.ts:35`) |
| V2.8 | `1h`, причём жестко | `V28_LIVE_TIMEFRAME = '1h'` (`v28Live.ts:52`); `v28EntryAtNextOpen` → `resolveEntry(setupOpenTime, TF_MS[V28_LIVE_TIMEFRAME], next)`, а `resolveEntry` (`legacy/v2/stateMachine.ts:7-19`) требует `nextCandle.openTime === setupCandleTime + timeframeMs` — несоседний или нечасовой бар отвергается (`NO_CONTIGUOUS_NEXT_BAR`) |

Контекстные свечи другого таймфрейма — для **поиска** сетапа: `V30_CONSTANTS.STRUCT_TF = '4h'`
(`v30Core.ts:33`) — структурный таймфрейм, а не исполнение. Монитор их для ведения не запрашивает: он берёт
именно `signals.timeframe`.

Регрессия: группа с таймфреймом не `1h` обязана получить окно, посчитанное по своему бару
(`tests/unit/signalMonitor.test.ts`, блок `timeframeMs`). Неизвестный таймфрейм даёт `SKIP`
с причиной `UNKNOWN_TIMEFRAME`, а не молчаливую подстановку 1h.

### 9.2. Окно реплея против максимального жизненного цикла

| Стратегия | Execution TF | Max lifecycle (баров) | Из чего складывается | Monitor replay bars | Достаточно |
|---|---|---|---|---|---|
| V3.0 | `1h` | ≈ 53–54 | коридор `CORRIDOR_EXPIRY_BARS = 3` + `TIMEOUT_BARS = 50` (`v30Core.ts:24-30`) + 1–2 на fill | `MAX_LOOKBACK_BARS = 1000` | **YES** |
| V3.3 | `1h` | ≈ 51–52 | коридор 3 + `TIMEOUT_BARS = 48` (`v33Core.ts:27-33`) + 1–2 на fill | 1000 | **YES** |
| V2.8 | `1h` | ≈ 113 | вход на следующем баре (1) + срез `barsFromEntry.slice(0, outcomeTimeoutBars + 64)` = 48 + 64 = 112 (`v28Live.ts:349`) | 1000 | **YES** |

Происхождение чисел:

* размер окна — `MAX_LOOKBACK_BARS = 1000` закрытых баров, ровно `CANDLE_LIMIT_1H` ядра
  (`signalMonitor.js:60`, `LiveSignalEngine.ts:53`);
* запас после бара сетапа — `LOOKBACK_MARGIN_BARS = 16` (`signalMonitor.js:65`);
* `outcomeTimeoutBars = 48` — из `outcome.timeout_bars` замороженных настроек
  (`results/v2-real-20260915-080338/settings.json:70`), проброшен как `FROZEN_ENGINE.outcomeTimeoutBars`
  (`shared/frozenSettings.ts:51`). Внутренний `TIMEOUT_BARS = 10` трейлера (`v25Trailing.ts:15`) применяется
  только пока позиция **не** вошла в BE; после взвода BE таймаута нет, поэтому именно срез 112 баров и
  ограничивает сверху жизненный цикл V2.8;
* контекст (4h/1d) на жизненный цикл не влияет: он нужен только генерации (§9.1).

**Вывод: окно (1000 баров) заведомо больше максимального жизненного цикла любой из трёх стратегий
(≈ 113 баров), поэтому корректный сигнал не может выпасть из окна при обычных параметрах.**
Сигнал может остаться вне окна только если он **старше 1000 баров** своего таймфрейма — и тогда монитор
честно пишет `UNRESOLVED` / `OUT_OF_DATA_WINDOW`, а не оставляет строку `ACTIVE` навсегда
(проверено интеграционным тестом «сигнал старше окна ядра», который дополнительно фиксирует запрос
ровно в `MAX_LOOKBACK_BARS` — без неограниченного фетча).

### 9.3. Когда монитор запускается, а все стратегии выключены

После миграций все три стратегии имеют `enabled = false`, `status = OFF`. Это не мешает монитору:

* монитор стартует **независимо от планировщика сканов** и от ВКЛ/ВЫКЛ стратегий
  (`server/index.js`); условие запуска — доступность БД, а не включённая стратегия;
* он работает с тем, что **уже сохранено** в `signals`: выключенная стратегия не создаёт новых
  сигналов, но существующие открытые сопровождаются до терминала — это и есть задуманная семантика;
* монитор **не генерирует** сетапы, **не включает** стратегии и **не меняет** их настройки; у него нет
  такого маршрута и такого кода. Единственный пользовательский эндпоинт, меняющий состояние стратегий,
  — админский `PATCH /api/admin/strategies/:id`;
* если открытых сигналов нет, тик не делает **ни одного** запроса к бирже.

Проверено тестом `tests/integration/signalMonitorPostgres.test.ts`, блок «Монитор при выключенных
стратегиях»: реальный `StrategyScheduler` при всех OFF не вызывает скан ни разу, `strategy_settings`
(включая `enabled`, `scan_interval_seconds`, `symbols`, телеметрию) не меняется, а уже сохранённый
открытый сигнал доводится монитором до терминала.

### 9.4. Частичный жизненный цикл и TP1

Выход на TP1 без TP2, стопа или таймаута — это **не** исход: `manageTrade` возвращает `null`, и монитор
оставляет строку в нетерминальном `FILLED` (позиция открыта). Промежуточное состояние не хранится и не
может быть потеряно между 30-секундными тиками или рестартом: оно каждый раз **пересчитывается** из бара
сетапа по закрытым свечам. Окно из §9.2 покрывает весь жизненный цикл от бара сетапа, поэтому усечённой
истории не возникает. Ограничение честное: у публикации за пределами TP2 целей frozen-ведение не ведёт
(§3.1).

Переход TP1 → BE проверен отдельным тестом: на баре, где достигнуто TP1, выход ещё невозможен
(`beArmed` требует `i > tp1Bar`), поэтому монитор обязан оставить `FILLED`; после рестарта тот же путь
даёт `TP1_THEN_BE` с тем же R, что и контроль без рестарта.

### 9.5. Контракт реконструкции: строка БД → адаптер → вход frozen-функции

`toPublishedSetup(row)` (`server/services/signalMonitor/signalTradeManager.js:44`) — **чистый перевод
формы**: он не пересчитывает ни одного уровня.

| Поле входа `trackPublishedSetup` | Из колонки/поля БД | Проверка адаптера |
|---|---|---|
| `strategyId` | `strategy_id` | должна быть в `TRACKED_STRATEGY_IDS`, иначе `UNTRACKED_STRATEGY` |
| `strategyVersion` | `strategy_version` | `?? null` |
| `symbol` | `symbol` | — |
| `timeframe` | `timeframe` | **таймфрейм исполнения**, по нему же фетчатся свечи (§9.1) |
| `direction` | `direction` | — |
| `setupOpenTime` | `signal_candle_ts` → `getTime()` | не число ⇒ `NO_SETUP_TIME` |
| `entryType` | `entry_type` | `LIMIT_CORRIDOR` → `trackCorridor`; `MARKET_NEXT_OPEN` → `trackNextOpen` |
| `entryZone` | `[entry_min, entry_max]` (`entry_max ?? entry_min`) | нет `entry_min` ⇒ `NO_ENTRY_ZONE` |
| `invalidationLevel` | `stop_loss` | нет ⇒ `NO_STOP` |
| `targets` | `targets[]`, отфильтрованы конечные | пусто ⇒ `NO_TARGETS` |
| `exitRule` | `exit_rule` | `?? ''` |
| `validForBars` | `valid_for_bars` | `?? null` |
| `createdAt` | `created_at` | fallback — `setupOpenTime` |
| `latencyBars` | `metadata.latencyBars` | `?? 0` |
| `riskRewardRatio` / `confirmingFactors` / `invalidationFactors` | `metadata.*` | `?? 0` / `?? []` |
| `status` | `status` | должна быть в `SIGNAL_STATUSES` |
| `prevHash` / `auditHash` | `previous_hash` / `hash` | `?? 'GENESIS'` |
| `fill` (информационно) | `fill_price` + `filled_at` (+ `fill_stop`, `fill_targets`) | только если оба не NULL |

**Чего в строке НЕТ и не должно быть:** `intermediate management state` и `bars already processed`.
`trackPublishedSetup` не читает `entry.fill` и не хранит прогресс — он детерминированно переигрывает путь
от `setupOpenTime` по закрытым свечам, поэтому единственное, что нужно для идентичного результата после
рестарта, — это **уровни публикации + бар сетапа + таймфрейм исполнения**, то есть ровно текущая строка
плюс свечи. Этим и объясняется паритет рестарта (§9).

**Чего монитор не делает:** не исполняет ордера, не считает новых сетапов (это задача `StrategyScheduler` +
`scanNow()`), не переписывает терминальные строки, не подменяет `closed_at` текущим временем, если ядро время
не отдало.

## 10. Знаменатели статистики: точные формулы

Все агрегаты — один SQL-набор (`aggregateSelect` в `server/services/signalStatistics.js`), поэтому «итого»,
«по стратегии» и «по инструменту» считаются по ОДНИМ правилам. Фильтры (`period`, `strategyId`, `symbol`)
общие для всех разрезов.

Пусть `TRADE_CLOSED_STATUSES = {TARGET_REACHED, INVALIDATED, CLOSED}` (`signalRepository.js:88`).

### 10.1. Счётчики

| Метрика | Точная формула | Что входит / не входит |
|---|---|---|
| `published` | `COUNT(*)` по фильтру | все строки, включая `ACTIVE`, `CANCELLED`, `EXPIRED`, `UNRESOLVED` |
| `waiting` | `COUNT(*) FILTER (status = 'ACTIVE')` | ждут входа |
| `filled` | `COUNT(*) FILTER (status = 'FILLED')` | **уже в позиции**, но сделка не завершена |
| `completed` | `COUNT(*) FILTER (status = ANY(TRADE_CLOSED_STATUSES))` | только завершённые сделки |
| `cancelled` | `COUNT(*) FILTER (status = 'CANCELLED')` | сделки не было |
| `expired` | `COUNT(*) FILTER (status = 'EXPIRED')` | сделки не было |
| `unresolved` | `COUNT(*) FILTER (status = 'UNRESOLVED')` | бар сетапа вне окна: **не сделка** |

### 10.2. Классификация завершённой сделки по результату

Четыре **взаимоисключающие** корзины, покрывающие `completed`:

| Корзина | Формула | Смысл |
|---|---|---|
| `wins` | `COUNT(*) FILTER (status = ANY(T) AND result_r > 0)` | результат строго больше нуля |
| `losses` | `COUNT(*) FILTER (status = ANY(T) AND result_r < 0)` | результат строго меньше нуля |
| `breakEven` | `COUNT(*) FILTER (status = ANY(T) AND result_r = 0)` | результат **ровно 0 R — НЕ убыток** |
| `unrated` | `COUNT(*) FILTER (status = ANY(T) AND result_r IS NULL)` | завершённая сделка без результата |
| `unratedCompleted` | `unrated` — то же значение под именем, которое не путается со статусом | см. ниже |

**NULL никогда не трактуруется как 0.** В PostgreSQL выражение `NULL = 0` даёт `NULL`, а не истину, поэтому
ни одна из трёх знаковых корзин не захватывает `NULL` неявно; отдельное условие `result_r IS NULL`
выделяет такие строки явно. Отдельной категории «ничья среди неопределённых» не появляется: неизвестный
результат — это отсутствие значения, а не ноль.

Тождество: `wins + losses + breakEven + unrated = completed`.

**Почему `unratedCompleted` названо именно так.** Рядом существует счётчик `unresolved` — это статус
«исход не отслежен» (бар сетапа вне окна наблюдения), где **сделки не было**. `unrated` / `unratedCompleted`
— это завершённая сделка (`TARGET_REACHED` / `INVALIDATED` / `CLOSED`), у которой в `result_r` `NULL`.
Это разные вещи, и совпадающие короткие имена привели бы к путанице в API и в UI.

```
ratedCompleted   = wins + losses + breakEven
unratedCompleted = completed - ratedCompleted = unrated
```

Тождество `ratedCompleted + unratedCompleted = completed` проверяется тестом. При этом `ratedCompleted`
берётся **отдельной SQL-колонкой** с условием `result_r IS NOT NULL`, а не вычисляется как
`wins + losses + breakEven`: если эти два выражения когда-либо разойдутся, расхождение увидит тест,
а не спрячет его арифметический тождественный вид.

### 10.3. Знаменатель доли успешных

```
ratedCompleted = wins + losses + breakEven
winRatePct     = wins / ratedCompleted * 100   (округление до 0.1)
```

То есть «доля прибыльных среди завершённых сделок **с известным результатом**».
При `ratedCompleted = 0` результат — `null` («—»), а не `0 %`: «нет данных» ≠ «ноль».

**Почему именно так, а не иначе:**

* не `wins / completed` — завершённая сделка без результата R (`unrated`) не имеет знака, и включать её в
  знаменатель значит занижать долю успешных по причине «нет данных», а не по причине убытка;
* не `wins / (wins + losses)` — сделка «в ноль» (`breakEven`) это завершённая сделка с известным
  результатом, и она обязана быть в знаменателе. Иначе доля успешных росла бы только за счёт ничьих.

Действующее правило: `0 R` — собственная корзина `breakEven`, а убыток требует строгого `result_r < 0`.
Никакая другая формула знаменателя не применяется: `wins / completed` и `wins / (wins + losses)`
отвергнуты по причинам выше и в продукте не используются.

### 10.4. Средние и суммы R — поведение при NULL

Условие `result_r IS NOT NULL` написано в SQL **явно**, а не оставлено на неявное правило «SQL-агрегат
пропускает NULL». Значение то же, но намерение читается из запроса и не зависит от поведения агрегата:

| Метрика | Формула | Что происходит с NULL |
|---|---|---|
| `grossRSum` | `SUM(result_r) FILTER (status = ANY(T) AND result_r IS NOT NULL)` | сделка без R не даёт вклада; это **отсутствие значения**, а не `+0` |
| `netRSum` | `SUM(net_result_r) FILTER (status = ANY(T) AND net_result_r IS NOT NULL)` | то же |
| `avgGrossR` | `AVG(result_r) FILTER (status = ANY(T) AND result_r IS NOT NULL)` | среднее только по сделкам с известным R; знаменатель — `ratedCompleted`, не `completed` |
| `avgNetR` | `AVG(net_result_r) FILTER (status = ANY(T) AND net_result_r IS NOT NULL)` | то же |

Если ни у одной завершённой сделки нет R, `SUM`/`AVG` дают `null` — и UI обязан показать «—».

| `completionRatePct` | `completed / published × 100` |

### 10.8. Исход ≠ классификация, и gross ≠ net

**Классификация идёт ТОЛЬКО по записанному `result_r`.** Ни название исхода (`close_reason`), ни
lifecycle-статус сделку не классифицируют — они решают лишь, была ли сделка вообще (терминальный статус).
Поэтому `TP1_THEN_BE` не объявляется «в ноль» автоматически: он попадает в `breakEven` **тогда и только
тогда**, когда фактический `result_r` равен 0. Если бы комиссии или net-семантика изменились и та же
причина исхода дала бы `result_r = -0.07`, сделка корректно ушла бы в `losses` — и наоборот. Это важно
потому, что у gross и net результата разная семантика, и вывод классификации из имени исхода заморозил бы
её навсегда.

Правило одно для всех трёх стратегий:

| Значение записанного `result_r` | Корзина |
|---|---|
| `> 0` | `wins` |
| `< 0` | `losses` |
| `= 0` | `breakEven` |
| `IS NULL` | `unrated` |

**Классификация одна и построена на gross.** Gross (`result_r`, до комиссий) и net (`net_result_r`,
после комиссий) показываются раздельно: в «Подробнее» панели есть «Средний gross R», «Средний net R»,
«Σ gross R», «Σ net R». Своей знаковой классификации у net **нет** — иначе одна и та же сделка могла бы
одновременно быть «прибыльной» по gross и «убыточной» по net, и счётчики перестали бы сходиться.
Если такая классификация когда-либо понадобится, она добавляется отдельным набором корзин
(`netWins` / `netLosses` / …), а не подменой существующих.

### 10.9. Куда попадает результат 0 R — и достижим ли `unrated`

**0 R — отдельная корзина `breakEven`, а НЕ убыток.** Убыток требует строго `result_r < 0`. Типичный
носитель нуля — `TP1_THEN_BE`, где половина позиции закрыта по TP1, а половина по цене входа
(`managedExitPrice('TP1_THEN_BE', …) = entry`, `grossR = 0.5·rOf(tp1) + 0.5·rOf(entry)`): сделка
завершена (`CLOSED`), но прибыли не дала. UI обязан показывать такую сделку строкой «В ноль», а не
«Убыточные», и не прятать в третью корзину.

**`unrated` в реальном frozen-потоке не порождается — это защитная корзина.** Единственный источник
`resultR = null` в frozen-коде — `noTrade()` в `lifecycle.ts:49`, и он используется только для
`EXPIRED` / `CANCELLED` / `UNRESOLVED`, т.е. для статусов, где сделки не было. Все пути, дающие
терминальный статус (`TARGET_REACHED` / `INVALIDATED` / `CLOSED`), возвращают числовой
`round(r.grossR, 4)` (`lifecycle.ts:118`, `lifecycle.ts:154`). При этом схема (`result_r NUMERIC NULL`, миграция 009) терминальный NULL
допускает, а `syncSignalLifecycle` → `closeSignal` пишет `num(outcome.resultR)` без проверки. Поэтому
корзина нужна: если такой результат когда-либо появится (будущая стратегия, частичная синхронизация,
ручная правка), статистика не смешает «результат неизвестен» с убытком. Это зафиксировано тестом
«frozen-поток ВСЕГДА даёт R для терминального статуса: unrated — защитная корзина».

### 10.10. UI

Панель статистики (`src/components/signals/SignalStatisticsPanel.tsx`) показывает на первом экране
отдельными строками: **Прибыльные**, **В ноль**, **Убыточные**, **Без расчёта результата** и
**Доля успешных**.
В блоке «Подробнее» — расшифровка знаменателя: «завершённые сделки с известным результатом = прибыльные +
убыточные + в ноль», явное «сделка в ноль не является убыточной», явное «завершённые сделки без
результата R в знаменатель не входят» и явное «классификация — по записанному результату, а не по
названию исхода; классификация одна и основана на результате до комиссий».

Тождества, проверяемые тестом: `wins + losses + breakEven + unrated = completed` и
`waiting + filled + cancelled + expired + unresolved + targetReached + invalidated + closed = published`.

`MAX_OPEN_SIGNALS_FOR_SYNC = 500` строками, т.е. bounded и дешёвый. Это осознанный компромисс: индекс
обслуживает именно путь монитора, а не общий список сигналов.

## 12. Инцидент 2026-09-24: три strategy_id с одним payload (provenance)

### 12.1 Что произошло

На production три РАЗНЫХ `strategy_id` (V3.0 / V3.3 / V2.8) записали на одном `symbol` и одном
`signal_candle_ts` полностью одинаковый payload: `direction`, `entry_min`, `entry_max`, `stop_loss`,
`targets`. Пример от владельца — BTC/USDT, `signal_candle_ts = 2026-09-24 14:00 UTC`:

| Поле | Значение |
|---|---|
| direction | `LONG` |
| entry_min | `83612.89569417082` |
| entry_max | `83734.64430582919` |
| stop_loss | `83297.56854125623` |
| targets | `{85389.275, 87278.54}` |

Та же картина на SEI, RENDER, NEAR, INJ и, возможно, других символах.

### 12.2 Root cause

**Файл:** `server/services/strategyEngine/strategyEngine.js` → функция `runStrategyScan()`.

`SignalsAuditLedger` — СТАТИЧЕСКИЙ синглтон, такой же как `LiveSignalEngine`
(`src/services/signals/SignalsAuditLedger.ts:201`). Конструктор движка берёт журнал через
`SignalsAuditLedger.getInstance()`, но сам `runStrategyScan` читал `getInstance()` **ПОСЛЕ `await`**
предзагрузки свечей:

```
core.SignalsAuditLedger.resetInstance?.();
core.LiveSignalEngine.resetInstance();     // движок создан → его конструктор взял ledger A
...
await Promise.allSettled(предзагрузка свечей);   // ← здесь скан уступает событийному циклу
const ledger = core.SignalsAuditLedger.getInstance();   // ← прочитан уже ЧУЖОЙ ledger
```

`StrategyScheduler.tick()` запускает стратегии **КОНКУРЕНТНО** (in-flight замок — только на ту же
стратегию), поэтому между этими двумя точками успевали отработать другие сканы, каждый из которых
вызывал `resetInstance()` и создавал свой экземпляр. К моменту возобновления статический журнал
принадлежал движку, созданному **последним**, — все три сканa читали ОДИН и тот же чужой журнал.
`buildSignalRecord()` ставил в строку `strategyId` **вызывающего**, а не автора сетапа, — и один
payload уходил в БД под тремя `strategy_id`. Сетапы двух остальных стратегий при этом терялись:
их журнал никто не читал.

Порядок запуска — `getEnabledStrategies()` → `ORDER BY strategy_id` ⇒ `V2.8, V3.0, V3.3`, то есть
общим обычно становился журнал **V3.3**. Конкретный «победитель» зависит от порядка, в котором сканы
дошли до `getInstance()`, поэтому назвать источник по коду нельзя — только по данным (см. 12.4).

### 12.3 Что исправлено (infrastructure, без математики стратегий)

| Было | Стало |
|---|---|
| движок брался из статического синглтона: `resetInstance()` + `getInstance()` | **свой движок на скан**: `new core.LiveSignalEngine({...})`; глобальный синглтон серверным сканом не трогается вообще |
| `ledger` читается после `await` | `ledger` фиксируется синхронно с созданием движка, до любого `await` |
| параллельные сканы свободно пересекались внутри ядра | **мьютекс критической секции** (`scanMutex.js`): внутри ядра ровно один скан. Предзагрузка свечей вынесена из блокировки, `MarketDataFetcher` дедуплицирует in-flight серии — платим wall-clock, а не запросами к бирже |
| `loadStrategyCore()` присваивал `cached` после `await` — два холодных вызова могли получить РАЗНЫЕ объекты модуля, а значит разные статические синглтоны | single-flight целиком: все сканы гарантированно делят ОДИН объект модуля |
| `buildSignalRecord()` подставляет `strategyId` вызывающего | если `setup.strategyId !== strategyId` — `record: null` + `provenanceMismatch`; relabel запрещён |
| новый сигнал записывался без доказательства происхождения | `provenanceStatus` ставится ДО записи: `VERIFIED` только при совпадении, иначе `UNKNOWN` (fail-closed) |
| расхождение было бы тихим | счётчик `provenanceMismatch` в сводке скана + `console.error` |

**Инвариант:** `published.strategy_id` = `strategyId` сетапа, который её породил; уровни берутся
из raw output ИМЕННО этой стратегии.

Математика V3.0 / V3.3 / V2.8 не тронута: **STRATEGY MATH MODIFIED: NO**.

### 12.4 Кто на самом деле породил payload

Поля `engine_setup_id`, `strategy_version` и `exit_rule` пишутся **из сетапа**
(`buildSignalRecord`: `engineSetupId: setup.id`, `strategyVersion: setup.strategyVersion`,
`exitRule: setup.exitRule`), поэтому они называют истинного автора даже в строке с чужим
`strategy_id`. Отсюда однозначный запрос:

```sql
SELECT strategy_id, split_part(engine_setup_id, '-', 1) AS generated_by, count(*)
  FROM signals
 WHERE engine_setup_id IS NOT NULL
   AND split_part(engine_setup_id, '-', 1) <> strategy_id
 GROUP BY 1, 2;
```

Полный аудит (collision groups + доказанные подмены + проверка цепочки) —
`scripts/sql/signal-provenance-audit.sql`, **только SELECT**.

**Что уже можно сказать по приведённым production-строкам, не заходя в БД.** Восстановление уровней
по формулам даёт: `close = 83673.77`, `ATR(1h) = 608.743058…`, экстремум бара `83388.88`,
подтверждённый 4H swing high `87278.54` и swing low `83500.01`.

* **V2.8 исключён.** Его LIVE-реплей публикует вход как ТОЧКУ (`entryZone: [entryRef, entryRef]` в
  `src/services/signals/live/replays/v28LiveReplay.ts`), то есть `entry_min = entry_max`
  всегда. Наблюдаемая ширина коридора `121.7486…` — это `2 × 0.10 × ATR`, форма V3.x.
  V2.8 не мог породить этот payload.
* **V3.0 воспроизводит строку без единого совпадения.** `stop = экстремум свипа − 0.15·ATR`
  ⇒ `83388.88 − 91.311458… = 83297.5685…` ✓; `TP2` = противоположный подтверждённый 4H-свинг
  `87278.54` ✓; `TP1` = равновесие 4H-диапазона `(87278.54 + 83500.01)/2 = 85389.275` ✓.
  Условие LONG-ловушки тоже выполняется: `low 83388.88 < 83500.01 < close 83673.77`.
* **V3.3 остаётся кандидатом, но требует совпадения.** Его `TP1` — середина displacement-ноги,
  и она должна в точности до третьего знака совпасть с равновесием 4H-диапазона
  (`legLow + legHigh = 170778.55`), а стоп `min(климакс, грань зоны) − 0.15·ATR` — даёт тот же
  `83388.88`. Возможно, но нога размером ≈ 3 900 (≈ 6.4 × ATR(1h)) для входа у минимума нехарактерна.

Итог: **payload, почти наверняка, порождён V3.0**; V3.3 исключается только данными БД
(см. запрос выше). Ни одно утверждение здесь не заменяет прогон SQL на production.

### 12.6 Политика для уже записанных production-сигналов

Все стратегии на production **остаются ВЫКЛЮЧЕНЫМИ**. Ничего не удаляется и не
переписывается: подозрительные строки — доказательство, а не мусор. Хэш-цепочка
не рвалась (это ошибка orchestration, а не правка задним числом), поэтому
`hash` / `outcome_hash` не трогаем.

Ранний выбор владельца (вариант **C**, карантин) реализован миграцией 011 и
процедурой классификации — см. §12.7–§12.9. Варианты A/B остаются как решение
по КАЖДОЙ конкретной строке **после** карантина:

| Вариант | Когда | Что делаем |
|---|---|---|
| **A. Мониторить** | у строки `engine_setup_id` и `strategy_version` СОВПАДАЮТ с её `strategy_id` (статус `VERIFIED`) | сигнал признаётся валидным; монитор сопровождает его как обычно |
| **B. Пометить административно** | подмена доказана (статус `MISMATCH`) | строка остаётся в таблице и исключена из мониторинга и статистики; причина видна в audit-счётчиках. НЕ удаление, НЕ пересчёт хэшей |
| **C. Карантин** | подмена затронула много строк (30 из 45) | применяется по умолчанию миграцией 011: `DEFAULT 'UNKNOWN'` (fail-closed), затем доказательные строки поднимаются до `VERIFIED`, доказанно чужие — в `MISMATCH` |

Реализация карантина — миграция **011** и `scripts/signal-provenance-classify.mjs`.
Она **не выполнена** на production: **PRODUCTION SIGNALS MODIFIED: NO ·
MIGRATION 011 PRODUCTION: NO**.

### 12.7 Карантин provenance (миграция 011)

Аддитивно: `signals.provenance_status TEXT NOT NULL DEFAULT 'UNKNOWN'` с
CHECK-доменом `('VERIFIED','MISMATCH','UNKNOWN')` и индексом под рабочий набор
монитора. Классификатор — префикс `engine_setup_id` (ядро создаёт его как
`${strategyId}-${SYMBOL}-${setupOpenTime}`):

| Префикс `engine_setup_id` | Статус | Смысл |
|---|---|---|
| совпадает с `strategy_id` | `VERIFIED` | запись согласна с генератором |
| есть, но другой | `MISMATCH` | строка перемаркирована, доказательство прямое |
| нет / не читается | `UNKNOWN` | доказательства нет; **никогда** не повышается автоматически |

Границы, которые нарушать нельзя:

* **Без DELETE.** Строки не удаляются никогда.
* **Без перезаписи `strategy_id` и `engine_setup_id`** — это доказательство.
  Процедура пишет РОВНО одну колонку.
* **Без пересчёта хэшей.** `provenance_status` не входит в `hashPayloadV2`,
  поэтому цепочка остаётся валидной до и после карантина (тест:
  `tests/integration/signalProvenanceQuarantine.test.ts`, «хэш-цепочка валидна
  ДО и ПОСЛЕ карантина»).
* **Без правки уровней** (`entry_min/max`, `stop_loss`, `targets`, `tp1/tp2`).

Правила использования строк:

| Потребитель | VERIFIED | MISMATCH | UNKNOWN |
|---|---|---|---|
| Монитор (открытые) | да | **никогда** | нет (fail-closed) |
| Статистика (win rate, R, сравнение) | да | нет | нет |
| Audit-счётчики | да | да | да |

### 12.8 Процедура классификации (на production НЕ запускалась)

`scripts/signal-provenance-classify.mjs`:

| Режим | Что делает |
|---|---|
| без аргументов | **только отчёт**: статусы до, матрица «записано → сгенерировано», план переходов. Ни одной записи |
| `--apply` | `BEGIN` → один `UPDATE` одной колонки → отчёт «после» → `COMMIT`; при ошибке `ROLLBACK` |
| `--json` | машиночитаемый отчёт (для ревью и для CI-проверки) |

Идемпотентна: повторный `--apply` меняет 0 строк (предикат
`provenance_status IS DISTINCT FROM <вычисленное>`). На production-подобном
наборе (45 строк / 15 групп) план обязан быть ровно таким:
`UNKNOWN → VERIFIED: 15`, `UNKNOWN → MISMATCH: 30`, **`UNKNOWN` не повышается
никто, кроме доказанных 15**.

### 12.9 Монитор PR #18 и ТОЧНЫЙ порядок деплоя

Монитор (`server/services/signalMonitor/`, миграция 010) уже в `main`, но
**не задеплоен**. Запускать его поверх непроверенных ACTIVE-сигналов нельзя:
он начал бы сопровождать сетапы, авторство которых не доказано, и записывал бы
их исполнение и исход в строки с чужим `strategy_id`, закрепив ошибку в
`fill_*`, `result_r` и статистике.

**Проверено по реальному коду запуска** (не по предположению):

* `systemd/cryptora.service`: `ExecStart=/usr/local/bin/node /home/user/CRYPTORA/server/index.js`,
  `Restart=always`, `RestartSec=5s`. Никакого отдельного «ключа монитора» нет.
* `server/index.js` → `start()` стартует монитор **автоматически и безусловно**,
  как только доступна БД (`getSignalMonitor().start()`), отдельно от
  планировщика стратегий и НЕЗАВИСИМО от того, включены ли стратегии. Выключенные
  стратегии не создают новых сигналов, но старые открытые строки монитор ведёт.
* `scripts/deploy.sh` делает `npm ci` → `typecheck` → `test` → `build`.
  Он **НЕ** применяет миграции и **НЕ** перезапускает сервис.
* `scripts/restart.sh` перезапускает `cryptora` через systemd; его fallback для
  не-systemd стартует `server/productionServer.js` — legacy static-сервер БЕЗ БД,
  auth и сигналов (см. комментарий в юните). На production путь один: systemd.
* Миграции применяются отдельно: `npm run migrate` (`scripts/migrate.mjs`).

Из этого следуют ТРИ ловушки, которых в наивном порядке нет:

1. **Код раньше миграции** — новый `listOpenSignals` ссылается на
   `provenance_status`, которой ещё нет: монитор падает на первом же тике
   (`column does not exist`), причём на старте процесса.
2. **Классификация раньше кода** — старый код не знает про карантин и отдаст
   монитору ВСЕ 42 открытые строки, включая 30 чужих. Карантин в БД без
   фильтра в коде не защищает.
3. **`git pull` без остановки сервиса** — `Restart=always` держит старый процесс
   со старым кодом; «задеплоили» окажется неправдой.

**Порядок, гарантирующий, что монитор никогда не увидит 30 чужих ACTIVE:**

| Шаг | Команда | Зачем |
|---|---|---|
| **A** | `sudo systemctl stop cryptora` | остановить монитор и планировщик; дальше ничто не трогает строки |
| **B** | `git fetch origin && git checkout <commit этого PR>` | новый код |
| **C** | `npm ci` | зависимости |
| **D** | `npm run migrate` | миграция 011: все 45 унаследованных строк становятся `UNKNOWN` (fail-closed) |
| **E** | `npm run build` | фронтенд (если менялся) |
| **F** | `sudo systemctl start cryptora` | монитор стартует и видит **0** открытых строк: ни одна ещё не `VERIFIED` |
| **G** | `node scripts/signal-provenance-classify.mjs` | ТОЛЬКО отчёт. Сверить: `UNKNOWN 45`, план `→ VERIFIED 15`, `→ MISMATCH 30`. Не сходится — стоп |
| **H** | `node scripts/signal-provenance-classify.mjs --apply` | один UPDATE одной колонки в транзакции |
| **I** | проверка: `GET /api/signals?open=1` → **12** строк, все `provenanceStatus: 'VERIFIED'`; статистика `provenance = { verified: 15, mismatch: 30, unknown: 0 }` | монитор видит только доказанные |

Шаги G–H допустимо поменять местами с F (пока сервис остановлен, монитор не
работает в принципе), но **не с B/E**: классификация до появления кода с
фильтром бессмысленна и опасна (ловушка 2).

Стратегии на всех шагах остаются **OFF**. Включение — отдельное решение
владельца, только после шага I и только если монитор действительно видит 12, а
не 42.
