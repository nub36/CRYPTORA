## 1. Что именно работает в LIVE (v0.8.48)

Три стратегии исследовательского архива запускаются на **фактических закрытых свечах** биржи (Binance / KuCoin через
`LiveMarketDataProvider`) без изменения правил. LIVE-движок — это **детерминированный реплей архивного раннера** на
окне последних закрытых баров, а не отдельная «упрощённая» реализация.

| Стратегия | Что вызывается (frozen, без изменений) | Вход | Вердикт исследования |
|---|---|---|---|
| **V3.0 HTF Liquidation Trap** | `detectTrap` → `buildPending` → `corridorStep` → `manageTrade` (v30Core) | лимитный коридор close ± 0.10 ATR, 3 бара, худшая граница | VALIDATED (3 из 6 символов) |
| **V3.3 HTF Zone Mitigation** | `buildZones` → `trackZone` → `absorption` → коридор → `manageTrade` (v33Core), вариант `while-protective-displacement` | лимитный коридор, 3 бара | TRAIN-ONLY, не валидировано |
| **V2.8 Zero-fee Sniper + Trailing** | `evaluateV2` @4839074 + `extremePoolKind`/`baseSniper` + `resolveEntry`/`executableLadder` + `trackOutcome` (слот) + `simulateTrailing` — через архивную обёртку `v28Live.ts` | OPEN бара N+1 | GROSS-ONLY (fees = 0), при 2/5 bps net-отрицательна |

Файлы: `src/services/signals/live/LiveSignalEngine.ts`, `live/replays/{v30,v33,v28}LiveReplay.ts`, `live/lifecycle.ts`,
`src/services/strategyArchive/definitions/v2_8-zero-fee-sniper-trailing/v28Live.ts`.

### 1.1. Цикл скана
1. Каждые 60 с (первый — через 5 с после старта LIVE-режима) для BTC, ETH, BNB, SOL, XRP, DOGE запрашиваются
   1000 свечей 1h и 4h (+ 400 свечей 1d для V2.8). **Forming-свеча отбрасывается** (`ohlcvToArchive(c, tf, nowMs)`).
2. Сначала ведутся уже опубликованные сетапы (см. §3) — это дёшево и не зависит от появления нового бара.
3. Если закрылся новый 1h-бар — запускаются реплеи трёх стратегий по всему окну; **в журнал публикуются только сетапы
   последнего закрытого бара** (latency 0 баров). Идентификатор `${strategyId}-${SYMBOL}-${setupOpenTime}`
   детерминирован — повторные сканы не создают дублей.
4. Pending, которые раннер отклонил бы на баре исполнения по геометрии (TP1 позади коридора — в исследовании V3.3 таких
   ≈ 51 %), не публикуются, но видны в «Ретроспективе окна» — счётчики сходятся с воронкой исследования.
5. Ошибки провайдера записываются **по инструменту** в `getStatus()` и показываются на странице; сбой одного символа не
   останавливает остальные. Демо-данные в LIVE-путь не подставляются никогда.

### 1.2. Почему сигналов мало
V3.0 в исследовании давала порядка одного сетапа на инструмент в несколько дней; V3.3 после геометрического фильтра —
реже; V2.8 (sniper) — ещё реже на 1h. Пустой журнал сразу после запуска — норма, а не сбой. Диагностика того, что стратегии
действительно считаются на данных, — блок «Покрытие по инструментам» и «Ретроспектива окна» на `/signals`.

## 2. Модель данных журнала (`SignalsAuditLedger`, ключ `cryptora_signals_ledger_v2`)

```typescript
interface AnalyticalSetup {
  id: string;                 // `${strategyId}-${SYMBOL}-${setupOpenTime}`
  strategyId: string;         // V3_0_HTF_LIQUIDATION_TRAP | V3_3_HTF_ZONE_MITIGATION | V2_8_ZERO_FEE_SNIPER_TRAILING
  strategyVersion: string;
  symbol: string;             // BTC/USDT
  direction: 'LONG' | 'SHORT';
  timeframe: '1h';
  setupOpenTime: number;      // openTime закрытого бара сетапа (ms UTC)
  entryType: 'LIMIT_CORRIDOR' | 'MARKET_NEXT_OPEN';
  entryZone: [number, number];
  invalidationLevel: number;  // стоп
  targets: number[];          // TP1, TP2 (V2.8 — лестница frozen-движка, ориентир)
  riskRewardRatio: number;
  confirmingFactors: string[];
  invalidationFactors: string[];
  exitRule: string;
  validForBars: number | null;
  createdAt: string;          // ISO UTC публикации
  latencyBars: number;        // 0
  status: 'ACTIVE' | 'FILLED' | 'TARGET_REACHED' | 'INVALIDATED' | 'CLOSED' | 'EXPIRED' | 'CANCELLED' | 'UNRESOLVED';
  fill?: { price; at; barOpenTime; stop?; targets? };   // исполнение (уровни после сдвига на дельту исполнения)
  closedAt?; exitReason?; exitPrice?; resultR?; netResultR?; pnlResultPct?; barsHeld?;
  prevHash: string;           // 'GENESIS' или auditHash предыдущей записи
  auditHash: string;          // sha256(issuance + prevHash) — фиксируется при публикации
  outcomeHash?: string;       // sha256(outcome) — фиксируется один раз при исходе
}
```

## 3. Жизненный цикл опубликованного сетапа (`live/lifecycle.ts`)

Исход считается по **опубликованным (уже захэшированным) уровням**, а не повторным прогоном стратегии, теми же
frozen-функциями архива:

- **V3.0 / V3.3 (LIMIT_CORRIDOR):** `corridorStep` на барах N+1…N+3 (исполнение по худшей границе, отмена при касании
  стопа, `REJECTED_GEOMETRY`, истечение) → `manageTrade` соответствующей версии (стоп раньше целей, TP1 → 50 % и BE со
  следующего бара, TP2, таймаут 50 / 48 баров).
- **V2.8 (MARKET_NEXT_OPEN):** `v28EntryAtNextOpen` (OPEN N+1, сдвиг стопа/целей на дельту исполнения, `executableLadder`,
  rr1 ≥ min_rr) → `v28TrailOutcome` (Trail V2.5: BE при MFE ≥ 1R, трейлинг 1R шагом 0.25R, таймаут 10 баров).

Статусы: `ACTIVE → FILLED → TARGET_REACHED | INVALIDATED | CLOSED` (сделка была) или `ACTIVE → EXPIRED | CANCELLED`
(сделки не было). `UNRESOLVED` — бар сетапа вышел за окно данных до исхода (честно помечается, не считается сделкой).

## 4. Принцип неизменяемости (Immutable History)

1. **Никакого переписывания задним числом:** публикация хэшируется цепочкой в момент закрытия бара; `verifyIntegrity()`
   ломается при любом изменении уровней или исхода. Метод `expireStale()` прежних версий удалён — он переписывал записи.
2. **Неудачные сигналы сохраняются навсегда:** удаление или редактирование записей API не предусмотрено.
3. **Честная статистика:** «Доля сделок с R > 0» считается только по сделкам с исходом; отмены/истечения — отдельно;
   net R учитывает комиссии 2/5 bps (maker вход / taker выход).

## 5. Отсутствие автоматического исполнения (No Auto-Execution)

- Сетапы — структурированные наблюдения для человека. Платформа **не отправляет ордера** и не хранит торговые ключи.
- Любое торговое решение принимается пользователем самостоятельно на внешних площадках.

## 6. Ограничения и честные оговорки

- Журнал страницы `/signals` хранится в **localStorage браузера** — другой браузер = другой журнал, а закрытая вкладка
  останавливает ведение сетапов (журнал ограничен 500 записями и продвигается только пока вкладка видима). Отдельно
  существует **серверный** журнал — таблица `signals` в PostgreSQL, которую ведёт серверный движок независимо от
  браузера (см. §8). Это два журнала ОДНОГО ядра: они расходятся по охвату окна и по моменту публикации, поэтому
  числа на странице и в `GET /api/signals` могут отличаться.
- LIVE-эмиссия в песочнице сборки не воспроизводима (нет доступа к биржам); проверено паритетом реплеев с архивными
  раннерами и сквозным тестом на mock-«бирже» (`tests/unit/signals/*`).
- V2.8 в LIVE — только 1h-подмножество исследования (15m/30m/4h не сканируются); все цифры V2.8 — GROSS.
- Окно данных конечно (≤ 1000 баров 1h): зоны V3.3, известные до начала окна, отбрасываются правилом прогрева (как
  `zonesSkippedByWarmup` в источнике), поэтому первые сканы после старта могут пропустить сетапы по очень старым зонам.
- **Зона V3.3, образованная последним закрытым 4h-баром, появляется только после закрытия следующего 4h-бара.**
  `buildZones` (`v33Core.ts`) требует бар `i+1` для проверки FVG, поэтому на момент скана самая свежая зона видна
  с задержкой до 4 часов. То же поведение у архивного раннера (`v33Runner.ts`), то есть это свойство замороженной
  стратегии, а не расхождение LIVE: за счёт новой зоны candidate-selection (Amendment-1, «сначала новая зона») при
  скане может выбрать более старую зону → stop/TP1 отличаются от ретроспективного прогона по всей истории.
  Практический вывод: уровни в журнале — уровни **на момент скана**, задним числом они не «переписываются».
- Резервный источник KuCoin (при недоступном Binance) теперь запрашивается явным окном `startAt`/`endAt`
  (`FetchCandles` + `TIMEFRAME_MS`, v0.8.46): без окна биржа отдаёт свою страницу по умолчанию. Если глубина всё же
  меньше запрошенной, провайдер пишет `console.warn`, а движок отчитывается о нехватке истории вместо тишины.
- Источник свечей виден в статусе: `SymbolScanStatus.source` = провенанс последней свечи окна (`binance` /
  `kucoin (резерв)`, v0.8.47). В журнал по-прежнему попадают только сетапы стратегий — провенанс не влияет на уровни.
- **Журнал аудита принимает только фактические сетапы** (v0.8.48): если провайдер отдаёт QA-фикстуру
  (`provider.isDemo`), движок считает стратегии для диагностики, но ничего не публикует, а `/signals` предупреждает об
  этом. QA-данные не могут попасть в журнал рядом с реальными сделками.

## 7. Валидация на реальных данных (офлайн-протокол)

Песочница сборки не имеет доступа к биржам, поэтому LIVE-путь проверялся на **закреплённом историческом датасете**
Binance spot (`c3c1dce`, месячные ZIP, 2022-01 → 2025-12-31, 6 пар: BTC/ETH/BNB/SOL/XRP/DOGE) через **те же**
LIVE-реплеи (`runV30LiveReplay`, `runV33LiveReplay`, `runV28LiveReplay`), которые вызывает `LiveSignalEngine`.
Датасет лежит вне репозитория (≈17 МБ), поэтому постоянных тестов на нём нет — протокол воспроизводится вручную.

### 7.1. Что подтверждено

| Проверка | Результат |
| --- | --- |
| Прогон полной истории (V3.0 / V3.3, 6 пар) | Сетапы есть: V3.0 ≈540–600 записей на пару за 4 года, V3.3 ≈4.2–4.9 тыс. записей |
| Q4-2025, публикуемые V3.0 | BTC 23, ETH 30, BNB 40, SOL 32, XRP 36, DOGE 33 |
| Q4-2025, публикуемые V3.3 | BTC 110, ETH 124, BNB 99, SOL 115, XRP 127, DOGE 93 |
| Прогон **через сам движок** (241 скан, 10 суток скользящего окна ≤1000 баров) | 121 опубликованный сетап; ledger: 96 закрытых сделок, accuracy 86.5 %, avg RR 3.38, Σ net R +50.30 |
| Сверка журнала движка с полным реплеем | 50/50 сетапов совпали по времени/направлению/входу; V3.0 `runV30Series` vs журнал — 0 расхождений в обе стороны |
| V2.8, полная 1h-история (4 года, 6 пар) | 65 сетапов всего (≈1 на пару в 3–5 месяцев), все исполнимы |
| V2.8, скользящее окно 1000 баров | ни один сетап полной истории не потерян (0 missing); 31 из 65 отличаются на один тик по входу/стопу (квантование коридора, ATR считается от начала ряда) |

### 7.2. Почему V2.8 молчит в коротком окне

Sniper-фильтр V2.8 очень строгий: из ≈1150–1250 actionable-сетапов движка V2 на пару за 4 года публикуются лишь
10–14. В окне 10 суток (240 баров) математическое ожидание числа сетапов ≈0.05 на пару — тишина ожидаема.
Утверждение «V2.8 ничего не публикует» корректно формулировать так: **стратегия редкая**, а не «сломана»;
подтверждение работоспособности — те 65 реальных сетапов плюс паритетный тест `v28Live.test.ts`.

### 7.3. Что из этого следует для продукта

- Три стратегии действительно считаются на фактических свечах и публикуют сетапы; заглушек в LIVE-пути нет.
- Уровни V3.3 в журнале — «как на момент скана» (см. §6), включая задержку зоны до одного 4h-бара.
- Числа §7.1 — исторический факт на закреплённом датасете, **не прогноз**; CRYPTORA не исполняет сделки.

## 8. Серверный конвейер сигналов (PostgreSQL + `GET /api/signals`)

Серверный путь существует с интеграции серверного слоя стратегий (миграции 006/007) и приведён в рабочее состояние
в задаче «signal pipeline foundation» (миграция 009). Он НЕ заменяет LIVE-движок браузера и не содержит собственной
математики: сервер исполняет то же замороженное ядро, собранное esbuild из `src/`.

### 8.1. Путь данных

```
Binance REST (публичные klines)
   └─ MarketDataFetcher (кэш TTL, дедуп in-flight, нормализация символа/таймфрейма, лимит ядра)
        └─ LiveSignalEngine.scanNow()          ← ТОТ ЖЕ код, что и в браузере
             ├─ SignalsAuditLedger (сетапы последнего закрытого бара)
             └─ getRetrospective() (fill/outcome по закрытым свечам окна)
                  └─ signalRepository (hash-цепочка v2, дедуп по UNIQUE из 007)
                       └─ PostgreSQL: signals (007 + 009)
                            └─ GET /api/signals (публичное чтение, newest-first, ограничено)
```

Расписанием владеет `StrategyScheduler` (`server/services/strategyEngine/strategyScheduler.js`): он читает
`strategy_settings` перед каждым циклом и вызывает `scanStrategySafely()` только для включённых стратегий. Ядро
сканируется одним проходом (`scanNow()`), без внутренних интервалов.

### 8.2. Что хранится (миграции 007 + 009)

| Группа | Колонки | Источник значения |
|---|---|---|
| Идентичность | `strategy_id`, `strategy_version`, `engine_setup_id`, `symbol` (пара `BTC/USDT`), `timeframe`, `signal_candle_ts` | `SetupIssuance` ядра; `signal_candle_ts` = `setupOpenTime` закрытого бара |
| Уровни публикации | `entry_min`, `entry_max`, `stop_loss`, `targets` (NUMERIC[] — вся лестница TP1..TPn), `tp1`, `tp2` (первые два элемента, для совместимости с 007) | `entryZone`, `invalidationLevel`, `targets` |
| Контекст | `entry_type` (`LIMIT_CORRIDOR` \| `MARKET_NEXT_OPEN`), `valid_for_bars`, `exit_rule`, `metadata` (RR, факторы, latency, engineVersion) | `SetupIssuance` |
| Исполнение | `fill_price`, `filled_at`, `fill_stop`, `fill_targets` | `ReplayRecord.fill` (V2.8 сдвигает стоп/цели на дельту исполнения) |
| Исход | `status`, `closed_at`, `close_price`, `close_reason`, `result_r`, `net_result_r`, `pnl_result_pct`, `bars_held` | `ReplayRecord.outcome` |
| Целостность | `hash`, `previous_hash`, `outcome_hash`, `chain_version` | см. §4 и §8.3 |

**Миграция 010 (`010_signal_monitor_bookkeeping`, аддитивная):** колонки учёта монитора открытых сигналов
(`monitor_check_count`, `monitor_last_check_at`, `monitor_last_result`, `monitor_last_error`) и таблица
`signal_monitor_state` (одна строка на открытую группу `symbol+timeframe`, обслуживающая индекс
`idx_signals_open_group`). Миграция 009 **не переписана**: 010 добавлена отдельным файлом, только `ADD COLUMN` /
`CREATE TABLE` / `CREATE INDEX` без потери данных, применяется обычным раннером (без
`CREATE INDEX CONCURRENTLY`, который невозможен внутри одной транзакции `scripts/migrate.mjs`).

Ключ дедупликации — `UNIQUE (strategy_id, symbol, timeframe, signal_candle_ts)` из 007. Поскольку
`signal_candle_ts` = `setupOpenTime`, повторный скан того же закрытого бара и рестарт процесса не создают дублей, а
новый закрытый бар с новым сетапом — создаёт новую строку.

`tp1`/`tp2` — производные от `targets` (`resolveLevels()` в `signalRepository`), а не второй источник истины: движок
их не заполняет, их выводит репозиторий. Строки, записанные до 009 (только `tp1`/`tp2`), при чтении получают
лестницу из этих двух уровней.

### 8.3. Жизненный цикл: состояние сетапа и исход сделки

Домен `status` (009) = `SetupStatus` ядра, разделённый на две группы:

```
A) состояние сетапа:   ACTIVE  ──(коридор исполнен)──▶  FILLED
B) исход:              TARGET_REACHED | INVALIDATED | CLOSED      ← сделка была, есть R
                       EXPIRED | CANCELLED | UNRESOLVED           ← сделки не было, R = null
```

Правила переноса (и что здесь НЕ делается):

* значения берутся из `ReplayRecord.fill` / `ReplayRecord.outcome` **как есть** — сервер не пересчитывает ни уровни,
  ни R, ни причину выхода;
* если ядро исход не определило (`outcome = null`), статус не меняется: «ещё не известно» не превращается в «закрыто»;
* переход монотонен: закрытая строка больше не изменяется (`ALREADY_CLOSED`);
* строка, которой нет в БД (стратегия была выключена, когда сетап сформировался), не выдумывается — в сводке скана
  это `lifecycle.notFound`;
* `closed_at` — время ЗАКРЫТИЯ бара исхода (`barOpenTime` ядра + длительность бара). Если ядро время не отдало,
  сохраняется `null`, а не «сейчас»: выдуманное время попало бы в `outcome_hash`.

Целостность: `chain_version = 2` (строки после 009) означает, что `hash`/`previous_hash` считаются только по
неизменяемой части публикации, а изменяемый исход хэшируется отдельно в `outcome_hash`. Строки формы 007
(`chain_version = 1`) продолжают проверяться своей формой payload'а. `verifyChain()` возвращает ровно
`{ rows, breaks }` для обеих форм. Это сознательное расхождение с браузерным журналом, где `auditHash` считается по
issuance, а `outcomeHash` — по исходу: сервер дополнительно хэширует исход при КАЖДОМ переходе, включая `FILLED`.

### 8.4. R в CRYPTORA: что это, кто считает, что нужно для пересчёта

**R — результат сделки в единицах первоначального риска**, а не процент и не «профит-фактор».

| Величина | Формула (frozen-ядро) | Где живёт |
|---|---|---|
| `grossR` (`result_r`) | signed: `(exit − entry) / (entry − stop)` для LONG и зеркально для SHORT; для TARGET_REACHED — по фактической цене выхода | `src/services/signals/live/lifecycle.ts` (`manageTrade` → `r.grossR`), агрегация окна — `ReplaySummary` |
| `netResultR` | `grossR − feeR(makerBps, takerBps)`, где комиссия выражена в R: 2 bps на вход (maker) и 5 bps на выход (taker); константы — `V30_CONSTANTS` / `V33_CONSTANTS` | там же (`lifecycle.ts:110-119`) |
| `pnlResultPct` | `pnlPct(direction, entry, exit)` — процент от цены входа (gross) | там же |
| ΣR / «доля R > 0» | сумма и доля по сделкам с исходом: `TRADE_CLOSED_STATUSES` = TARGET_REACHED + INVALIDATED + CLOSED; отмены/истечения в знаменатель не входят | `ReplaySummary.{grossRSum, netRSum, positiveR, negativeR}`, `strategyArchive/engine/rMetrics.ts` |

Входы для пересчёта: закрытые свечи окна (1h исполнение + 4h/1d контекст), уровни публикации, факт и цена
исполнения, правило выхода стратегии. Ничего из этого сервер не хранит «про запас» и не восстанавливает по-своему:
R приходит готовым из реплея и записывается в `result_r` / `net_result_r`.

Оговорки, которые обязаны быть видны пользователю:

* **V2.8 исследована при нулевых комиссиях** (`fees = 0`), поэтому её net R при модели 2/5 bps отрицателен. Это
  свойство стратегии (GROSS-ONLY), а не ошибка хранения или транспортировки;
* **R существует только у сделок**: у `EXPIRED` / `CANCELLED` / `UNRESOLVED` он `null`, и «0» здесь недопустимо
  (0 ≠ «нет данных»);
* **отрицательный net R ≠ ошибка**: `INVALIDATED` даёт ≈ −1 R по построению;
* **UI показывает серверные `result_r` / `net_result_r`** (`GET /api/signals` → карточка сигнала и панель
  статистики). Браузерный журнал (`SignalsAuditLedger`) остаётся отдельным источником только в сворачиваемом
  блоке «Статистика и аудит» и **не смешивается** с серверными агрегатами. Формат R единый
  (`formatSignedR`, «+1.67 R»), на клиенте R не пересчитывается.

### 8.5. Контракт `GET /api/signals`

```
GET /api/signals?symbol=&strategy=&status=&open=&direction=&limit=&offset=
```

* **Фильтры:** `symbol` (принимаются `BTC/USDT`, `BTCUSDT`, `BTC` → нормализуется к `BTC/USDT`), `strategy`
  (только известные id, иначе `400 INVALID_STRATEGY` — молча пустой список не отдаётся), `status` (одно из восьми
  состояний), `open=true|false` (открытые = ACTIVE+FILLED / терминальные), `direction=LONG|SHORT`;
* **Пагинация:** `limit` 1..200 (по умолчанию 50), `offset` 0..5000; выход за границы — `400`, а не тихая обрезка;
* **Порядок:** детерминированный, новые сверху — `created_at DESC, id DESC` (`ordering` в ответе);
* **Ответ:** `signals`, `count` (страница), `total` (всего под фильтром), `limit`, `offset`, `maxLimit`,
  `appliedFilters` (что реально применено), `statuses` и `openStatuses` (домен состояний — UI не должен хардкодить),
  `source: "server"`;
* **Уровни:** только посчитанные стратегией — `entryMin`/`entryMax`, `stopLoss`, `targets` (вся лестница),
  после исполнения — `fillPrice`/`fillStop`/`fillTargets`. Досчитывать цели на клиенте запрещено.

Индекс `idx_signals_symbol_status_created` (009) обслуживает горячий путь будущего UI: выбранный инструмент +
ограниченная лента последних сигналов с фильтром по состоянию.

### 8.5.1. Контракты `GET /api/signals/statistics` и `GET /api/signals/monitor`

```
GET /api/signals/statistics?period=all|24h|7d|30d|90d&strategy=&symbol=
GET /api/signals/monitor
```

* **`/statistics`** — агрегаты по PostgreSQL (`server/services/signalStatistics.js`), НЕ по браузерному журналу:
  `published`, `waitingEntry`, `filled`, `completed`, `cancelled`, `expired`, `unresolved`, `targetReached`,
  `invalidated`, `closed`, `wins`, `losses`, `winRatePct`, `avgGrossR`, `avgNetR`, `grossRSum`, `netRSum`,
  `fillRatePct`, `completionRatePct` + разрезы `byStrategy` / `bySymbol` + `definitions` (человеческие пояснения
  метрик). Доля успешных считается только по сделкам (`TRADE_CLOSED_STATUSES`): сигнал, не дождавшийся входа, в
  знаменатель не попадает. `null` означает «нет данных» и обязан отображаться как «—», а не «0 %».
* **`/monitor`** — телеметрия серверного монитора открытых сигналов: `running`, `cycles`, `inFlight`,
  `lastTickStartedAt`/`lastTickFinishedAt`/`lastTickDurationMs`, `lastError`, `consecutiveFailures`, `stale`,
  `lastSummary`. Эндпоинт **только читает**: ни один пользовательский маршрут не меняет состояние стратегий.

### 8.6. Что серверный путь НЕ делает

* не исполняет ордера, не хранит торговые ключи (§5);
* мониторит открытые сигналы **не в реальном времени внутри бара**, а по факту закрытия свечи: см. §9;
* не синхронизируется с журналом браузера и не «чинит» его;
* не включает стратегии: после миграций все три выключены, включение — действие администратора
  (`PATCH /api/admin/strategies/:id`).

### 8.8. Пользовательский интерфейс (Signals V2)

Страница `/signals` переведена с браузерного журнала на серверную ленту `GET /api/signals`
(задача 9.3, дизайн — `docs/agent-plan/SIGNALS_V2_HANDOFF.md`). Главный принцип сохраняется:
**показывается только то, что посчитало ядро и сохранил сервер** — ни один уровень, статус, R или время
не досчитывается на клиенте.

**Компоненты и порядок на мобильном** (`src/pages/SignalsPage.tsx`):

| Блок | Компонент | Источник |
|---|---|---|
| Селектор монеты (+ чипы монет с сигналами) | `SignalsCoinSelector` | полный активный Spot-universe (`SymbolPickerModal`, лениво, кэш) — **не** админ-вселенная скана; чипы — `distinct` по загруженной ленте |
| Сводка последнего/выбранного сигнала | `SignalSummaryCard` | `signals[0]` / выбранный сигнал |
| Свечной график выбранного инструмента | `SignalChartCard` → общий `CandleChart` | свечи — только выбранный символ и таймфрейм (`useSignalChartCandles`), маркеры — сохранённые сигналы, линии — уровни выбранного сигнала |
| Уровни выбранного сигнала + детали | `SignalDetailsPanel` | `entryMin/entryMax/stopLoss/targets[]` (+ `fill*` после исполнения), исход, R, аналитика, целостность |
| История сигналов монеты | `SignalHistoryList` | та же лента `GET /api/signals?symbol=…`, постранично (`limit`/`offset`) |
| Статистика и аудит | `SignalsLedgerAuditSection` | серверная лента и браузерный журнал — **отдельно**, не смешиваются |

**График.** `CandleChart` расширен аддитивными пропсами `markers` / `levelLines` / `onMarkerClick`
(`src/types/chart.ts` — библиотечно-независимые типы). Существующие потребители (/coin, /overview) их не
передают и ведут себя как раньше. Линии уровней заменяются по `id`: выбор другого сигнала переключает линии,
смешать уровни двух сигналов нельзя. Маркер встаёт только на бар, реально присутствующий в загруженных свечах;
сторона читается без цвета (форма `arrowUp`/`arrowDown`, позиция и текст «LONG · V3.0»).

**Отображение.** `src/services/signals/ui/signalUiModel.ts` — единственная точка `SignalDto` → модель UI
(произвольная длина `targets[]`, отсутствующие поля, неизвестный статус); `signalChartProjection.ts` — маркеры
и линии; `src/utils/serverSignalText.ts` — человеческий словарь (статусы, направление, «Цель N», пояснение R).
Таймфрейм сигнала (исполнения, у всех трёх стратегий `1h`; V2.8 — не «15m») отделён от таймфрейма графика,
рассогласование помечается.

**Гонки и бюджет запросов.** Смена монеты/таймфрейма отменяет устаревшие запросы (`AbortController` +
монотонный номер запроса в `useServerSignals` / `useSignalChartCandles`). Свечи запрашиваются только для
выбранного символа и таймфрейма — веера `universe.map(fetchCandles)` нет: открытие экрана не грузит свечи,
выбор монеты — один запрос свечей, переключение таймфрейма — один запрос того же символа.

**Статусы.** Отображается только достоверный серверный статус; фронтенд не определяет «цель достигнута /
стоп сработал / позиция закрыта» по текущей цене. Рядом со статусом — подсказка «Статус отражает последнее
состояние, зафиксированное сервером по закрытым свечам». Неизвестный серверу статус показывается как есть,
не подменяется нейтральным словом.

**Часовой пояс.** `src/utils/timePresentation.ts` — ЕДИНСТВЕННЫЙ форматтер времени в продукте: оси графиков,
перекрестие, бейджи свежести, время сигнала и время исхода зовут его. Источник зоны —
`Intl.DateTimeFormat().resolvedOptions().timeZone` (пояс ОС/браузера), поэтому Asia/Tokyo, Europe/Berlin с
переходом на летнее время и любой другой пояс отображаются корректно без правок кода. В базе и API время
остается UTC/ISO. Режим `mode: 'UTC'` сохранен только для отладки и печати. Захардкоженных UTC+3 / Europe/Moscow
в презентационной логике нет — это проверяется тестом, сканирующим исходники.

**Статус сканирования (BUG C).** Прежняя плашка читала состояние браузерного движка
(`LiveSignalEngine.getStatus()`) и показывала «LIVE-скан · каждые 60с» при выключенных стратегиях. Теперь
источник один — серверный `/api/strategies` (`useServerScanner`, опрос 15 с, пауза при скрытой вкладке):

| Состояние сервера | Что показывает плашка |
|---|---|
| 0 включенных стратегий | «Сканирование сигналов выключено» (+ пояснение, что сохраненные сигналы продолжают отслеживаться) |
| N включенных | «Сканирование включено: N стратегий · каждые Xс» — X из `scanIntervalSeconds`, а не константа UI |
| стратегия в ERROR | отдельная строка с текстом ошибки сканирования, не подмененная словом «выключено» |
| запрос состояния упал | «Статус сканирования недоступен»: отсутствие ответа сервера не есть доказательство выключенного сканера |

Плашка ничего не переключает: пользовательского эндпоинта, меняющего состояние стратегий, нет.

**Пустые и ошибочные состояния (BUG B).** Раньше на экране было ДВА разных блока про «нет сигналов»
(страничный и внутри `SignalSummaryCard`). Теперь блок один — `signals-empty[data-state]` с явной причиной:
`scanner-off` (сервер не публикует), `empty` (лента загрузилась и пуста), `error` (`/api/signals` упал),
`market-error` (свечи недоступны). Ни одна причина не маскируется под другую.

**Авто-обновление.** Лента сигналов опрашивается с интервалом 60 с, статус сканера — 15 с, статистика — 60 с
(`useAutoRefresh`: ограниченный polling, пауза при скрытой вкладке, отмена устаревших запросов). Серверный
монитор (§9) пишет исход в PostgreSQL независимо от открытой вкладки, поэтому статус сигнала меняется на
экране сам — без перезагрузки страницы. Это проверено в `e2e/signalsV2.spec.ts` сценарием P.

**Серверная статистика.** `SignalStatisticsPanel` показывает агрегаты `GET /api/signals/statistics` (PostgreSQL),
а не браузерный `SignalsAuditLedger`. Первый экран — человеческие счетчики (опубликовано, ожидают входа,
дождались входа, завершились сделкой, прибыльных/убыточных, доля успешных); производные метрики (gross R,
net R, суммы R, разрезы по стратегии и инструменту) — под «Подробнее». Браузерный журнал остался отдельным
сворачиваемым блоком «Статистика и аудит» и с серверными агрегатами не смешивается.

**Ограничения (остаток).** Статус может отставать на бар: исход определяется по закрытым свечам окна
(<= 1000 баров 1h), это «последнее зафиксированное сервером состояние», а не «прямо сейчас». Сигналы старше
окна реплея могут оставаться `ACTIVE`/`FILLED` до тех пор, пока не попадут в окно (§9). Серверный перенос
браузерного журнала — отдельная задача.

### 8.9. Browser E2E: сценарии `/signals` (реальный Chromium)

`e2e/signalsV2.spec.ts` подменяет ТОЛЬКО сетевую границу (`page.route`); продуктовый код не трогается.

| Сценарий | Что проверяется |
|---|---|
| A | структура V2, сводка LONG, `targets[3]` дает «Цель 1/2/3», история из 3 строк |

| B/D/J | переключение таймфреймов без ошибок страницы и без «прилипания» старого |
| K | поиск селектора: `B`→BTC/BNB, `BT`→BTC, `BTC/USDT`→BTC, `btc`, backspace, `1000SHIB`, `PEPE`, честное «ничего не найдено» |

| M | на графиках нет метки LOCAL и нет тумблера зоны; подпись — настоящий IANA-пояс |
| N1/N2 | эмуляция Asia/Tokyo и Europe/Berlin: время сигнала выводится в поясе браузера, DST учитывается |
| O1/O2 | серверная статистика: фактические счетчики и R; падение агрегатов не выдается за «сигналов нет» |
| P | лента обновляется сама (опрос 60 с): статус `ACTIVE`→`FILLED` без перезагрузки страницы |

## 9. Серверный монитор открытых сигналов (realtime)

До монитора исход сигнала определялся только реплеем окна скана: страница показывала статус «по данным
последнего закрытого бара», а сигнал, не дождавшийся входа, мог годами висеть `ACTIVE`, если стратегия была
выключена или окно реплея не покрывало момент.

**Архитектура.** `server/services/signalMonitor/signalMonitor.js` + `signalTradeManager.js`:

```
StrategyScheduler (независимо) ──▶ getSignalMonitor().tick()   MONITOR_TICK_MS = 30 с
                                     ├─ SELECT открытые сигналы (ACTIVE|FILLED), бюджет <= 500 / цикл
                                     ├─ группировка по symbol+timeframe (<= 64 групп, конкуррентность <= 4)
                                     ├─ MarketDataFetcher: lookback = минимум(1000 баров 1h, окно сигнала)
                                     └─ trackPublishedSetup()  ← ЗАМОРОЖЕННЫЙ trade-management, без изменений
                                          └─ closeSignal(...) → PostgreSQL (монотонный переход, outcome_hash)
```

**Свойства, которые обязаны сохраняться:**

* **Независимость от браузера.** Монитор живет в процессе сервера; закрытая вкладка не влияет на учет.
* **Переживание рестарта.** Состояние цикла — в `signal_monitor_state` (010), счетчики проверок — в колонках
  `signals.monitor_*`. После перезапуска процесс продолжает с того же места, строки не дублируются.
* **Переживание отказа рынка.** Ошибка рыночных данных не роняет тик и не переводит сигнал в терминальное
  состояние: группа помечается `ERROR`, сигнал остается открытым, следующий тик повторяет попытку. После
  `MONITOR_STALE_AFTER_FAILURES` подряд статус монитора помечается `stale` — UI обязан показать это честно.
* **Паритет с ядром.** `signalTradeManager` — адаптер вокруг замороженного `trackPublishedSetup()`
  (`src/services/signals/live/lifecycle.ts`): семантика закрытого бара, `CORRIDOR_EXPIRY_BARS = 3`,
  `TIMEOUT_BARS = 50`, комиссии 2 bps maker / 5 bps taker, приоритет стопа при касании TP и стопа на одном
  баре, LONG fill = `min(open, zoneHigh)`, SHORT fill = `max(open, zoneLow)` — все как в ядре. Любое расхождение
  ловит `tests/unit/signalMonitorParity.test.ts`.
* **Бюджет запросов.** Нет fan-out'а: на группу (символ+таймфрейм) — один запрос свечей за тик, число групп и
  число сигналов ограничены константами. Вселенная из сотен инструментов не превращается в сотни запросов,
  потому что в группу идут только ОТКРЫТЫЕ сигналы.

**Чего монитор не делает:** не исполняет ордера, не считает новых сетапов (это задача `StrategyScheduler` +
`scanNow()`), не переписывает терминальные строки, не подменяет `closed_at` текущим временем, если ядро время
не отдало.
