## 1. Вывод исследования: ДА, изолировать V3.4 можно

Изоляция возможна **без единого изменения в математике и путях V3.0/V3.3**, потому что
развилка по стратегии уже существует ровно в одной точке — `trackPublishedSetup`
(`src/services/signals/live/lifecycle.ts`). Она единственная решает, как опубликованный
сетап переходит из «опубликован» в «исполнен/не состоялся», и её вызывают ВСЕ потребители:

| потребитель | вызов | назначение |
|---|---|---|
| браузерный движок | `LiveSignalEngine.trackOpenSetups` → `trackPublishedSetup(entry, h1)` | журнал аудита во вкладке |
| серверный монитор позиций | `signalMonitor.js:526` → `core.trackPublishedSetup(entry, candles)` | ведение строк БД, пока браузер закрыт |
| ре-экспорт для сервера | `server/services/strategyEngine/entry.ts:27` | связывает ядро и сервер |

Ветка по `strategyId` внутри этой функции затрагивает только V3.4: V3.0/V3.3 идут прежним
путём `trackCorridor` → `corridorStep`, тот же код, те же константы, тот же результат.
Это подтверждено тестом равенства объектов результата (блок 13).

**Единственное исключение из «одной точки»** — серверный сканер: `syncLifecycleFromCore`
(`server/services/strategyEngine/strategyEngine.js`) пишет в БД `rec.fill`/`rec.outcome`
прямо из ретроспективы реплея, минуя `trackPublishedSetup`. Для V3.4 это придётся
отключить, иначе часовой фил реплея будет продолжать перезаписывать минутный вход.
Это часть подключения (раздел 5), а не ядра.

## 2. Источник минутных данных: новой инфраструктуры НЕ требуется

| факт | где проверено |
|---|---|
| `'1m'` уже есть в маппинге интервалов Binance | `marketDataFetcher.js`, `BINANCE_INTERVAL_BY_TIMEFRAME` |
| фетчер общий, с TTL-кэшем и дедупликацией in-flight | `MarketDataFetcher.getCandles` |
| граница финальности свечи соблюдается для любого интервала | `isClosed = closeTime < nowMs` (`ohlcvAdapter.ts:27`) |
| окно входа = 4 часа = 240 минут ≤ лимита Binance (1000) | `BINANCE_MAX_KLINES` |
| TTL для `'1m'` не задан → берётся `DEFAULT_CACHE_TTL_MS` = 60 000 мс | `CACHE_TTL_MS`, `marketDataFetcher.js:196` |

То есть достаточно попросить у уже существующего фетчера ещё одну серию. Никаких вебсокетов,
никакого нового транспорта, никакого хранения тиков. Единственное, что стоит подправить при
подключении, — TTL для `'1m'` (60 с равен периоду свечи; для минутного мониторинга разумнее
меньше), это одна строка в таблице TTL.

**Стоимость запросов.** Монитор группирует открытые сигналы по (символ, таймфрейм), поэтому
это +1 запрос на символ за тик (30 с), а не на сигнал. Вес запроса klines с `limit ≤ 500` = 2.
При шести символах это 12 единиц веса за тик при лимите Binance 6000/мин — запас ~стократный.

## 3. Что реализовано в этом коммите

### `src/services/signals/live/v34EntryLifecycle.ts` (новый, чистый модуль)

Состояния: `WAITING_FOR_ENTRY → FILLED → (TP1/TP2/SL)`, плюс терминальные без сделки
`INVALIDATED`, `MISSED`, `EXPIRED`.

**ENTRY_ELIGIBLE_FROM** = `max(setupOpenTime + 1ч, publishedAt)`.
Первое слагаемое запрещает бару-триггеру исполнить самого себя, второе — исполнение до
публикации. Минута учитывается по `openTime`: минута, начавшаяся раньше этого момента,
отбрасывается целиком, а не «частично», потому что она содержит движение, которого
подписчик не мог использовать.

**Окно жизни** = `setupOpenTime + (CORRIDOR_EXPIRY_BARS + 1)·1ч`, то есть ровно те же
3 бара исполнения, что у V3.3. Срок жизни публикации не менялся.

**Условие касания** — как задано: `candle.high >= zoneLow && candle.low <= zoneHigh`.

**Порядок проверок внутри одной минуты** (внутриминутная последовательность неизвестна,
сомнение трактуется против сделки):

1. стоп задет → `INVALIDATED`, даже если та же минута задела зону
   (та же конвенция, что в замороженном `corridorStep`: `touches && hitStop → CANCELLED`);
2. зона задета → `FILLED`;
3. TP1 достигнут → `MISSED`.

**Цена исполнения** — детерминированная функция ОДНОЙ свечи:
`LONG: min(open, zoneHigh)`, `SHORT: max(open, zoneLow)`. Это та же формула, что уже
заморожена в `corridorStep`, поэтому конвенция «вход = открытие, ограниченное худшей
гранью» в системе остаётся одна. Разбор случаев (LONG, SHORT зеркально):

| случай | условие | цена входа |
|---|---|---|
| открытие внутри зоны (в т.ч. гэп внутрь) | `zoneLow ≤ open ≤ zoneHigh` | `open` |
| открытие выше зоны, свеча опускается в неё | `open > zoneHigh`, `low ≤ zoneHigh` | `zoneHigh` |
| гэп ниже зоны с возвратом в неё | `open < zoneLow`, `high ≥ zoneLow` | `open` |
| свеча пересекла зону насквозь снизу вверх | `open < zoneLow`, `high > zoneHigh` | `open` |
| свеча накрыла зону сверху вниз | `open > zoneHigh`, `low < zoneLow` | `zoneHigh` |

Будущее не используется: берутся только `open` той же свечи и опубликованные границы.
Брать `low` (самую выгодную точку свечи) было бы заглядыванием внутрь бара.

**Граничный случай, который надо знать.** Свеча, целиком лежащая ЗА зоной с выгодной
стороны (LONG: `high < zoneLow`), по заданному условию касанием **не считается** —
пересечения диапазонов нет. Экономически стоящий лимитный ордер в такой момент
исполнился бы. Расхождение оставлено осознанно: условие касания задано в постановке, а
«додумывать» исполнение там, где диапазоны не пересекаются, значит придумать сделку,
которой нет в данных. На практике случай почти всегда поглощается стопом — уйти за зону
с выгодной стороны, не задев её, это движение к стопу. Покрыто тестом.

**Сопровождение после входа не меняется.** Вход происходит внутри часа, поэтому первым
баром сопровождения становится синтетический **остаток часа от минуты входа включительно**
(`partialHourFromFill`), а дальше идут обычные часовые бары. Так `manageTrade` V3.3
получает ровно ту же семантику («бар входа считается первым баром»), но не видит движения,
случившегося ДО входа, — иначе минутный провал до входа выдал бы ложный SL.

### `src/services/signals/live/lifecycle.ts` (ветка только для V3.4, строго opt-in)

- Новый необязательный аргумент `opts?: { m1?: ArchiveCandle[] }`. V3.0/V3.3 его не читают.
- Ветка V3.4 срабатывает **только если минутные свечи переданы явно и непусты**.
  Ни один продуктовый вызов их не передаёт, поэтому поведение рантайма не изменилось:
  V3.4 по-прежнему ведётся `trackCorridor` по часовым барам.
- Проверка стоит **до** правила «бар сетапа последний ⇒ UNCHANGED»: минутный вход
  наступает внутри часа, когда часовой бар ещё не закрылся.
- Внутри самой ветки — fail-closed: пустая серия даёт `SKIP`, а не выдуманный вход.

**Принятое решение: не выбирать сейчас ни один из вариантов.** Маскировать
`WAITING_FOR_ENTRY` под `ACTIVE` и `MISSED` под `CANCELLED` — значит зафиксировать
семантику до того, как она спроектирована. Канонические статусы проектируются отдельно,
после аудита продакшена.

## 5. Подключение к живому контуру — НЕ ДЕЛАЕТСЯ

Ядро готово и изолировано, но **намеренно не подключено**. Ниже — оценка объёма работ на
будущее, а не план на сейчас. Каждый шаг меняет поведение живого контура:

1. **Монитор позиций** (`signalMonitor.js`): для групп со стратегией V3.4 дополнительно
   запросить `1m` (≈ 300 баров) и передать третьим аргументом
   `core.trackPublishedSetup(entry, candles, { m1 })`. Плюс добавить `'1m'` в `CACHE_TTL_MS`.
2. **Серверный сканер** (`strategyEngine.js`, `syncLifecycleFromCore`): перестать писать
   `rec.fill`/`rec.outcome` реплея для V3.4 — иначе часовой фил из ретроспективы будет
   перезаписывать минутный вход. Владельцем жизненного цикла V3.4 становится монитор.
3. **Браузерный движок** (`LiveSignalEngine.trackOpenSetups`): либо тоже тянуть `1m`, либо
   осознанно оставить V3.4 в `SKIP` во вкладке (журнал в браузере — диагностика,
   источник истины и так серверный).

Ретроспектива реплея V3.4 **не трогается**: `fill`/`outcome` не удаляются, расчёт не
меняется, UI и notes не переписываются. Отмечено, что после возможного подключения
исторические метрики V3.4 перестанут быть сопоставимыми (доля исполнений сегодня 100 %),
но это следствие будущего решения, а не текущего состояния.

## 5a. KNOWN ISSUE (зафиксировано, не исправляется сейчас)

> **V3.4 historical replay currently uses existing 1H next-bar execution semantics.
> Proposed real-entry lifecycle is not connected and is not canonical yet.**

Единое решение принимается позже и сразу по всем шести пунктам, чтобы не получить
частично согласованную систему:

1. entry semantics;
2. `WAITING_FOR_ENTRY`;
3. fill model;
4. historical replay;
5. live monitor;
6. LONG/SHORT conflict policy.

Порядок работ: сначала READ-ONLY аудит жизненного цикла в продакшене (APT, SOL и глобально
все ACTIVE-сигналы), затем проектирование канонических статусов, и только после этого —
вопрос о миграции и подключении.
