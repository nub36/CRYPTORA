## B. Шапка — корень проблемы

`src/components/layout/Header.tsx`. Строка: `mx-auto flex min-w-0 max-w-[1920px] flex-wrap items-center gap-x-2`, три ребёнка: бренд `order-1 … shrink-0` (:392), `<nav>` `order-3 … xl:flex-1 xl:justify-center` (:436), контролы `order-2 ml-auto … shrink-0` (:479).

Каждый пункт навигации был `relative flex shrink-0 items-center … whitespace-nowrap` (ссылка :215, обёртка дропдауна :277, кнопка :283) — **без `truncate`, и `<nav>` без `overflow`**.

Несжимаемый (`shrink-0`) неразрывный (`whitespace-nowrap`) элемент физически не может уложиться в отведённый `flex-1`. Когда содержимое шире контейнера, оно выплёскивается наружу; `justify-center` делает выплёск **симметричным** — влево под бренд и вправо под контролы. Отсюда `CRYPTORA` наезжает на `Обзор` именно при сужении окна.

`overflow-hidden` на `<nav>` неприменим: внутри живут выпадающие меню.

## C. Исправление шапки

Архитектурное, а не `margin-left` под один экран — 5 правок:

| Узел | Было | Стало |
|---|---|---|
| пункт-ссылка (:215) | `shrink-0 … whitespace-nowrap` | `min-w-0 shrink …` + `<span class="truncate">` |
| обёртка дропдауна (:277) | `shrink-0` | `min-w-0 shrink` |
| кнопка дропдауна (:283) | `shrink-0` | `min-w-0 shrink` |
| подпись дропдауна | без усечения | `<span class="truncate">` |
| шеврон | без ограничения | `shrink-0` |

Теперь при нехватке ширины пункт **сжимается и усечается**, а не выплёскивается: бренд и контролы остаются `shrink-0`, навигация — единственная гибкая зона. Перекрытие стало структурно невозможным на любой ширине, включая 1024.

Существующий компактный режим сохранён и не менялся: `text-[13px]` → `2xl:text-sm`, иконки `hidden … nav2xl:block`, инлайн-поиск `hidden navxl:block`, бейдж версии `navxl:inline-block` (кастомные брейкпоинты `navxl:1440px`, `nav2xl:1700px`).

Бюджет ширины на 1280 px (консервативно, 7,4 px/символ Inter 13 px): навигация ≈ 586 + бренд 137 + контролы 240 + отступы 32 = **995 px < 1280**. Запас есть.

## LIQ-D. Что на самом деле означало «24ч»

До правки «24ч» было **фикцией в двух местах**:

1. **Хронология.** `buildTimeline` всегда строил ровно 8 трёхчасовых баров
   `WINDOW_24H_MS / TIMELINE_BUCKETS` от `now - 24h` до `now`, независимо от
   длительности наблюдения. При подключении на 40 минут семь баров были
   пустыми и подавались как наблюдения.
2. **Overview.** Заголовок карточки был жёстко `Ликвидации · 24ч`, хотя
   `hasFullObservationWindow` был `false`. Страница `/liquidations` при этом
   честно писала «С момента подключения» — то есть две страницы противоречили
   друг другу (ровно то, на что указывает §51).

Страница `/liquidations` в шапке уже переключалась на «С момента подключения»,
но сами агрегаты подписывались `totalLong24h`/`eventsCount24h` и карточки
лонгов/шортов писали «(24ч)».

**Исправлено:** бары строятся только внутри фактического наблюдения, «24ч»
появляется только при `hasFullObservationWindow`, Overview использует ту же
проверку. Поля схемы (`total24h`, `eventsCount24h`) переименовывать не стал —
это публичный контракт типов, а честность обеспечена на уровне подписей и
флага окна.

## LIQ-E. Нормализация Binance

Поток `!forceOrder@arr`, payload `{ o: { s, S, p, ap, q, T } }`.

```
symbol    = getAssetByBinanceSymbol(s) ?? s без суффикса USDT
price     = ap ?? p ?? 0            // ap — средняя цена исполнения, приоритетнее
qty       = q
amountUsd = price × qty             // q уже в базовой монете → множителя нет
side      = S === 'SELL' ? LONG : SHORT
id        = `liq-${symbol}-${T}-${price}-${qty}`
```

Отбрасывается при `!Number.isFinite(amountUsd) || amountUsd <= 0`.

## LIQ-F. Нормализация Bybit

Поток `allLiquidation.{symbol}`, payload `{ T, s, S, v, p }`.

```
price     = p      // bankruptcy price
qty       = v      // размер в монете
amountUsd = p × v
side      = S === 'Buy' ? LONG : S === 'Sell' ? SHORT : отбрасывается
id        = `liq-bybit-${symbol}-${T}-${p}-${v}`
```

Неизвестная сторона (`S` не Buy/Sell) отбрасывается, а не угадывается —
проверяется тестом.

## LIQ-G. Нормализация OKX

Поток `liquidation-orders`, payload `{ instId, details:[{ bkPx, sz, side, posSide, ts }] }`.

```
instId    только *-USDT-SWAP (USDT-линейные свопы)
ctVal     из публичного REST /api/v5/public/instruments?instType=SWAP
qty       = sz × ctVal          // sz в КОНТРАКТАХ, не в базовой монете
amountUsd = bkPx × sz × ctVal
```

**Ключевое:** контракты **не** приравниваются к количеству базовой монеты.
`ctVal` обязателен; если каталог инструментов недоступен или для `instId`
нет `ctVal`, событие **отбрасывается целиком** — нотионал не оценивается.
Если REST не ответил, поток честно остаётся `unavailable`
(`loadInstruments()` бросает, оценочные `ctVal` не подставляются).

Пример из теста: 100 контрактов BTC-USDT-SWAP при `ctVal = 0.01` и
`bkPx = 60000` → **$60 000**, а не $6 000 000.

## LIQ-H. Маппинг сторон

Семантика обратная у всех трёх бирж, и у каждой своя форма:

| Биржа | Поле | Правило |
|---|---|---|
| Binance | `o.S` (сторона ордера закрытия) | `SELL` ⇒ ликвидирован **LONG**; `BUY` ⇒ **SHORT** |
| Bybit | `S` | `Buy` ⇒ ликвидирован **LONG**; `Sell` ⇒ **SHORT** |
| OKX | `posSide`, fallback `side` | `long`/`short` напрямую; иначе `sell` ⇒ **LONG**, `buy` ⇒ **SHORT** |

OKX использует `posSide` как первичный источник — это прямая сторона
позиции, а не вывод из стороны ордера. На каждую биржу написан
регрессионный тест (§54).

## LIQ-I. Дедупликация

`recordEvent()` отбрасывает событие, если `events.some(e => e.id === event.id)`.
Идентификаторы детерминированные, из полей биржевого payload — `Math.random()`
не используется:

- Binance: `liq-${symbol}-${T}-${price}-${qty}`
- Bybit:   `liq-bybit-${symbol}-${T}-${p}-${v}`
- OKX:     `liq-okx-${symbol}-${ts}-${bkPx}-${sz}`

Префиксы биржи исключают столкновения между биржами: одно и то же событие,
пришедшее с Bybit и OKX, считается двумя (проверяется тестом). Повторный
приём того же кадра при reconnect агрегаты не удваивает.

Отдельного exchange event ID биржи в этих payload нет, поэтому используется
детерминированный составной ключ — как и предполагал §47.

## LIQ-J. Переподключение — найден и исправлен дефект

**Дефект подтверждён, в текущем `main` он НЕ был исправлен.** Прежний код:

```ts
private scheduleReconnect(): void {
  if (this.reconnectAttempts >= this.maxReconnectAttempts) {   // 10
    this.setState('unavailable');
    return;                    // ← сокет умирал навсегда
  }
  ...
}
```

`reconnectAttempts` сбрасывался только на успешном `onopen`, поэтому после
10 неудач подряд транспорт больше никогда не восстанавливался — до
перезагрузки вкладки. UI при этом показывал «недоступен» как постоянное
состояние.

**Исправлено** в `LiquidationStreamTransport.ts`:

- попытки **не ограничены** — восстановление продолжается бесконечно;
- `unavailableAfterAttempts` (10) теперь только порог честной метки в UI,
  а не отказ от восстановления;
- backoff экспоненциальный с потолком `reconnectMaxDelayMs` (30 с) —
  не tight loop;
- счётчик сбрасывается на успешном `onopen`;
- добавлены триггеры мгновенного восстановления на `visibilitychange`
  (возврат на вкладку) и `online` (появление сети) — ждать остаток
  экспоненциальной паузы при уже появившейся связи бессмысленно;
- `isExplicitlyClosed` и флаг «попытка уже запланирована» исключают
  дублирование таймеров;
- `disconnect()` снимает слушатели и останавливает восстановление.

Покрыто четырьмя тестами: восстановление после >10 неудач, отсутствие
tight loop, сброс счётчика, остановка по `disconnect()`.

## LIQ-K. Хронология — переделка

**Было:** 8 фиксированных трёхчасовых UTC-баров за 24ч, подпись
«Хронология ликвидаций по 3-часовым барам за 24ч», события вне сетки
молча терялись, тултип показывал только одну сторону.

**Стало:**

- период — от `min(observationStartedAt, earliestEvent)` до `now`, но не
  глубже 24ч; ненаблюдавшиеся бары не строятся вовсе;
- первый бар начинается ровно со старта наблюдения (без выравнивания назад
  по сетке) — иначе при коротком окне единственный бар оказывался
  частично ненаблюдавшимся и весь период выглядел пропуском;
- **адаптивный шаг** (§38): <1ч → 5м, 1–2ч → 15м, 2–6ч → 30м, 6–24ч → 1ч,
  ≥24ч → 3ч; лимит 48 баров;
- подпись фактического периода: `Наблюдение: 05:12 UTC — 05:52 UTC · шаг 5м, 8 бар.`;
- заголовок: `Liquidations Timeline · с момента подключения` или `· 24ч`;
- **тултип** (§39): Time, Long, Short, Total, Event count;
- флаг `observed` на каждом баре; UI рисует ненаблюдавшиеся приглушённо.

## LIQ-L. Разбивка по биржам

Было: только биржи с событиями (`exchangeTotals` строился из событий),
поэтому Binance с нулём исчезал из списка, а «3/3 потоков» соседствовало

Стало (§40, §48): в разбивке **все три биржи всегда**. Ноль — валидное

сокет больше не прячется за общим числом.

## LIQ-M. Топ активов — root cause «APT $11.98K / Shorts: $0.00»

**Это не баг данных, а баг презентации.** В `assetBreakdown` инвариант
`totalUsd = longUsd + shortUsd` выполнялся всегда (строится как сумма).
Карточка показывала только **Total** и **Shorts**, опуская Long. Для APT
все $11.98K были ликвидациями лонгов, поэтому `Shorts: $0.00` при
`Total: $11.98K` выглядело как расхождение, которого не существовало.

Стало — таблица (§41): `Symbol · Total · Long · Short · Events · Largest`,
сортировка по Total убыв. На мобильных — компактные карточки.
Инвариант закреплён тестом по каждому инструменту, плюс сходимость сумм
по биржам и инструментам к общему итогу.
